# Agent Harness — Distributed, Scalable Architecture
## Part 5: Domain-Specific Control Loops — Process as an Executable Definition

This paper records the next architectural emphasis for the harness: author multiple, purpose-built Temporal workflows for distinct use cases and business domains. Each workflow is a durable control loop that defines how a class of work proceeds, rather than leaving that procedure solely to a model prompt or a skill document.

**This is also the harness's entire notion of a "skill."** There is no separate prose-procedure mechanism alongside it. Two earlier ideas are superseded outright, not merely extended: the harness-owned procedural-memory subsystem (`load_skill`/`RecordSkill`/`SkillDiscover`/`skill_procedures`, which auto-recorded prose procedures from transcripts and was removed in the turn-pipeline redesign — `docs/components/turn-pipeline.md`) and the never-built plan to source curated prose skills from mcp-hub's `search_skills`/`get_skill` (`docs/components/tool-registry.md`). Both are gone. A skill's body is a Temporal workflow, not a document, authored like code, discovered locally, never recorded from a transcript.

This extends, rather than replaces, the shared Session Coordinator, Turn Workflow, activity, state, workspace, and tenancy designs in Parts 1–4. It does **not** reintroduce a pre-turn classifier or router — `turn-pipeline.md`'s core principle (no classifier deciding a lane, no router deciding which subsystems to consult) stays intact. Workflow/skill selection here is a model-decided, mid-loop tool call, symmetric to how the model already decides when to call `discover_tools` or `spawn_subagent` — never a step the harness runs before the model sees the request. See *Discovery and Invocation* below.

---

### The Decision

**Make domain-specific control workflows the first-class specialization mechanism.** A workflow encodes the meaningful states, transitions, waits, approval points, retry boundaries, and completion rules for a particular kind of work. Temporal executes that definition durably.

There is not one universal loop with a growing prompt full of exceptions. There can be many carefully authored workflows, for example:

- a change-control workflow that gathers repository context, plans, requests approval where needed, delegates an implementation, verifies the result, and prepares a commit;
- a research workflow that establishes a question and evidence plan, runs bounded source collection, evaluates coverage, resolves contradictions, and produces a traceable synthesis;
- an operations workflow that classifies an incident, gathers diagnostics, applies only permitted mitigations, waits for signals or human input, and records the outcome.

These are examples of shapes, not a fixed product taxonomy. A new workflow is justified when a domain has durable process semantics worth owning explicitly: ordering, safety boundaries, external waits, failure handling, governance, or completion criteria that should not depend on a model remembering instructions.

---

### A Skill Is a Workflow, Not a Document

A conventional skill is a probabilistic instruction-following aid: a document tells a model how to approach a task, which tools to prefer, and what good output looks like. The generic agent loop still asks the model to choose whether, when, and in what order to follow those instructions — and, in this harness's own prior history, to record new ones from its own transcripts, which fragmented into partial, half-learned procedures across multi-message tasks (`turn-pipeline.md`'s "Skill recording" section has the full account).

This design replaces that document-and-recording model with an executable one. A skill *is* a domain-specific control workflow:

| Concern | Prose skill (removed) | Skill as a domain workflow |
|---|---|---|
| Process owner | Model interpretation | Executable workflow definition |
| Sequence and transitions | Suggested by instructions | Encoded and enforced in workflow state |
| Interrupts, waits, and approvals | Prompt-dependent or ad hoc | First-class Temporal signals and durable waits |
| Recovery after a worker failure | Model must reconstruct intent | Workflow resumes from recorded history |
| Auditability | What the model chose to do | State transitions and activities are explicit |
| How it's learned | Recorded from transcripts (removed — fragmented, noisy) | Authored once in code, versioned like any other artifact |
| Reuse | Reuse instructions | Reuse activities while varying process composition |

This is not merely "deterministic workflows versus probabilistic models." Model judgment remains useful—and often necessary—within a step: interpret evidence, choose among allowed actions, summarize a result, or decide *whether* a given skill applies at all. The distinction is that once a skill workflow is entered, it owns the enclosing process and the model does not get to silently skip or reorder its governing stages.

There is no fallback prose-skill tier for cases that don't warrant a full workflow. If a procedure is too lightweight to justify authoring a workflow, it stays as ordinary static-core guidance or a scratchpad note — it is not packaged as a "skill" in this harness at all.

---

### Composition: Many Workflows, Shared Activities

Multiple workflows do **not** imply copying the low-level “call a model, invoke a tool, persist state” loop into every domain implementation. Activities remain the shared, side-effecting building blocks:

- model calls and context assembly;
- tool and delegated-agent execution;
- state persistence, retrieval, and memory access;
- outbound delivery, approval requests, and other user interaction;
- workspace operations, claim-check storage, and explicit subagent merge-back.

Each workflow chooses and sequences these activities according to its domain. The activity contract remains stable, observable, retryable, and tenant-scoped; the workflow supplies the process policy. A change-control workflow and a research workflow may both call a model, search, delegate work, and persist results, but they need not share the same gates, evidence thresholds, or finish conditions.

This is the intended boundary:

```text
shared activities + shared state/workspace contracts
                         ↓
      authored Temporal workflows for specific domains
                         ↓
      durable, governed execution of a domain process
```

### Discovery and Invocation

There is no pre-turn selector. The gateway stays a thin ingress layer (identify tenant/session, normalize the event, `SignalWithStart` to the Session Coordinator); the coordinator forwards to the active turn, or starts an ordinary `TurnWorkflow` — or, when the session's own mode says otherwise, starts that mode's own turn-shaped workflow instead (see *Session-Persistent Modes* below, which this section now assumes rather than a superseded by-name-tool-call design).

**2026-09-27, superseded outright, not extended:** an earlier design (built the same day, replaced the same day after user correction) made every skill a **static, always-on capability** callable directly by its own name — mirroring `spawn_subagent`/`shell_exec`, with an optional `skill-hub` semantic-search convenience (`discover_skills`) for extra detail. That entire mechanism (`turn.go`'s `runSkill`, `types.SkillWorkflowInput`/`SkillWorkflowOutput`, `ToolCallRef.UseSkill`, `ReadSkillCallArguments`/`CloseSkillCall`, `discover_skills`/`search_skills`, `skill_hub.py`) is deleted, not kept alongside modes as a second dispatch shape — see the *Session-Persistent Modes* section's own Notes Log entries for why. A skill *is* a mode now, with exactly one invocation path:

- **Authoring** — a mode's own Go workflow type is registered directly in `cmd/loop-worker/main.go` (`mode_journaling.go`/`mode_service_monitoring.go`, a real `types.TurnInput`/`TurnResult`-shaped `runTurn` caller) and its name added to `activities/activities/llm.py`'s `MODE_TURNS` dict — a fixed, deployment-wide fact about which names are genuine dispatch targets, identical for every tenant. Per-tenant *enablement* of that name is separate, genuine per-tenant data: a row in this tenant's own Postgres `skills` table (migration `040_skills.sql`), `enabled` per row. `tenant_worker.py` loads this tenant's enabled rows at startup (`skills.init(pool)`) and calls `llm.load_skills(...)`, which intersects the two into `llm.ENABLED_MODES`. Gateway's `GET /skills` (`workflows/internal/gateway/web/skills.go`) queries the same table directly.
- **Discovery** — none needed, and no separate mechanism for it: `switch_mode`'s own tool description already enumerates every mode this tenant currently has enabled, by name, with a one-line description of when to use it. There is nothing to search for that isn't already stated up front.
- **Invocation** — the model calls `switch_mode(mode="journaling")` (an ordinary tool, not a skill-shaped one), which signals the session's own `CoordinatorWorkflow` to dispatch that mode's own turn-shaped workflow for the *next* message — see *Session-Persistent Modes* for the full mechanism. A skill is never called directly by its own name, and never dispatched as a nested child of an already-running turn (contrast `spawn_subagent`, still exactly that — see *Skill Workflows Are Independent of Subagents* below).

Once entered, a mode turn owns its own conversation until it leaves:

1. it is a real top-level turn with full conversational continuity, not a scoped fragment carrying only what it was explicitly handed (see *Session-Persistent Modes*);
2. it progresses through its domain stages using the exact same shared activities and reason-act loop any ordinary turn uses, governed entirely by its own curated system prompt rather than Go-coded stages;
3. it responds to the same interruption/cancellation signals any turn does;
4. it persists observable outcomes the same way any turn does; and
5. it leaves by the model calling `switch_mode()` bare, once its own curated prompt judges the activity itself — not just one reply — genuinely finished.

Long-lived coordination and short-lived execution keep the existing split: the Session Coordinator is long-lived and deliberately small; a turn (mode or otherwise) is bounded and disposable, dispatched fresh per message. Workflow evolution must follow Temporal-compatible versioning practices when in-flight executions may exist.

### Determinism Where It Counts, Not All the Way Down

A mode's *process* — when to confirm before acting, how to verify a write actually landed, when the activity is genuinely finished — stays governed, but by a curated system prompt, not hand-parsed guesswork bolted onto Go code. That was a real mistake made and corrected while building the first non-trivial skill (`journaling`, committing an entry to a Notion database whose exact API response shapes weren't known in advance): interpreting messy external reality (did this search result actually contain the thing being looked for, did a write actually succeed) is a model's job.

**2026-09-27, superseded:** an earlier design routed this interpretation through a separate mechanism, `workflow.RunReasonActLoop` invoked via a scoped `skills.RunReasoningTurn(ctx, input, idSuffix, objective)` helper — a nested `turns` row (`parent_type = "skill"`) distinct from the top-level turn, closed out via a distilling Python activity (`SummarizeReasoningTurn`). That mechanism produced a real production incident (a reasoning turn returned "done" having made zero tool calls at all, and the skill told the user "Saved" having written nothing — see Notes Log) and was deleted wholesale once both skills migrated off it, along with its incident patches (`no_action_taken`, `exclude_skill_name`).

There is no separate mechanism to describe in its place, because there is no separate turn shape any more: a mode turn *is* an ordinary top-level turn (`runTurn`, the same body `TurnWorkflow` itself uses), so it already gets the model's real judgment for free, through the exact same `ModelCall`/`ToolCall` loop, the same `ask_user` → `UserInputRequestWorkflow` path, the same default tool catalog. A mode's own curated system prompt is what actually governs its "confirm first," "verify by reading back," and "recognize when genuinely done" steps — ordinary prompt instructions followed with ordinary tools, not new workflow states. The tool-restriction question the old design's own doc left open (a scoped reasoning turn could technically call `spawn_subagent`/`shell_exec` even though a well-written objective never would) is moot now for the same reason: there is no separate, narrower turn to restrict — a mode turn already IS a full top-level turn, by design, not an accident to gate.

### Session-Persistent Modes

The scoped-reasoning-bridge pattern above (`RunReasoningTurn`) fit a skill that does one bounded piece of work per invocation and hands control straight back. It does not fit a skill whose whole point is staying the active handler across an arbitrary number of *future* messages, not just the one that triggered it (`journaling`: the user may add several entries across a sitting before they're actually done). 2026-09-27, after `journaling` hit exactly that mismatch in production (see Notes Log), it was rebuilt on a different, session-level primitive instead of stretching the scoped-reasoning-bridge to cover both shapes — and `service_monitoring` followed the same day, even though its own activity is naturally single-round (see below): the mode mechanism doesn't require staying resident, only a curated prompt that calls `switch_mode()` back to chat as soon as its one round concludes rather than staying open for more. Once both were migrated, the scoped-reasoning-bridge itself (`RunReasoningTurn`/`support.go`, its `no_action_taken`/`exclude_skill_name` patches, `SummarizeReasoningTurn`) had zero remaining callers and was deleted wholesale, not left as unused infrastructure.

- **`sessions.mode`** — one column (migration `041_sessions_mode.sql`), `"chat"` by default. The session's own `CoordinatorWorkflow` holds the operational copy in memory (updated live by a signal); the Postgres column is purely the external/client-visible mirror of it, on the same footing `turns.status` already has — never read back by the coordinator for its own dispatch decisions.
- **`switch_mode(mode)`** — an ordinary, activity-backed tool (`tools.switch_mode`), not a peeled meta-tool like `report_status`. Calling it with a mode name signals the coordinator and writes `sessions.mode` in one call; calling it bare defaults to `"chat"`. Deliberately not tied to a turn's own ordinary completion: `report_status` fires every step regardless of outcome, so if reaching "done" ever moved `mode` on its own, a session-persistent mode would revert after its very first reply. Only an explicit `switch_mode` call changes it, in either direction — chat → a mode, or a mode → chat once the model judges the activity itself, not just one reply, is actually finished.
- **`turnWorkflowTypeName(mode)`** (`turn.go`) — resolves a mode directly to the Temporal workflow type name the coordinator dispatches for the *next* message: `"TurnWorkflow"` for `"chat"`, the mode string itself otherwise (`workflow.ExecuteChildWorkflow` by bare type-name string). `llm.MODE_TURNS` (Python) is the one small, hand-maintained list of names actually safe to use this way — a mode target must be a real `types.TurnInput`/`TurnResult`-shaped workflow (`runTurn`'s own shared body, `mode_journaling.go`/`mode_service_monitoring.go`). This is the *only* skill-dispatch shape in this codebase (see Notes Log, 2026-09-27 follow-up) — there is no separate one-shot dispatch mechanism to distinguish it from. Deliberately a plain Python dict, not a per-tenant Postgres row — *which* names are genuine Go dispatch targets is a fixed, deployment-wide fact about this codebase's own source, identical for every tenant, changing only when a developer does that rewrite.
- **Per-tenant enablement, kept, not dropped** — a name being a real dispatch target (`MODE_TURNS`) is necessary but not sufficient: whether *this tenant* may switch to it is still genuine per-tenant data, read from the `skills` table (`enabled` per row — `service_monitoring` stayed seeded `enabled=false`/opt-in, `journaling` stayed `enabled=true`/on for everyone, migration `040_skills.sql`, unchanged by the mode rewrite). `llm.load_skills(entries)` intersects the two into `llm.ENABLED_MODES`, which is what `switch_mode`'s own schema (its enum only ever lists a tenant's actually-enabled modes) and its handler's validation both read — `MODE_TURNS` alone is never enough to allow a switch.
- **Continuity for free** — a mode turn is a real top-level turn (`ParentType: "session"`, its own `turn_id`), not a scoped sub-turn nested under something else. It gets full conversational history through the exact same LCM context-assembly path any ordinary turn already uses — no bespoke "pass the initial context along" plumbing needed at the handoff.
- **Curated, not generic, framing** — `model_call.py` picks a mode-specific system prompt (`ModelCallInput.mode`, threaded through from `RunReasonActLoopInput.Mode`, set once by the calling workflow since it already knows its own identity at compile time) instead of the session's stored prompt. This is *not* a diff against `DEFAULT_SYSTEM_PROMPT` (same reasoning `VOICE_SYSTEM_PROMPT` already documents for itself) — critically, it must not mention "registered skills" the way the default prompt does, since that exact framing is what caused a skill's own scoped reasoning turn to recursively call itself in the incident that started this rebuild.
- **No native "stay resident" machinery** — confirming an entry before writing it, verifying a write by fetching the page back, and deciding when the user is actually done are curated *prompt* instructions the model follows with its ordinary tools (`ask_user`, `discover_tools`/`call_tool`, `switch_mode`), not new Go-side states. Session persistence itself is entirely the coordinator's dispatch decision, repeated per message — nothing about a mode turn's own workflow body differs from an ordinary turn's.

### Skill Workflows Are Independent of Subagents

A skill (a mode) and `spawn_subagent` are two separate primitives — not one generalizing the other, and not competing for the same use case. **2026-09-27:** before the mode rewrite, this distinction was "both are Temporal child workflows, dispatched differently" — a skill was a bounded child workflow of a fixed, purpose-built type, nested under whichever turn called it. That's no longer the shape; the real distinction now is about *where in the dispatch tree* each one runs:

- `spawn_subagent` is the model's choice to delegate open-ended scoped *reasoning* work **mid-turn**. The child is another `TurnWorkflow` (same type, recursively), nested under — and dispatched by — the turn that called it, receiving a clone of the parent's session context plus an explicit brief. It decides its own approach, and its result folds back as an observation into the turn that spawned it.
- A mode is the model's choice to change **which workflow the coordinator dispatches for the session's own next message.** It is never nested under, or dispatched by, an in-flight turn — `switch_mode` signals the session's own `CoordinatorWorkflow` directly, and the mode's own turn starts fresh, at the top level, the next time a message arrives. It is a real top-level turn (full LCM context, no clone, no brief needed since it isn't scoped to one calling turn's context at all), not a bounded child of anything.

A subagent's own turn can itself call `switch_mode` if its author's objective calls for it — the two primitives compose (a subagent's own turn is still an ordinary turn, with the same tools) — but a mode is never itself dispatched as a nested child the way a subagent is.

Control workflows (of either kind) do not carry the entire system in their history. Postgres remains the durable state and audit layer. The session filesystem remains the workspace and claim-check store for files and large payloads. Context and memory are assembled through their dedicated contracts. This division lets workflow code make deterministic control decisions from IDs, status, and small structural metadata while activities handle non-deterministic I/O and large content.

Tenancy is not an afterthought to workflow selection. A selected definition must run within the tenant’s Temporal namespace and worker boundary, using that tenant’s database, credentials, permissions, and session storage. A control workflow can therefore express domain policy without creating a path around the isolation model.

---

### Authoring Criteria and Tradeoffs

Not every task deserves a new workflow. A generic turn remains appropriate for open-ended assistance or low-consequence exploration. Introduce a purpose-built workflow when the same process recurs and the harness should enforce something real: a required sequence, approval boundary, evidence standard, retry policy, handoff rule, or terminal condition.

The cost is intentional design and maintenance. Every workflow needs clear states, activity contracts, observability, versioning, and tests. That cost is worth paying only when executable process ownership creates more value than a prompt convention. Shared activities and common state/workspace contracts keep that cost from becoming duplicated infrastructure.

---

### Consequence

Agent Harness is not defined by a library of prose skills wrapped around a generic agent loop. It is defined by durable, inspectable, domain-aware control workflows that orchestrate shared capabilities and model judgment — and those workflows *are* this harness's skills, entered by explicit model decision (`switch_mode`) with every option already stated up front, not a separate packaging layer bolted on top of execution.
