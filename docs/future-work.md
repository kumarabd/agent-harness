## 1. Do we really need Temporal? (Orchestration cost/benefit)
**Status: RESOLVED FOR NOW — keeping Temporal.** But recording the reasoning so we can revisit.

The wondering: is a full orchestration layer overkill when "all we need is to trigger a job"?

**What Temporal buys us (beyond durability/replay):**
- Distributed active-session guard: one-workflow-per-ID guarantee. Without Temporal we'd hand-build this with distributed locks or careful queue partitioning.
- Interrupt-via-signal mechanism: comes built in; otherwise hand-rolled.
- Mid-turn crash recovery: if a worker dies several tool calls deep, Temporal resumes exactly where it left off. A plain job queue restarts the whole turn and re-runs side effects.

**Counterpoint (when a plain queue might suffice):**
- If turns are mostly short AND re-running a whole turn on failure is acceptable, a plain queue (Redis/SQS) with idempotent handlers may be enough.
- The value of orchestration scales with how long and how side-effect-heavy the turns are.

**To revisit:** profile actual turn length and side-effect density in our workload to confirm Temporal earns its keep.

## 2. Real-time / Voice Interaction
**Status: OPEN — parked for later exploration.**

The tension:
- Everything designed so far is turn-based and durability-first — optimized for text, where a few hundred ms of queue + persist overhead is invisible.
- Voice is continuous and low-latency — even ~200ms of added latency is a perceptible, awkward pause.

**Working hypothesis:**
- A durable workflow-per-turn does NOT belong on the hot path of a voice interaction.
- Likely want a SEPARATE real-time path: a persistent low-latency session that streams audio in and out.
- Temporal sits BEHIND that real-time path, handling durable/heavier side effects (actual tool execution, state persistence) — not on the hot path.

**To trace later:** what the split (real-time path in front, durable path behind) looks like end-to-end — where audio streaming lives, how it hands off to durable tool execution, how state stays consistent between the fast path and the durable path.

## 4. Model Sometimes Ends a Turn With No Real Content — a Prompt Problem, Not a Retry Problem
**Status: ROOT CAUSE CONFIRMED WITH REAL EVIDENCE, fix deliberately deferred.** Found while testing the multi-session/branching feature (`components/gateway.md`'s "Resolved: Multi-Session Channels") live: after a gated tool call gets approved and executes successfully, the turn sometimes completes with the final assistant message's `content` empty — the UI (`agent-web`'s `turnToMessages`) then wrongly labels this "(this turn was cancelled)" even though the turn genuinely completed and the tool call genuinely succeeded.

**Confirmed mechanism, not LLM randomness** — verified directly: reconstructed the exact real conversation via `lcm.assemble()` (the same function `ModelCall` itself uses) for a real session that had hit this, and called the real model 5 times with that exact input. All 5 came back `content=''`, `finish_reason='tool_calls'`, with the model calling *only* `declare_next_step_hint` (`llm.py`'s meta-tool, instructed via `DEFAULT_SYSTEM_PROMPT` to be called "alongside anything else" every response) — deterministic for this conversation shape, not sampling noise. Likely trigger: the model had already narrated its *intent* in the message immediately before the tool call (e.g. "I'll run the command with an added newline"), and the user's own message never explicitly asked for the result to be reported back — the model appears to treat the loop as already closed once the tool succeeds, satisfies the one instruction it's told to always follow (`declare_next_step_hint`), and skips the separate "then summarize the result in plain text" instruction.

**A proposed fix was considered and explicitly rejected**: retrying the same `ModelCall` when a response has neither real content nor real tool calls. Rejected because the mechanism above is deterministic for a given conversation — a bare retry with the identical input would almost certainly reproduce the exact same `declare_next_step_hint`-only response again, not fix anything. Any real fix needs to either change the conversation before retrying (e.g. append an explicit corrective nudge) or change the system prompt itself so the model doesn't get into this state in the first place.

**Deliberately deferred, at the user's direction**: prompt tuning is its own real analysis task (understanding exactly why this specific instruction shape produces this behavior across a range of real conversations, not just the one traced here, and fitting a change that doesn't regress the `declare_next_step_hint` mechanism's own purpose), not something to bolt on as a quick reaction to one traced case.

**To revisit**: a real prompt-engineering pass on `DEFAULT_SYSTEM_PROMPT` (`activities/activities/llm.py`) — likely separating "you must always end with a plain-text summary" from the `declare_next_step_hint` instruction more forcefully, or restructuring how/when that meta-tool gets requested. Also worth deciding, once a fix direction is chosen: should the *symptom* (frontend mislabeling a content-empty completed turn as "cancelled") get fixed independently in the meantime, since it's user-visibly wrong regardless of the root cause's timeline?
