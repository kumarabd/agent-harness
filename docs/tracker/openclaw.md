# Tracker: OpenClaw

> Last verified: 2026-08-07, via a web-research pass (official docs at docs.openclaw.ai, repo github.com/openclaw/openclaw, Wikipedia, Forbes, secondary sources noted per-row). Not verified against direct source-code reading. High-confidence findings only unless flagged otherwise — see per-row confidence notes and caveats below.

### Important framing correction
`../01-architecture-overall-topology.md` (line 20) groups OpenClaw alongside Codex, Claude Code, OpenCode, and Hermes Agent as a peer "coding harness." Research shows this is **not quite accurate**: OpenClaw's actual center of gravity is a **general-purpose, messaging-first personal AI assistant platform** (WhatsApp, Telegram, Discord, Slack, Signal, iMessage, Google Chat) with a CLI/TUI as a secondary interface — not a dedicated coding-CLI harness. Coding capability is *delegated*, either to external harnesses (Claude Code, Cursor, Copilot, OpenCode, Gemini CLI, etc.) via its "ACP" protocol, or to a third-party community plugin (`openclaw-code-agent`) that adds git-worktree-based coding sessions on top. Core OpenClaw does still run its own native reason-act-observe loop and can execute tools directly — so the loop-level comparison in `01-architecture-overall-topology.md` isn't wrong, just worth this caveat. **Consider updating that line** to note OpenClaw's actual scope, or leave as-is if the point being made there is narrowly about the shared loop architecture.

Additional background: created by Peter Steinberger (PSPDFKit founder), launched ~Nov 2025 as "Clawdbot," renamed to "Moltbot" (Jan 2026, after an Anthropic trademark complaint) then "OpenClaw" (~Jan 29–30 2026), now stewarded by an "OpenClaw Foundation." MIT-licensed, Node.js/TypeScript, local-first (runs on the user's own device, not hosted SaaS). [Wikipedia](https://en.wikipedia.org/wiki/OpenClaw), [Forbes](https://www.forbes.com/sites/ronschmelzer/2026/01/30/moltbot-molts-again-and-becomes-openclaw-pushback-and-concerns-grow/), [github.com/openclaw/openclaw](https://github.com/openclaw/openclaw)

### Legend
- ✅ **Matched** — our design achieves equivalent or better functionality.
- 🔁 **Different by design** — deliberate divergence, not a gap (rationale linked).
- ⏳ **Not yet designed** — gap, needs a design pass.
- ⛔ **Deliberately out of scope** — considered and explicitly deferred/rejected.
- ❓ **Unverified / low confidence** — see note.

| Area | OpenClaw today | Our design | Status | Note |
|---|---|---|---|---|
| Agent loop | ReAct-style reason→act→observe, run by a local "Gateway" ("Brain" component). [docs](https://docs.openclaw.ai/concepts/agent-runtimes) | Same loop, hosted in a Turn Workflow | ✅ | Same conceptual loop; host/runtime differs entirely (see below). |
| Execution model | Not purely synchronous — sub-agents and delegated ACP sessions run as background tasks; follow-ups route to the same persistent session. No evidence of a distributed/multi-node model beyond optional remote sandbox backends. [docs](https://docs.openclaw.ai/tools/acp-agents) | Stateless Temporal worker pool, horizontally scalable | 🔁 | OpenClaw is still fundamentally a local, single-machine Gateway process — not distributed execution in the sense this design means. |
| Session/state persistence | Local files under `~/.openclaw/` — workspace, config, credentials, sandboxes; `memory/` as dated Markdown logs. ACP sessions keyed like `agent:<id>:acp:<uuid>`, resumable via `resumeSessionId`. **No confirmed database backend** (no SQLite/Postgres explicitly named in docs). [docs](https://docs.openclaw.ai/concepts/agent-workspace), [docs](https://docs.openclaw.ai/tools/acp-agents) | Postgres | 🔁 | Genuinely different tier — local files/Markdown vs. a networked DB. Not an apples-to-apples "which DB" comparison like the Hermes one. |
| Subagent / delegation model | Two distinct mechanisms: (1) **native sub-agents** — background child agent, restricted tool policy, enforced depth limit, **flat hierarchy only** (a sub-agent cannot itself spawn sub-agents) [medium confidence, DeepWiki secondary source]; (2) **ACP** — spawns an entire *external* coding harness (Claude Code, Cursor, Copilot, OpenCode, Gemini CLI, etc.) as an independent session. [docs](https://docs.openclaw.ai/tools/acp-agents) | Recursive child workflow, same workflow type at every tree depth, no depth cap | 🔁 | Notable divergence: OpenClaw's native sub-agents are explicitly capped at one level (flat), where we deliberately chose no depth cap. Worth a beat of reflection — is unlimited recursion actually needed, or is OpenClaw's flat cap evidence of a real-world reason to bound it? |
| File/workspace isolation | Default workspace is a **soft default, not a sandbox** — absolute paths can escape it unless sandboxing is explicitly enabled. When enabled, tools run under `~/.openclaw/sandboxes` (scope: agent/session/shared). **Git worktrees are used only by the third-party `openclaw-code-agent` plugin**, not core OpenClaw — each coding session gets a delegated worktree, merged/PR'd/discarded after approval. Notably, ACP-delegated external harness sessions are **not** wrapped by OpenClaw's own sandbox policy at all. [docs](https://docs.openclaw.ai/concepts/agent-workspace), [docs](https://docs.openclaw.ai/tools/multi-agent-sandbox-tools), [github.com/goldmar/openclaw-code-agent](https://github.com/goldmar/openclaw-code-agent) | Shared mount + Postgres-backed leases, per-subagent subdirectories, explicit merge-back | 🔁 | Interesting: the community plugin's git-worktree approach is exactly the option we considered and rejected (`components/session-filesystem.md`) — for the same reason we rejected it (per-worker/per-process pinning), it likely wouldn't survive a distributed worker pool either. Core OpenClaw's "soft default, opt-in sandbox" is looser than anything we've designed — we treat isolation as mandatory, not opt-in. |
| Interrupt / mid-turn handling | Explicit, well-documented "steer" system, 3 modes: **steer** (default — injects at next model-call/tool-launch boundary), **followup/collect** (waits for a later turn), **interrupt** (aborts active run, starts newest message immediately). A running tool call is never interrupted mid-flight; only *unstarted* sequential calls are skipped, in-flight parallel calls in the same batch complete. [docs](https://docs.openclaw.ai/concepts/queue-steering), [docs](https://docs.openclaw.ai/tools/steer) — **but** multiple open GitHub issues report the documented behavior doesn't reliably work in practice (steer silently degrading to followup: [#50880](https://github.com/openclaw/openclaw/issues/50880), [#48003](https://github.com/openclaw/openclaw/issues/48003)) | Real cooperative cancellation — `WAIT_CANCELLATION_COMPLETED` + mandatory per-tool heartbeating, actively tears down in-flight work, not just skips unstarted calls | 🔁 | Directly relevant to our own earlier "interrupt is described more strongly than the mechanism supports" gap (`future-work.md`) — OpenClaw's docs describe a 3-mode steering system, but their own bug tracker shows the same gap-between-claim-and-mechanism we caught and fixed in our own design before committing it to Temporal semantics. Worth citing as real-world validation that this was a genuine risk, not a hypothetical one. OpenClaw also explicitly never interrupts an in-flight tool call — closer to our "fallback" (loop-boundary-only) path than our default (active cancellation). |
| Multi-agent tool runtime selection | Model/runtime-agnostic — supports multiple providers and can run other coding CLIs as pluggable "Agent Runtimes," with priority-based selection (model-scoped → provider-scoped → auto → fallback). [docs](https://docs.openclaw.ai/concepts/agent-runtimes) | Similar shape, deliberately narrower scope: our harness IS an orchestrator over specialist CLIs (`docs/04-architecture-orchestrator-vision.md`, `components/delegated-agents.md`) — one `delegate_*` tool per supported CLI (Claude Code, Codex, Aider, ...), each with its own structured-event-stream adapter. Not designed as a pluggable priority-router; the model picks explicitly by tool name. | 🔁 | Same category of design (orchestrator-over-CLIs), same "leverage, don't rebuild" instinct, different mechanism (explicit tool per CLI vs. runtime abstraction with priorities). Worth a look if/when a real routing need surfaces that the model can't handle by choosing between tool names directly. |
| Multi-tenancy | Not applicable — local-first, single-user by design, runs on the user's own device. [github README](https://github.com/openclaw/openclaw) | Explicitly deferred, single-user for now | ✅ | Same scope decision, for what looks like similar reasoning (simplicity at single-user scale). |
| Skills system | Modular capabilities as directories with a `SKILL.md` metadata/instructions file; workspace-level skills override global/bundled ones. [docs](https://docs.openclaw.ai/) | **Reconsidered 2026-08-29** — a real mcp-hub-document-store implementation (`search_skills`/`get_skill` as two native tools) was built 2026-08-29, then reverted the same day: a skill is now being treated as an abstract concept on the memory layer (`components/memory-slot.md`) rather than a separate discovery mechanism with its own tools/index. Not built in either shape currently — see `components/skills.md`'s "Superseded" section. | ⏳ | Redirected toward this project's own memory layer rather than either OpenClaw's filesystem-directory shape or the mcp-hub-indexed-document shape originally planned here — worth another look once the memory-layer design lands. |

### Known caveats on this research pass
- A lot of "OpenClaw" content online is low-quality SEO/content-farm material (the research agent flagged ~10+ suspicious domains) generated after the project went viral in early 2026 — weighted official docs/repo/Wikipedia/Forbes over these, per-row confidence noted above.
- No name-collision issue found — all credible sources converge on one project.
- Star/fork counts (~247K stars / ~47.7K forks as of March 2026, reported by a secondary source) could not be independently verified — omitted from the table above as not relevant to the functionality comparison.
- A benchmark paper ("Claw-SWE-Bench," arXiv 2606.12344) uses "claws" as a generic term for agent harnesses in general — raises a real risk that some secondary-source descriptions of "OpenClaw's" specific tool-denial list/output format actually describe a different benchmarked harness, not core OpenClaw. Excluded from the table above pending better sourcing.
- Native sub-agent flat-hierarchy claim is sourced from DeepWiki (a secondary/derived-docs source), not OpenClaw's own primary documentation — flagged in its row.
