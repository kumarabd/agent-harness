# Component: Tool Registry

> STATUS: IN PROGRESS — two-tier architecture, mcp-hub adoption, per-tenant deployment shape, Postgres isolation, the mcp-hub-mediated integration mechanism, and native-tool discovery (shell-hub) resolved. Cross-language duplication (native tier only), permission gating, and tool versioning remain open.

### Role (one line)
The single source of truth for which tools an agent can invoke, their schemas, execution tiers, and (eventually) permission policy — replacing today's tool dispatch table and timing config, hand-duplicated across two languages, with something that actually scales past a handful of tools.

### Why this exists (recap)
Two hand-maintained copies of the same information exist today, and the code says so outright:
- `activities/activities/tools.py`'s `TOOL_REGISTRY` is a plain Python dict mapping tool name → handler + heartbeat/timeout tuning.
- `workflows/internal/workflow/tool_tiers.go`'s `toolActivityOptions` is a plain Go map with the same per-tool timing, and its own comment admits it: *"mirrors activities/activities/tools.py's TOOL_REGISTRY by hand... the workflow can't ask the Python activity layer for this at runtime, since it has to be set on ActivityOptions before the activity is dispatched."*

Only one tool (`shell_exec`) is real today; `search`, `slow_tool`, `noop_tool` are fixture-only demo stubs sharing one generic timing profile. A harness capable of genuinely complex tasks needs a much broader tool surface — read/edit/search-equivalent tools, not just raw shell — and hand-copying registry entries across two languages doesn't scale to that.

### Responsibilities (from architecture)
- Single source of truth for: tool name, JSON schema (name + arguments shape), execution tier (the Tier A/B/C heartbeat/timeout tuning from `components/activities-outbound-delivery.md`), and which handler implements it.
- Solve the cross-language duplication: the Go workflow needs per-tool `ActivityOptions` (heartbeat/timeout) *before* dispatch, and the Python worker needs the actual handler — both currently hand-copied from one conceptual registry that doesn't exist as a real, single artifact.
- Natural home for the permission/destructive-command gating already parked as its own open item (`future-work.md` §4, "Permission Gating for Destructive Tool Calls") — allow/deny policy per tool, possibly per-tenant.
- Per-tenant tool scoping: does every tenant get every tool, or is the tool surface itself tenant-configurable — ties into `components/multi-tenancy.md`.
- **Inherited from `components/memory-slot.md`'s resolved design** (revised 2026-08-22 — that doc dropped its generic backend-interface framing and is now opinionated to agent-brain directly): host two concrete new tools, `search` and `expand`, both calling agent-brain's `memory_search`/`memory_expand` directly. **Both unrestricted** — not the subagent-only split originally modeled on LCM's `lcm_expand`; agent-brain's `memory_expand` has no depth to escalate through, so the unbounded-re-expansion risk that guardrail existed for doesn't apply here. Not yet designed in this doc — `memory-slot.md`'s own "Resolved: Search/Expand Tools" section has the reasoning; this doc still owns the actual tool-registry entries once it's designed.

### Resolved: Two-Tier Architecture — Native Activities vs. mcp-hub-Mediated
Not every tool needs the same execution model, and forcing a broad tool surface through one mechanism was the wrong framing. Splits cleanly on one real axis: does the tool need Temporal's durable-execution semantics (heartbeating, cooperative cancellation, retry-via-replay)?

- **Native Temporal activities** — for tools like `shell_exec`: long-running, cancellable, needing real heartbeat-driven cancellation delivery (already built and verified end-to-end earlier in this project). This tier keeps today's hand-maintained registry shape (`TOOL_REGISTRY`/`toolActivityOptions`), and the cross-language duplication problem stays real and unsolved *for this tier specifically* — see Open Questions.
- **mcp-hub-mediated** — for everything else: stateless, short-lived, external-API-shaped calls (search, GitHub, Notion, Grafana, etc.). No heartbeat/cancellation sophistication needed for a quick API round-trip, so a simpler async-RPC model is a genuine fit here, not a compromise. This tier is where "a much broader tool surface... without hand-copying registry entries" (this doc's own motivation) actually gets solved.

### Resolved: Leverage mcp-hub, Not a New Registry Implementation
`/Users/abishekkumar/Documents/infra/mcp-hub` is a real, already-working project — the literal implementation behind the `mcp-hub` MCP server referenced in this environment's own tool-discovery protocol, evaluated directly against its actual code, not assumed from its name. It exposes `search_tools`/`call_tool` (semantic search over a Postgres-backed index of every registered backend's tools, kept fresh by a background poller, dispatch by backend+tool name) and `search_skills`/`get_skill` (the same pattern for curated procedure documents). Backends register via a YAML manifest declaring a transport URL and auth (static header key, or OAuth — `authorization_code` with a manual browser bootstrap, or `client_credentials` for machine-to-machine). Adding a new mcp-hub-tier tool is a manifest, not a code change in either Go or Python — this directly closes the "hand-copying doesn't scale" problem for that tier.

### Resolved: Per-Tenant Deployment — Separate Pod, Subchart Dependency
One mcp-hub instance per tenant, not a shared global instance — real per-tenant isolation matters here (tenant A's own GitHub org and credentials shouldn't be reachable from tenant B), which a single shared instance (today's actual mcp-hub deployment, built for single-operator personal infra) doesn't provide. Deployed as its own pod (a `Deployment`, not a sidecar — reached via mcp-hub's own existing `ClusterIP` `Service`, no new networking mechanism), pulled into `agent-harness-tenant`'s Helm chart as a **subchart dependency** on mcp-hub's existing chart — not a copied/duplicated template, which would just be the same hand-duplication problem this doc exists to avoid, one layer up.

**Three deployable units per tenant**: tenant-worker, mcp-hub, Postgres.

### Resolved: Postgres Isolation — Shared Server, Separate Databases
Postgres stays shared at the infrastructure level (the tenant's existing StatefulSet, not a new one), but mcp-hub's data does **not** share a database with agent-harness's own conversational state. Two databases on the same server: `agent_harness` (sessions/turns/messages/tool_calls/context_summaries, unchanged) and a new `mcp_hub` database (tool/skill embeddings, backend manifests, OAuth tokens), each with its own role/credentials. This isn't a new pattern invented for this — it's mcp-hub's own existing convention (it already expects a distinctly-named `mcphub` database with its own role on a shared Postgres server), just applied to the tenant's own instance instead of a separate central one. `pgvector` (required for `search_tools`' embedding search) only needs enabling on the `mcp_hub` database — no reason to touch `agent_harness`'s extensions.

### Resolved: Per-Tenant OAuth Bootstrap Is a New Onboarding Step
A real, disclosed consequence of per-tenant isolation, not something to gloss over: connecting a tenant's own GitHub/Notion/etc. backends requires mcp-hub's manual browser-based OAuth bootstrap, per tenant. Presumably happens alongside provisioning `deploy/helm/tenants/<tenant>.yaml` — a new operational step tenant onboarding doesn't have today.

**Security note, carried forward from evaluating the real mcp-hub repo, not to be repeated here**: mcp-hub's own chart currently commits live plaintext credentials (a GitHub PAT among them) directly in a git-tracked `values.yaml`, pushed to a real remote — the same class of mistake this project already found and fixed once for its own LLM key (`deploy/helm/tenants/README.md`'s convention: real secrets go in a gitignored per-tenant override, never in a chart's tracked defaults). Per-tenant mcp-hub manifests/credentials in this design must follow that same convention from the start. The original mcp-hub repo's exposure is a separate, unresolved issue outside this project — not fixed as part of this doc.

### Resolved: mcp-hub-Mediated Integration Mechanism — Expose `search_tools`/`call_tool` Directly
Verified against the real mcp-hub server code (`/Users/abishekkumar/Documents/infra/mcp-hub/src/mcp_hub/server.py`), not assumed: it's a `FastMCP` server (the same official `mcp` Python SDK already used for the agent-brain integration), serving **streamable-HTTP only** (`server.run_streamable_http_async()` — no SSE), with **no incoming authentication of its own** — isolation comes entirely from per-tenant pod/network boundaries (`components/multi-tenancy.md`), not a credential check on the endpoint. Its real tool surface is a two-step discover-then-invoke protocol:
```
search_tools(query, top_k=5) -> [{server, tool, description, input_schema}]
call_tool(server, tool, arguments) -> CallToolResult
```
(`search_skills`/`get_skill` exist on the same server but are explicitly out of scope for this pass.)

Same integration shape as agent-brain, same reasoning: expose the real MCP tools directly to the model as two new native tools named `search_tools`/`call_tool` (matching mcp-hub's own names, not a paraphrased wrapper), via a new thin client module (`mcp_hub.py`, no auth headers needed — simpler than `agent_brain.py` for exactly that reason) calling mcp-hub's real endpoint (`MCP_HUB_URL`, already wired into the tenant-worker pod). `call_tool`'s handler is a straight proxy; `search_tools`' handler additionally fans out to shell-hub below and returns the union.

The two-step nature (search reveals a target tool's schema; call needs that schema to construct valid `arguments`) is not friction to engineer around — a model can't validly fill in `call_tool`'s `arguments` for a dynamically-discovered tool it hasn't seen the `input_schema` for yet. Collapsing this into one call would mean guessing arguments blind. Real precedent that the two-step shape works fine in practice: this project's own environment already uses mcp-hub via the identical `search_tools`-then-`call_tool` pattern.

### Resolved: Native-Tool Discovery — shell-hub (in-process, zvec)
A real gap, not a hypothetical one: `shell_exec` is invisible to `search_tools` (it's not registered in mcp-hub — and can't be, see below), so a locally-available CLI capability the model doesn't already know about from training data (e.g. a hypothetical `gog` for Gmail access) has no way to be discovered, while an equivalent mcp-hub-registered tool would be. Considered and rejected: routing `shell_exec` itself through mcp-hub (i.e. making it a `call_tool`-invoked, manifest-registered backend) — rejected because `shell_exec`'s cancellation semantics (heartbeat-driven `RequestCancelActivity` delivery, process-group teardown, session-directory lease renewal — all in `activities/activities/tools.py`) require the Turn Workflow to dispatch it *directly* as a native Temporal activity with real `ActivityOptions{HeartbeatTimeout}` set *before* dispatch (`tool_tiers.go`'s `toolTimingFor`). A stateless HTTP proxy call has no way to carry that contract through. Also considered and rejected: making mcp-hub itself Temporal-aware (a worker registering `shell_exec` as an activity) — rejected because mcp-hub is shared, multi-consumer personal infra (its own Postgres role list: cognee, hindsight, finance, health, and this project's own Claude Code session, alongside agent-harness) that shouldn't be coupled to one consumer's specific Temporal cluster/credentials for no gain the harness-side fix below doesn't already provide.

**Resolved mechanism**: `shell_hub.py`, a small, local, in-process registry — a [zvec](https://github.com/alibaba/zvec) collection (real, verified: Apache-2.0, official Python SDK, genuinely in-process — a local file path, no server, no network port, so "scoped to the container" is a real property, not just a description) built at tenant-worker startup. **Catalog is auto-populated, not hand-seeded**: a real `$PATH` scan (`_discover_path_commands`) against the tenant-worker's actual running image, filtered against a small hand-picked exclude list of obvious coreutils/shell builtins, with a one-line description pulled from each discovered command's own `--help` output (a safe, side-effect-free convention nearly every real CLI supports; each call is time-bounded and run concurrently, and the whole scan is capped at `_MAX_DISCOVERED_COMMANDS=1000`). Verified directly in the real tenant-worker container (`docker build` + `docker run --entrypoint python3`, not assumed): a hand-picked exclude list can't keep pace with a real image's noise (base-image system tools, transitive-dependency console scripts) — tried a ~360-entry hardcoded snapshot of `python:3.12-slim`'s own baseline `$PATH` first, discarded it, since noise still got through regardless (this project's own pip dependencies dump entry points like `numpy-config`/`jsonschema` on `$PATH` too) and an image-tag-coupled hardcoded list is a maintenance burden the search step doesn't need — the semantic+FTS ranking at query time already keeps an irrelevant catalog entry from surfacing, so a little residual discovery noise costs nothing downstream. Also found and fixed by that same real-container testing: zvec rejects doc ids containing certain characters (a real `$PATH` scan can turn up names with anything in them — hit this from a unicode-obfuscated binary name), fixed by using a hash of the command name as the doc id instead of the raw name. Uses zvec's **hybrid search** (vector + full-text, fused via `RrfReRanker`, `rank_constant=60` matching agent-brain's own RRF `rrfK=60` for consistency) rather than FTS alone — verified necessary, not assumed: the queries `search_tools` receives are vague natural-language task descriptions ("check my inbox"), not literal tool names, and mcp-hub's own real `search_tools` implementation already does exactly this (embeds the query, searches by vector) for the identical reason. Embeddings reuse `mcp-hub`'s own LiteLLM config (`mcp-hub.embedding.baseUrl`/`model`/`dimensions`/`apiKey` in `values.yaml`) rather than standing up a third embedding credential — those values are now also wired into the tenant-worker pod's own env (`EMBEDDING_*`), and `zvec.OpenAIDenseEmbedding` speaks that same OpenAI-compatible shape directly.

`search_tools`' handler queries mcp-hub for real (unchanged) and shell-hub locally, returning one combined list — genuinely central discovery from the model's perspective, one tool call. Invocation stays split exactly where it already was: an mcp-hub-sourced result is invoked via `call_tool`; a shell-hub-sourced result is invoked via `shell_exec` directly (shell-hub entries describe a capability, they don't add a new invocation path) — so `tool_tiers.go`'s clean `toolName → timing` lookup for the Go-side workflow dispatch never has to change or inspect nested arguments to figure out what's really being called.

**Considered and reverted**: an explicit `DEFAULT_SYSTEM_PROMPT` rule telling the model to check `search_tools` before reaching for a shell command on external-service tasks. Reverted — it's solving a problem the mechanism doesn't have. Nothing structurally requires a search before invocation: `shell_exec` and `call_tool` are both directly callable, unconditionally. `shell_exec`'s schema is always visible, so the model can call it directly whenever it already knows what it wants, no search needed. `call_tool` practically needs `search_tools` first almost every time *not* because of a prompt rule but because its `server`/`tool`/`arguments` are opaque, per-deployment identifiers the model has no way to know without having seen a `search_tools` result — a structural fact, not an instruction. The direct-invocation-when-known / discover-then-combine-when-ambiguous split falls out of what information the model actually has at each point, not from prompt engineering layered on top of it. Each tool's own description (already reasonably specific) is enough for a capable model to reason correctly without an extra imperative rule.

### Open Questions / To Design
- **Cross-language duplication — narrowed to the native tier only. Explicitly deferred, future item — not urgent at current scope (one tool).** mcp-hub-mediated tools no longer need this solved (a manifest, not per-language config). For `shell_exec`-class tools specifically: `tool_tiers.go`'s `HeartbeatTimeout`/`StartToCloseTimeout` are Temporal `ActivityOptions`, not activity input — the workflow must resolve them to concrete Go values *before* calling `ExecuteActivity` (declaring them *is* invocation), and can't ask the Python registry at runtime either (workflow code can't do arbitrary I/O, Temporal's determinism rule). So passing config to the activity at invocation time doesn't close this — by the time something could be "passed as input," the workflow has already had to commit to a value some other way. Real fix, if/when this stops being one tool's worth of duplication: codegen `tool_tiers.go` from the Python `TOOL_REGISTRY` at build time, or have both sides load from one shared, language-neutral config file — either way the Go side still ends up with a resolved static value, just not hand-typed independently of Python's.
- **Extensibility — resolved for the mcp-hub tier (a manifest), still open for the native tier.** Adding a new native, durable tool is still necessarily a code change in both languages; no way around that given Temporal's own constraints.
- Whether permission gating (`future-work.md` §4) gets designed as part of this doc or stays a separate follow-on — likely matters more for the mcp-hub tier now (e.g. a GitHub tool with write access) than originally scoped.
- Tool versioning/schema evolution: what happens to an in-flight turn's replay if a tool's schema changes mid-flight — a workflow-determinism concern, similar in shape to the `GetVersion`/patching convention already resolved in `components/temporal-workflow.md`. Arguably sharper for the mcp-hub tier now, since manifests can change independently of any agent-harness deploy (the poller picks up changes on its own interval).
- Helm subchart version-pinning: how `agent-harness-tenant` tracks/upgrades its mcp-hub subchart dependency over time — not yet decided.
