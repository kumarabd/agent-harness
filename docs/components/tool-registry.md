# Component: Tool Registry

> STATUS: IN PROGRESS — two-tier architecture, mcp-hub adoption, per-tenant deployment shape, and Postgres isolation resolved. Cross-language duplication (native tier only), permission gating, and tool versioning remain open.

### Role (one line)
The single source of truth for which tools an agent can invoke, their schemas, execution tiers, and (eventually) permission policy — replacing today's tool dispatch table and timing config, hand-duplicated across two languages, with something that actually scales past a handful of tools.

### Why this exists (recap)
Two hand-maintained copies of the same information exist today, and the code says so outright:
- `activities/activities/tools.py`'s `TOOL_REGISTRY` is a plain Python dict mapping tool name → handler + heartbeat/timeout tuning.
- `workflows/internal/workflow/tool_tiers.go`'s `toolActivityOptions` is a plain Go map with the same per-tool timing, and its own comment admits it: *"mirrors activities/activities/tools.py's TOOL_REGISTRY by hand... the workflow can't ask the Python activity layer for this at runtime, since it has to be set on ActivityOptions before the activity is dispatched."*

Only one tool (`shell_exec`) is real today; `search`, `slow_tool`, `noop_tool` are fixture-only demo stubs sharing one generic timing profile. A harness capable of genuinely complex tasks needs a much broader tool surface — read/edit/search-equivalent tools, not just raw shell — and hand-copying registry entries across two languages doesn't scale to that.

### Responsibilities (from architecture)
- Single source of truth for: tool name, JSON schema (name + arguments shape), execution tier (the Tier A/B/C heartbeat/timeout tuning from `components/activities-outbound-delivery.md`), and which handler implements it.
- Solve the cross-language duplication: the Go workflow needs per-tool `ActivityOptions` (heartbeat/timeout) *before* dispatch, and the Python worker needs the actual handler — both currently hand-copied from one conceptual registry that doesn't exist as a real, single artifact.
- Natural home for the permission/destructive-command gating already parked as its own open item (`future-work.md` §4, "Permission Gating for Destructive Tool Calls") — allow/deny policy per tool, possibly per-tenant.
- Per-tenant tool scoping: does every tenant get every tool, or is the tool surface itself tenant-configurable — ties into `components/multi-tenancy.md`.
- **Inherited from `components/memory-slot.md`'s resolved design** (revised 2026-08-22 — that doc dropped its generic backend-interface framing and is now opinionated to agent-brain directly): host two concrete new tools, `search` and `expand`, both calling agent-brain's `memory_search`/`memory_expand` directly. **Both unrestricted** — not the subagent-only split originally modeled on LCM's `lcm_expand`; agent-brain's `memory_expand` has no depth to escalate through, so the unbounded-re-expansion risk that guardrail existed for doesn't apply here. Not yet designed in this doc — `memory-slot.md`'s own "Resolved: Search/Expand Tools" section has the reasoning; this doc still owns the actual tool-registry entries once it's designed.

### Resolved: Two-Tier Architecture — Native Activities vs. mcp-hub-Mediated
Not every tool needs the same execution model, and forcing a broad tool surface through one mechanism was the wrong framing. Splits cleanly on one real axis: does the tool need Temporal's durable-execution semantics (heartbeating, cooperative cancellation, retry-via-replay)?

- **Native Temporal activities** — for tools like `shell_exec`: long-running, cancellable, needing real heartbeat-driven cancellation delivery (already built and verified end-to-end earlier in this project). This tier keeps today's hand-maintained registry shape (`TOOL_REGISTRY`/`toolActivityOptions`), and the cross-language duplication problem stays real and unsolved *for this tier specifically* — see Open Questions.
- **mcp-hub-mediated** — for everything else: stateless, short-lived, external-API-shaped calls (search, GitHub, Notion, Grafana, etc.). No heartbeat/cancellation sophistication needed for a quick API round-trip, so a simpler async-RPC model is a genuine fit here, not a compromise. This tier is where "a much broader tool surface... without hand-copying registry entries" (this doc's own motivation) actually gets solved.

### Resolved: Leverage mcp-hub, Not a New Registry Implementation
`/Users/abishekkumar/Documents/infra/mcp-hub` is a real, already-working project — the literal implementation behind the `mcp-hub` MCP server referenced in this environment's own tool-discovery protocol, evaluated directly against its actual code, not assumed from its name. It exposes `search_tools`/`call_tool` (semantic search over a Postgres-backed index of every registered backend's tools, kept fresh by a background poller, dispatch by backend+tool name) and `search_skills`/`get_skill` (the same pattern for curated procedure documents). Backends register via a YAML manifest declaring a transport URL and auth (static header key, or OAuth — `authorization_code` with a manual browser bootstrap, or `client_credentials` for machine-to-machine). Adding a new mcp-hub-tier tool is a manifest, not a code change in either Go or Python — this directly closes the "hand-copying doesn't scale" problem for that tier.

### Resolved: Per-Tenant Deployment — Separate Pod, Subchart Dependency
One mcp-hub instance per tenant, not a shared global instance — real per-tenant isolation matters here (tenant A's own GitHub org and credentials shouldn't be reachable from tenant B), which a single shared instance (today's actual mcp-hub deployment, built for single-operator personal infra) doesn't provide. Deployed as its own pod (a `Deployment`, not a sidecar — reached via mcp-hub's own existing `ClusterIP` `Service`, no new networking mechanism), pulled into `agent-harness-tenant`'s Helm chart as a **subchart dependency** on mcp-hub's existing chart — not a copied/duplicated template, which would just be the same hand-duplication problem this doc exists to avoid, one layer up.

**Three deployable units per tenant**: tenant-worker, mcp-hub, Postgres.

### Resolved: Postgres Isolation — Shared Server, Separate Databases
Postgres stays shared at the infrastructure level (the tenant's existing StatefulSet, not a new one), but mcp-hub's data does **not** share a database with agent-harness's own conversational state. Two databases on the same server: `agent_harness` (sessions/turns/messages/tool_calls/context_summaries, unchanged) and a new `mcp_hub` database (tool/skill embeddings, backend manifests, OAuth tokens), each with its own role/credentials. This isn't a new pattern invented for this — it's mcp-hub's own existing convention (it already expects a distinctly-named `mcphub` database with its own role on a shared Postgres server), just applied to the tenant's own instance instead of a separate central one. `pgvector` (required for `search_tools`' embedding search) only needs enabling on the `mcp_hub` database — no reason to touch `agent_harness`'s extensions.

### Resolved: Per-Tenant OAuth Bootstrap Is a New Onboarding Step
A real, disclosed consequence of per-tenant isolation, not something to gloss over: connecting a tenant's own GitHub/Notion/etc. backends requires mcp-hub's manual browser-based OAuth bootstrap, per tenant. Presumably happens alongside provisioning `deploy/helm/tenants/<tenant>.yaml` — a new operational step tenant onboarding doesn't have today.

**Security note, carried forward from evaluating the real mcp-hub repo, not to be repeated here**: mcp-hub's own chart currently commits live plaintext credentials (a GitHub PAT among them) directly in a git-tracked `values.yaml`, pushed to a real remote — the same class of mistake this project already found and fixed once for its own LLM key (`deploy/helm/tenants/README.md`'s convention: real secrets go in a gitignored per-tenant override, never in a chart's tracked defaults). Per-tenant mcp-hub manifests/credentials in this design must follow that same convention from the start. The original mcp-hub repo's exposure is a separate, unresolved issue outside this project — not fixed as part of this doc.

### Open Questions / To Design
- **Cross-language duplication — narrowed to the native tier only.** mcp-hub-mediated tools no longer need this solved (a manifest, not per-language config). For `shell_exec`-class tools specifically: how does the Go workflow get tiering info without breaking the determinism boundary — still a hardcoded Go map today, still unresolved.
- **Extensibility — resolved for the mcp-hub tier (a manifest), still open for the native tier.** Adding a new native, durable tool is still necessarily a code change in both languages; no way around that given Temporal's own constraints.
- Whether permission gating (`future-work.md` §4) gets designed as part of this doc or stays a separate follow-on — likely matters more for the mcp-hub tier now (e.g. a GitHub tool with write access) than originally scoped.
- Tool versioning/schema evolution: what happens to an in-flight turn's replay if a tool's schema changes mid-flight — a workflow-determinism concern, similar in shape to the `GetVersion`/patching convention already resolved in `components/temporal-workflow.md`. Arguably sharper for the mcp-hub tier now, since manifests can change independently of any agent-harness deploy (the poller picks up changes on its own interval).
- Helm subchart version-pinning: how `agent-harness-tenant` tracks/upgrades its mcp-hub subchart dependency over time — not yet decided.
