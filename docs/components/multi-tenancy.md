# Component: Multi-Tenancy
## (Namespace-per-Tenant Isolation)

> STATUS: IN PROGRESS — core isolation strategy resolved; a few narrower items still open.

### Role (one line)
Defines the isolation boundary between tenants (users/orgs) across every layer of the system — data-at-rest (Postgres), compute (Temporal), and filesystem (session working directories) — so that this design is actually multi-tenant-capable, not just theoretically extensible to it.

### Why this exists (recap)
Originally, multi-tenancy was scoped out entirely — `01-architecture-overall-topology.md`'s stated goal is a "multi-organization system," but the design was deliberately narrowed to single-user first (see that doc's history). It was reopened once it became clear the actual motivation for this whole architecture (distributed execution, Postgres over SQLite, Temporal durability) is eventual multi-user scale with governance/security — a single-user deployment alone wouldn't justify this architecture over just running Hermes as-is. So this is now designed as a first-class part of the system, not a deferred afterthought.

### Responsibilities (from architecture)
- Define the tenant isolation boundary at every layer: gateway, Postgres, Temporal compute, session filesystem.
- Ensure no process, database, or worker ever holds more than one tenant's credentials or raw content — dedicated deployment topology where that's the only way to guarantee it (tenant workers, Postgres, PV); a reference-passing contract where a shared process is safe by construction instead (loop-worker) — see below.
- Provide natural enforcement points for per-tenant rate limiting/quotas.

### Resolved: Data-at-Rest Isolation
- **Gateway-per-tenant is already free** — `01-architecture-overall-topology.md` §5's "one gateway per source" already covers this; a user/org is just a specific kind of source, no redesign needed.
- **One self-hosted Postgres *instance* per tenant, PV-backed — not a managed Postgres service per tenant, and not row-level security on a shared table.** (Revised 2026-08-14 — see "Superseded" below; originally specified only "a separate database," this is now a stronger and more specific claim.) Chosen to avoid a unified/shared Postgres layer across tenants entirely — no external managed-database dependency to provision per tenant, and structurally the same isolation strength as before (a separate database/instance cannot leak across tenants, unlike RLS which is one missing `WHERE` clause away from a leak). **Revised again, 2026-08-23 — no longer shares the tenant's session-filesystem PV.** Postgres now deploys via the vendored Bitnami `postgresql` subchart (`deploy/helm/agent-harness-tenant`'s `postgresql.*` values), which provisions its own dedicated PVC (`postgresql.primary.persistence`) — see `components/session-filesystem.md`'s corresponding correction for why. One Postgres *process* per tenant, own exclusive data directory, is still the isolation property that matters here; it just no longer depends on volume-sharing with the session tree to get it. Deployed as part of the `deploy/helm/agent-harness-tenant` chart, one release per tenant — split out from the shared loop-worker pool's own chart, `deploy/helm/agent-harness-shared` (one release for the whole cluster); see the 2026-08-14 chart-split note below.
- **Real costs accepted, stated explicitly:** self-hosting Postgres per tenant means owning its operations (backups, upgrades, failover) rather than delegating to a managed service — a genuine ongoing responsibility, not a one-time setup cost. It also becomes a **new per-tenant single point of failure**: every content-touching activity now depends on that tenant's Postgres being reachable (see the reference-passing contract below), not just the persist step — if it's down, more fails than before. The shared-PV-disk-IO cost named when this was first revised no longer applies now that Postgres has its own dedicated PVC — a new, smaller cost in its place: two PVCs to provision/size per tenant instead of one.
- The schema itself (`components/state-layer.md`) is unaffected by this change — it was always a deployment-topology decision, not a schema change.

### Superseded: "Separate Postgres Database" and "Dedicated Worker Fleet" (both narrower than the current decision)
Two earlier decisions in this doc have been revised, not merely extended — recorded here so the reasoning trail stays intact:
1. "Separate Postgres database per tenant" (2026-08-07) implied a database on a shared/managed Postgres service, tenant-isolated only at the database level. Revised to a fully separate, self-hosted Postgres *instance* per tenant (above) — chosen specifically to avoid any unified Postgres layer across tenants, not just a unified *database*.
2. "Dedicated worker fleet, both workflow and activity workers, per tenant" (2026-08-07) is revised below — workflow workers are no longer dedicated per tenant.

### Resolved: Compute Isolation — Namespace-per-Tenant, Dedicated *Tenant* Workers, Shared Loop-Worker Pool
**Revised 2026-08-14.** The original decision dedicated *both* the loop worker and tenant workers per tenant, reasoning that loop-layer blast radius (a crash/bug affecting every tenant scheduled on a shared process) was worth closing alongside credential isolation. Reopened and reconsidered: the Turn Workflow / Session Coordinator code is genuinely tenant-agnostic — it contains no tenant-specific branching — and once activity inputs/outputs carry only references rather than raw content (see "Resolved: Reference-Passing" below, `components/temporal-workflow.md`), a shared loop-worker process never has tenant content in its memory to leak in the first place. That removes the strongest argument for dedicating it.

- **Tenant workers remain dedicated per tenant, unchanged.** This is where tenant credentials, the tenant's Postgres connection, and (per the reference-passing contract) actual content I/O all live — `ModelCall`, `ToolCall`, and the message/turn bookkeeping activities, all in one fleet, one task queue (`components/temporal-workflow.md`'s "Considered and Deferred: Task Queue Separation" covers why this isn't split further by activity type). Nothing about tenant-worker isolation changes.
- **The loop-worker (Session Coordinator, Turn Workflow, subagent-turn workflows) runs as a shared pool**, not one fleet per tenant. The code is identical across tenants and never holds tenant content in memory under the reference-passing contract, so the isolation a dedicated loop-worker was buying is no longer load-bearing.
- **Temporal namespace-per-tenant is preserved** — this decision is about *worker* dedication, not namespace isolation. Namespace-per-tenant still gives workflow-ID uniqueness, per-tenant visibility, and per-tenant retention, independent of which workers execute the workflow code. (Reconsidered separately on 2026-08-15 — collapsing to a single shared namespace with per-tenant queues instead was floated and rejected: it costs zero pods either way, since the loop-worker pool is already shared regardless of namespace count, so there was never a pod-count reason to trade away the access-control isolation namespaces provide.)
- **Accepted trade, stated explicitly, not minimized to "just noisy neighbor":**
  - **Resource contention (noisy neighbor)** — one tenant's turn volume can compete for CPU/memory with another's on the shared pool. Mitigable at the gateway (rate limits, per-tenant quotas) — this part genuinely is a throughput problem a limit can bound.
  - **Availability blast radius** — a crash, panic, or resource exhaustion in the shared loop-worker process can affect in-flight turns for every tenant currently scheduled on it, not just the tenant that caused it. This is *not* fully addressed by rate limiting (a slow memory leak from one tenant's legitimately large turn still eventually starves others; a crash is a crash regardless of preceding traffic volume). Accepted as a real, named cost, not eliminated.
  - **Tool-invocation-pattern visibility across tenants sharing the process is not new risk introduced by this decision** — that visibility exists by design regardless of worker-sharing, see below.
- **Mechanics — resolved 2026-08-14, static config.** A Temporal `Client` is bound to a single namespace, and a `Worker` is bound to a single `Client` — there is no native "one worker polls many namespaces" primitive. "Shared pool" means each loop-worker process runs one `Client`+`Worker` pair **per tenant namespace it serves**, concurrently, in the same process. Which namespaces a given process serves is **static configuration** at deploy time (`TEMPORAL_NAMESPACES`, comma-separated) — the same pattern already chosen for gateway shard assignment (`components/gateway.md`), for the same reason: tenant onboarding is a slow, deliberate event (new namespace + tenant worker fleet + Postgres + PV all need to be stood up together regardless), not something that needs live dynamic registration. The task queue name (`agent-loop`) and Temporal address stay shared across every tenant a process serves — only the namespace varies per pair, since task queues are already namespace-scoped and can't collide across tenants. Dynamic registration (a loop-worker process picking up a newly-onboarded tenant without a redeploy) is not designed and not needed at this stage — revisit only if tenant onboarding frequency ever makes static config genuinely operationally painful.

### Resolved: Reference-Passing — What the Shared Loop Worker Is and Isn't Allowed to See
The mechanism that makes sharing the loop-worker pool safe, not just a policy choice. Full design lives in `components/temporal-workflow.md` and `components/state-layer.md`; summarized here as the multi-tenancy-relevant contract:
- **Activity inputs and outputs are references, not content.** `ModelCall`, `ToolCall`, and related activities read/write actual message content, tool arguments, and tool results directly against that tenant's own Postgres/PV. The workflow passes and receives only IDs (`turn_id`, `message_id`, `args_ref`) — raw tenant content never crosses into the shared loop-worker process's memory on the success path, which is the dominant path (not just the failure/panic path).
- **Tool *name*, and aggregate invocation metadata (which tools, how many times, in what sequence, per turn) is workflow-visible by design, not an accepted leak.** The workflow structurally needs the tool name to decide how to dispatch a call (plain activity vs. subagent child workflow, which heartbeat tier applies). Treated as an intentional, low-sensitivity signal — the same category of thing already extracted deliberately in `components/dreaming.md` — not something to suppress. What's explicitly **not** exposed at this layer: tool *arguments* and tool *results*, which stay reference-only same as message content.
- **Panic suppression is defense-in-depth, not load-bearing.** Because content isn't in the workflow's memory on the success path, a panic inside an activity has much less to leak even unhandled. The one residual seam: activity *inputs* must also be reference-only (not just outputs) for this to fully hold — a serialization failure on a content-bearing input could still surface it in a Temporal-generated failure. Activities should still catch and sanitize their own panics as good practice, but this is not the primary isolation mechanism anymore.
- **Large payloads (big tool outputs, file diffs) route through the PV via the same claim-check pattern**, not through Postgres — see `components/session-filesystem.md`.

### Key Design Decisions (recap)
- Isolation is enforced by **deployment topology** (per-tenant namespace, self-hosted Postgres instance, PV, dedicated tenant workers) rather than by application-level scoping (tenant_id columns, RLS, in-process checks) — chosen consistently for the same reason: structurally safer than a check that can be missed or misconfigured.
- **Loop-worker pool is shared across tenants**; tenant workers, Postgres, and the PV remain dedicated per tenant. Made safe by a reference-passing content contract, not by trusting the shared process to behave.
- Explicitly rejected: task-queue-only isolation (an earlier, narrower version of today's decision — rejected the first time for leaving loop-layer blast radius shared *without* the reference-passing contract that makes today's version safe), row-level security / shared-table tenant scoping in Postgres, managed/shared Postgres service per tenant, and cluster-per-tenant.

### Open Questions / To Design
- **Session key / workflow ID tenant-scoping** — likely already resolved implicitly by namespace-per-tenant (workflow IDs are only unique *within* a namespace, so cross-tenant collision is structurally impossible once each tenant has its own namespace), but worth confirming explicitly rather than assuming.
- **Dynamic per-tenant worker fleet provisioning** — for tenant workers (still dedicated) this remains as originally scoped: new tenant onboarding needs its namespace, tenant worker fleet, Postgres instance, and PV stood up before the tenant can run anything.
