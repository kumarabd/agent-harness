### Superseded: mcp-hub Document-Store Design
**2026-08-29.** Everything below this section (Role, Why this exists, Responsibilities, and every "Resolved"/"Considered and Rejected" section) describes the design that was built and then reverted the same day — kept verbatim as a real historical record, not describing current architecture.

**Why it was reconsidered**: prompted directly ("I see a skill to be an abstract concept on the memory") — the mcp-hub-document-store shape treated a skill as a *discovery-and-fetch* problem, structurally identical to `search_tools`/`call_tool` (a separate index, a separate per-tenant document store, a separate pair of tools). Framing a skill as a *memory* concept instead means it's not a new kind of thing at all — but, corrected directly the same day after a first pass at this note wrongly proposed it as a fourth peer `type` in `memory-slot.md`'s existing `episode`/`domain-fact`/`persona-rule` model: **a skill isn't a new stored category sitting next to those three, it's something that emerges from combining them** ("existing concepts form together to become a skill+something"). Not yet designed what "combining" means mechanically — see `memory-slot.md`'s own Open Questions entry for the honest, still-open shape of this.

**What was actually undone, for real, not just documented as reverted:**
- `activities/activities/tools.py` — `search_skills`/`get_skill` handlers and their `TOOL_REGISTRY` entries removed.
- `activities/activities/llm.py` — the two `TOOLS_SCHEMA` entries removed; `DEFAULT_SYSTEM_PROMPT`'s "check search_skills first" sentence removed. The REST of that same day's system-prompt rewrite (dropping the stale "autonomous coding assistant" framing) was kept — that fix was correct and orthogonal to the skills-mechanism question, not part of what got reconsidered.
- `activities/activities/mcp_hub.py` — the JSON-vs-plain-text fallback added specifically for `get_skill`'s plain-text return was reverted too, back to unconditional `json.loads`. Kept-as-defensive-robustness was considered and rejected: with `get_skill` gone, no real caller needs the fallback anymore, and carrying unused mechanism forward past its motivating need is exactly what this project's own discipline argues against elsewhere (`tool-registry.md`'s "Considered and reverted" precedent, `memory-slot.md`'s repeated "don't design ahead of real need").
- `workflows/cmd/gateway/platform_prompts.go` — `voiceSystemPromptText`'s matching nudge sentence removed.

**Not undone**: `docs/tracker/openclaw.md`'s "Skills system" row is updated to reflect this reversal (not left claiming "built"), not reverted to its pre-2026-08-28 "not yet implemented" wording either, since the actual current state (reconsidered toward a different mechanism, not simply undesigned) is a real, distinct status worth recording accurately.

**What's genuinely still open, not resolved by this revert**: what "existing concepts form together to become a skill" actually means mechanically — a retrieval-time composition across several `memory_search` results, a write-time synthesis akin to what agent-brain's own mining/generalization pipeline already does adjacent to (`memory-slot.md`'s own `domain-fact`-default treatment of agent-brain-synthesized content), or something else entirely; whether it needs its own retrieval trigger/nudge the way this doc's own "Prompt-Level Nudge" section worked out for the (now-reverted) mcp-hub shape; and whether `WriteMemory`'s extraction path (or a separate explicit authoring path) is involved at all, given a skill by this framing isn't written down as its own artifact in the first place — it's composed from things already written down. None of that is designed yet — this revert only removes the previous (reconsidered) mechanism; it doesn't replace it with a new one. "For now," per the direction that prompted this — a real future design pass, not assumed to fit neatly into memory-slot's existing three-type shape just because that's the obvious adjacent place to look.

## Historical: mcp-hub Document-Store Design (superseded, describes the undone architecture)

### Role (one line)
Discovery and retrieval of curated **procedural knowledge** — "how to do X in this environment" — sourced from mcp-hub's already-existing `search_skills`/`get_skill` primitives, giving the model a real way to pull in domain-specific procedures on demand rather than either hardcoding them into the system prompt (bloat) or making the model reinvent them each time (unreliable).

### Why this exists (recap)
Two distinct gaps this closes, both real:

1. **The orchestrator vision** (`docs/04-architecture-orchestrator-vision.md`) explicitly relies on procedural guidance: "when the user asks to refactor auth in a repo, first check the skill catalog for a project-specific how-to, then delegate to Claude Code with those instructions embedded." Today the harness has no such catalog. Skills fill that slot exactly.
2. **Compared to Claude Code / OpenClaw** (`docs/tracker/openclaw.md`, "Skills system" row): both have modular capability directories with `SKILL.md`-style metadata. This project's tracker already flagged that as a gap; this component closed it by leveraging mcp-hub rather than inventing a new one.

The primitives already exist in the tenant's own mcp-hub deployment (see `components/tool-registry.md`, "Resolved: Leverage mcp-hub" — real, verified against mcp-hub's actual server code). The gap was entirely on the harness's side: the two tools weren't wired into `tools.py`, weren't in `TOOLS_SCHEMA`, and the model had no prompt-level nudge toward them.

### Responsibilities (from architecture)
- Expose `search_skills` and `get_skill` as **two native tools**, straight passthrough to mcp-hub (`activities/activities/mcp_hub.py`) — same shape as the already-shipped `search_tools`/`call_tool`.
- Contribute prompt guidance so the model knows *when* to look for a skill — the parallel to how `call_tool` practically requires a preceding `search_tools` because the model doesn't know backend names, skills practically require a preceding `search_skills` because the model doesn't know what's cataloged.
- Stay out of the mcp-hub server itself. mcp-hub already indexes/searches/serves skills; this component was only the harness-side surface.
- Deliberately **not** an execution mechanism. A skill is guidance text — a document telling the model "to do X in this repo, run these commands / call this tool / apply these constraints." The model reads the skill and then decides what to invoke (`shell_exec`, `delegate_claude_code`, `call_tool`, subagent, ...). This was a discovery layer, not a new dispatch shape. See "Considered and Rejected" below.

### Key Design Decisions (recap, mirrors tool-registry.md's mcp-hub tier)
- **Same pattern as `search_tools`/`call_tool`** — two-step discover-then-fetch protocol, same MCP client (`mcp_hub.py`), same `MCP_HUB_URL` env, same auth story (none — per-tenant pod isolation is the boundary, per `components/multi-tenancy.md`).
- **Same graceful-degradation posture** — if `MCP_HUB_URL` isn't configured, `search_skills` returns empty and `get_skill` returns a clear "not configured" error, exactly the way `search_tools` already degrades. A deployment without mcp-hub still works, just with no skill discovery.
- **Same Postgres isolation** — mcp-hub's own `mcp_hub` database owns the skill index/embeddings; agent-harness's `agent_harness` database doesn't touch it. No schema change on the agent-harness side to enable skills.

### Resolved: Skills Are Guidance Documents, Not Executable Recipes
An alternative was considered and rejected: making `get_skill` return a structured "recipe" (a command template with argument slots the model fills in), so `invoke_skill(skill_id, args)` becomes its own dispatch path. Rejected for the same reason the model registry decided against caller-side extraction: **the model already has `shell_exec`, `delegate_*`, `call_tool`, and subagent spawn as invocation paths.** Adding a fifth ("invoke_skill") that internally routes to one of those is a redundant indirection layer whose only purpose would be preventing the model from choosing wrongly — which prompt engineering and skill-document content solve better than a new tool would.

Concrete consequence: `get_skill`'s return is plain Markdown/text (or whatever mcp-hub returns from its own `get_skill`, verbatim). The model reads it, extracts the procedure, decides what to invoke, and calls the appropriate tool directly. Same "the model already knows how to reason about text" precedent as memory-slot's typed-content retrieval.

### Resolved: Prompt-Level Nudge, Not a Structural Requirement
Same reasoning as `components/tool-registry.md`'s "Considered and reverted" note on `search_tools`: there is nothing structurally requiring a `search_skills` call before any specific action. The model has `shell_exec` and can just run a shell command; there's no invariant to enforce. What there IS a real reason for is a prompt-level guidance rule: **"if the user's request looks like a repeatable procedure (release, deploy, troubleshoot, refactor a known pattern), check `search_skills` first before improvising."** That's a nudge, not a gate — same shape as the (deliberately absent) `search_tools`-first rule.

### Resolved: Per-Tenant Skill Catalog
Skills were per-tenant, because mcp-hub is per-tenant (`components/tool-registry.md`, "Resolved: Per-Tenant Deployment"). Each tenant's skill catalog would have been a set of Markdown documents registered with their own mcp-hub instance via mcp-hub's existing skill-registration protocol — **not designed here**; that was mcp-hub's own domain. What mattered at the harness level was that "skills the model can discover" equals "skills the tenant registered with their own mcp-hub instance," no cross-tenant leakage.

**Note on operational burden**: same real cost as the mcp-hub tool tier — bringing a new tenant online would have meant registering their skill catalog with their own mcp-hub instance, alongside their tool backends. `components/tool-registry.md`'s "Resolved: Per-Tenant OAuth Bootstrap Is a New Onboarding Step" comment applies verbatim; skills would have added to that step, not created a second one.

### Considered and Rejected: A Separate Skill-Registry Table on Agent-Harness's Side
Considered: a new `skills` table in the `agent_harness` database, populated by the harness independently, letting the harness's own admins add skills without going through mcp-hub. Rejected — it duplicates exactly the discovery/index/embedding machinery that motivated `tool-registry.md`'s "Leverage mcp-hub, Not a New Registry Implementation" resolution. Two skill sources, two authoring flows, two indexes to keep coherent — for zero win over just registering the skill in mcp-hub. (Ironic in hindsight: the memory-layer redirect that superseded this whole document is, in effect, a different flavor of "harness-native handling" this section anticipated as a possible future need — just landing on agent-brain/memory-slot rather than a new `agent_harness`-side table.)

### Historical: Implementation (built 2026-08-29, reverted the same day)
Built end to end, closing this doc's own "To Design" checklist item by item — `mcp_hub.py`'s client extended to tolerate a plain-text (non-JSON) tool result, `TOOL_REGISTRY`/`TOOLS_SCHEMA` entries added for `search_skills`/`get_skill`, `DEFAULT_SYSTEM_PROMPT` and `voiceSystemPromptText` both given the prompt-level nudge. A real bug was caught before it shipped, worth preserving as a lesson even though the code is gone: mcp-hub's real `get_skill` (verified directly against `server.py`) returns a plain string — the skill's verbatim Markdown content — not a JSON-serialized object the way every other mcp-hub tool's result was. The shared client's `json.loads(...)` call had been unconditional, since every prior caller only ever got structured (dict/list) results back; calling it against real skill content would have thrown `json.JSONDecodeError` on the very first real fetch. Fixed generically at the time (try JSON, fall back to raw string) — reverted along with everything else once the mechanism itself was reconsidered, per the "kept-as-defensive-robustness... rejected" note above.

Verified via a throwaway script (deleted after passing) that faked only the MCP transport boundary so the real parsing logic ran unmocked — all 8 checks passed, including the plain-text fallback and confirming `search_tools`' own existing JSON path was untouched. `go build`/`go vet`/`gofmt` and `py_compile` clean at the time. None of this is live anywhere now — the revert removed it from the running code the same day it was verified.
