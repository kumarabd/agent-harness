# Component: Skills

> STATUS: SCAFFOLD — designed here for the first time, not yet implemented. Structurally identical to the already-resolved `search_tools`/`call_tool` mcp-hub-mediated tier in `components/tool-registry.md`, so the plumbing shape is fully known; what's new is exposing `search_skills` and `get_skill` as two additional native tools and updating the system prompt / tool guidance so the model knows to reach for a skill before improvising a procedure. Introduced 2026-08-28 alongside `docs/04-architecture-orchestrator-vision.md` and `components/delegated-agents.md`.

### Role (one line)
Discovery and retrieval of curated **procedural knowledge** — "how to do X in this environment" — sourced from mcp-hub's already-existing `search_skills`/`get_skill` primitives, giving the model a real way to pull in domain-specific procedures on demand rather than either hardcoding them into the system prompt (bloat) or making the model reinvent them each time (unreliable).

### Why this exists (recap)
Two distinct gaps this closes, both real:

1. **The orchestrator vision** (`docs/04-architecture-orchestrator-vision.md`) explicitly relies on procedural guidance: "when the user asks to refactor auth in a repo, first check the skill catalog for a project-specific how-to, then delegate to Claude Code with those instructions embedded." Today the harness has no such catalog. Skills fill that slot exactly.
2. **Compared to Claude Code / OpenClaw** (`docs/tracker/openclaw.md`, "Skills system" row — marked ⏳): both have modular capability directories with `SKILL.md`-style metadata. This project's tracker already flagged that as a gap; this component closes it by leveraging mcp-hub rather than inventing a new one.

The primitives already exist in the tenant's own mcp-hub deployment (see `components/tool-registry.md`, "Resolved: Leverage mcp-hub" — real, verified against mcp-hub's actual server code). The gap is entirely on the harness's side: the two tools aren't wired into `tools.py`, aren't in `TOOLS_SCHEMA`, and the model has no prompt-level nudge toward them.

### Responsibilities (from architecture)
- Expose `search_skills` and `get_skill` as **two native tools**, straight passthrough to mcp-hub (`activities/activities/mcp_hub.py`) — same shape as the already-shipped `search_tools`/`call_tool`.
- Contribute prompt guidance so the model knows *when* to look for a skill — the parallel to how `call_tool` practically requires a preceding `search_tools` because the model doesn't know backend names, skills practically require a preceding `search_skills` because the model doesn't know what's cataloged.
- Stay out of the mcp-hub server itself. mcp-hub already indexes/searches/serves skills; this component is only the harness-side surface.
- Deliberately **not** an execution mechanism. A skill is guidance text — a document telling the model "to do X in this repo, run these commands / call this tool / apply these constraints." The model reads the skill and then decides what to invoke (`shell_exec`, `delegate_claude_code`, `call_tool`, subagent, ...). This is a discovery layer, not a new dispatch shape. See "Considered and Rejected" below.

### Key Design Decisions (recap, mirrors tool-registry.md's mcp-hub tier)
- **Same pattern as `search_tools`/`call_tool`** — two-step discover-then-fetch protocol, same MCP client (`mcp_hub.py`), same `MCP_HUB_URL` env, same auth story (none — per-tenant pod isolation is the boundary, per `components/multi-tenancy.md`).
- **Same graceful-degradation posture** — if `MCP_HUB_URL` isn't configured, `search_skills` returns empty and `get_skill` returns a clear "not configured" error, exactly the way `search_tools` already degrades. A deployment without mcp-hub still works, just with no skill discovery.
- **Same Postgres isolation** — mcp-hub's own `mcp_hub` database owns the skill index/embeddings; agent-harness's `agent_harness` database doesn't touch it. No schema change on the agent-harness side to enable skills.

### Resolved: Skills Are Guidance Documents, Not Executable Recipes
An alternative was considered and rejected: making `get_skill` return a structured "recipe" (a command template with argument slots the model fills in), so `invoke_skill(skill_id, args)` becomes its own dispatch path. Rejected for the same reason the model registry decided against caller-side extraction: **the model already has `shell_exec`, `delegate_*`, `call_tool`, and subagent spawn as invocation paths.** Adding a fifth ("invoke_skill") that internally routes to one of those is a redundant indirection layer whose only purpose would be preventing the model from choosing wrongly — which prompt engineering and skill-document content solve better than a new tool would.

Concrete consequence: `get_skill`'s return is plain Markdown/text (or whatever mcp-hub returns from its own `get_skill`, verbatim). The model reads it, extracts the procedure, decides what to invoke, and calls the appropriate tool directly. Same "the model already knows how to reason about text" precedent as memory-slot's typed-content retrieval.

### Resolved: Prompt-Level Nudge, Not a Structural Requirement
Same reasoning as `components/tool-registry.md`'s "Considered and reverted" note on `search_tools`: there is nothing structurally requiring a `search_skills` call before any specific action. The model has `shell_exec` and can just run a shell command; there's no invariant to enforce. What there IS a real reason for is a prompt-level guidance rule: **"if the user's request looks like a repeatable procedure (release, deploy, troubleshoot, refactor a known pattern), check `search_skills` first before improvising."** That's a nudge, not a gate — same shape as the (deliberately absent) `search_tools`-first rule.

### Resolved: Per-Tenant Skill Catalog
Skills are per-tenant, because mcp-hub is per-tenant (`components/tool-registry.md`, "Resolved: Per-Tenant Deployment"). Each tenant's skill catalog is a set of Markdown documents registered with their own mcp-hub instance via mcp-hub's existing skill-registration protocol — **not designed here**; that's mcp-hub's own domain. What matters at the harness level is that "skills the model can discover" equals "skills the tenant registered with their own mcp-hub instance," no cross-tenant leakage.

**Note on operational burden**: same real cost as the mcp-hub tool tier — bringing a new tenant online means registering their skill catalog with their own mcp-hub instance, alongside their tool backends. `components/tool-registry.md`'s "Resolved: Per-Tenant OAuth Bootstrap Is a New Onboarding Step" comment applies verbatim; skills add to that step, don't create a second one.

### Considered and Rejected: A Separate Skill-Registry Table on Agent-Harness's Side
Considered: a new `skills` table in the `agent_harness` database, populated by the harness independently, letting the harness's own admins add skills without going through mcp-hub. Rejected — it duplicates exactly the discovery/index/embedding machinery that motivated `tool-registry.md`'s "Leverage mcp-hub, Not a New Registry Implementation" resolution. Two skill sources, two authoring flows, two indexes to keep coherent — for zero win over just registering the skill in mcp-hub. If a specific class of skill genuinely needs harness-native handling later (e.g. skills that trigger workflow-level behavior, not just text guidance), that's a real design pass at that time, not a preemptive parallel registry now.

### To Design (once implementation starts, not blocking this doc)
- **`mcp_hub.py`'s Python client already speaks the MCP protocol** — verified for `search_tools`/`call_tool`. `search_skills`/`get_skill` are additional tools on the same server; the client work should be strictly additive (two new methods proxying the corresponding MCP tool calls). No transport/auth/session changes.
- **`TOOL_REGISTRY` in `tools.py`** grows two entries — `search_skills` and `get_skill`, both Tier B by default (network round-trip, no cancellable subprocess) — mirroring the existing `search_tools`/`call_tool` entries exactly. Same `heartbeat_interval_seconds`/`heartbeat_timeout_seconds`/`start_to_close_timeout_seconds` triple.
- **`TOOLS_SCHEMA` in `llm.py`** grows two entries with descriptions that mirror mcp-hub's own real skill tool descriptions verbatim-ish, plus a note on when the model should reach for `search_skills` (procedural / repeatable-task requests).
- **`tool_tiers.go`** — cross-language duplication applies here too, one entry per new tool. Same open cross-language-duplication concern from `tool-registry.md` (Open Questions) — narrow at scope, not blocking, but worth noting.
- **System prompt guidance**: one short sentence pointing at `search_skills` for procedural tasks. Not designed here; belongs to the wider system-prompt restructure `docs/04-architecture-orchestrator-vision.md` calls out as a follow-up. Skill-tool wiring can land before that restructure — the tools will just be under-used until the prompt tells the model when to reach for them.
- **No Helm chart change needed.** The tenant-worker already has `MCP_HUB_URL` configured for `search_tools`/`call_tool`; `search_skills`/`get_skill` reuse the exact same env and endpoint.

### Open Questions / To Design
- **When the model should call `search_skills`.** Prompt-level nudge, not a structural gate. The tension is real: nudge too little and skills get ignored; nudge too much and every "hello, what's the weather" call wastes tokens on a skill lookup. Same "how eagerly should the model search" question `search_tools` also has — for `search_tools` the answer landed on "each tool's own description is enough for a capable model to reason about; no imperative rule needed" (`tool-registry.md`, "Considered and reverted"). Skills might genuinely need something stronger, since a "release the service" task has no visible-tool hint that a skill exists — a model without a nudge might just try to figure it out. Deferred until real usage data shows whether the model reaches for skills often enough on its own.
- **Skill authoring UX per tenant.** Registering a skill means writing Markdown to mcp-hub's own skill store. This project doesn't own that UX; whether tenants get a real skill-authoring flow (a web UI? a git repo synced to mcp-hub? mcp-hub's own CLI?) is mcp-hub's concern, not this harness's. Named as a real cost of the mcp-hub-mediated design, not fixed here.
- **Interaction with `delegate_claude_code`.** A common shape will be "look up a skill, then delegate the actual work to Claude Code with the skill content embedded in the prompt." The model has to compose this itself today — read `get_skill`'s output, construct a `delegate_claude_code` call with that output in the prompt. Whether the delegate tool eventually gains a `skill_id` shortcut argument that automatically fetches + embeds is a real, worth-designing question, but not this pass — build the raw pieces first, watch how they get composed in practice.
