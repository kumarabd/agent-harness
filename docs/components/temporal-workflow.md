# Component: Turn Workflow
## (The Agent Turn — and, Recursively, Each Subagent)

> STATUS: IN PROGRESS — loop mechanics, interrupt/cancellation, and the reference-passing content contract are resolved. A few numeric/operational items remain deliberately deferred (see Open Questions).

### Role (one line)
The durable, bounded workflow that represents one agent turn — hosting the reason–act–observe loop, fanning out parallel tool calls, and recursing into child workflows for subagents. Started as a child workflow of the [Session Coordinator](./session-coordinator.md); one workflow *type* implements every level of the tree, whether it's the top-level turn or a nested subagent invocation. Runs in a **tenant-agnostic, shared loop-worker pool** (`components/multi-tenancy.md`) — deliberately different from the dedicated-per-tenant tenant workers it dispatches to, made safe by holding references to content rather than the content itself.

### Responsibilities (from architecture)
- Run the reason–act–observe loop: model-call activity (reasoning) → tool-call activities/child workflows (act) → observe → loop until stop condition.
- On start, hydrate context **by reference** — the workflow holds `turn_id`/`message_id`s, not raw conversation content; the `ModelCall` activity reads the actual content from that tenant's own Postgres. (Revised 2026-08-14 — see "Resolved: Reference-Passing Contract" below. This is what makes the shared-across-tenants loop-worker pool in `components/multi-tenancy.md` safe.) It does not inherit in-memory state from any prior turn — the coordinator only hands it a session/turn reference, same as before.
- Within one reasoning step, execute all requested tool calls **in parallel** as concurrent activity futures.
- When a tool call is a subagent, start a **child workflow** of the same type instead of a plain activity — recursively, no hard numeric depth cap, but no longer unbounded either: a subagent-issued spawn must show genuine narrowing of responsibility (see "Resolved: Recursion Termination Guard" below) — real, structural termination pressure, not just "arbitrary depth." The subagent is given its own scoped working subdirectory on the shared session mount (`/session/{session_key}/sub/{n}/`, nested for deeper recursion) — see `components/session-filesystem.md`. Any file-touching tool call, including parallel siblings within one reasoning step, coordinates through that component's Postgres-backed leases rather than assuming exclusive access.
- On subagent completion, its file changes are **not** automatically visible to the parent — merge-back into the parent's working directory happens explicitly, driven by the subagent's result/observation (exact trigger mechanics still open — see `components/session-filesystem.md`).
- Catch a failed tool call or subagent and surface it to the model as an observation, rather than hard-failing the turn.
- Handle a forwarded signal (new message arriving mid-turn) by actively cancelling whatever is currently in flight — outstanding tool-call activities (via `WAIT_CANCELLATION_COMPLETED`) and/or a running subagent child workflow (via `RequestCancelChildWorkflowExecution`, which cascades) — then folding the new message into context once cancellation is confirmed. Tools that don't implement cooperative cancellation (Tier A / fire-and-complete, see `components/activities-outbound-delivery.md`), or that are one atomic non-chunkable call, fall back to running to completion before the fold-in happens.
- On a confirmed cancellation, append a `status: "cancelled"` observation (not a bare error) alongside the newly-arrived message in the same context update — see the observation shape in `components/activities-outbound-delivery.md` — so the interrupted action stays visible to the model rather than silently disappearing.
- Trigger persist + deliver activities once the loop produces a final response, then complete (bounded lifetime — it does not wait around for the next turn).

### Key Design Decisions (recap)
- Workflow ID = `{session_key}:turn:{turn_seq}` for the top-level turn; nested subagents extend the path, e.g. `{session_key}:turn:{turn_seq}:sub:{n}` — legible in the Temporal UI since the ID mirrors the tree path.
- **Postgres borrows these IDs directly rather than minting its own** — `turns.turn_id` = the workflow ID; `tool_calls.tool_call_id` = the activity ID (fully qualified as `{turn_id}:act:{n}`), or, for a subagent call, the child workflow's own turn_id directly. This requires every tool-call activity to be started with an **explicitly assigned activity ID** (`{turn_id}:act:{n}`), not the SDK's auto-generated one — a concrete implementation requirement, not just a naming convention. See `components/state-layer.md` for the full schema.
- Tool call → Activity by default; Child Workflow only when the tool is itself a subagent needing its own nested loop, history isolation, and retry boundary.
- `ParentClosePolicy = REQUEST_CANCEL` (not `TERMINATE`) for subagent children — never abruptly kill an in-flight subagent; consistent with never aborting a half-finished tool call.
- No hard numeric depth or fan-out cap on subagent recursion or parallel tool calls — **revised 2026-08-29**: depth now has a real, structural termination guard (declaration-and-rejection, not a numeric ceiling; see "Resolved: Recursion Termination Guard"); fan-out remains genuinely uncapped, deliberately (parallel sibling dispatch isn't nested delegation, so the guard doesn't apply to it — see that section).
- **Interrupt is a real cancellation, not queue-after.** `WAIT_CANCELLATION_COMPLETED` on activities (never `ABANDON` — rejected because it leaves an orphaned activity with an unknown final outcome, worse than the latency it saves), cascading `RequestCancelChildWorkflowExecution` for subagents. Requires every tool activity to implement cooperative cancellation (heartbeat + check-and-teardown) — see `components/activities-outbound-delivery.md`. Interrupt latency is therefore bounded (next heartbeat + cleanup time), not instant. A tool with no cooperative cancellation, or one atomic non-chunkable call, falls back to running to completion before fold-in — the old "loop boundary only" behavior is now the fallback, not the default.
- A turn workflow completing is not "losing state" — the coordinator holds the resumption pointer, and Postgres holds the content a fresh turn rehydrates from. See [[session-coordinator]] for why this workflow doesn't need to wait around between turns.

### Resolved: Determinism Constraints on the Loop
Temporal replays a workflow by re-running its code and feeding back the *already-recorded* results of past activities/signals, rather than re-executing the real world. The constraint this imposes: **the loop's control flow must be a pure function of (workflow input, activity results received so far, signals received so far)**.

- **No direct randomness or wall-clock reads in workflow code** — must go through Temporal's deterministic primitives (`workflow.now()`, `workflow.uuid4()`) if ever needed. In practice this barely bites here: the `{turn_id}:act:{n}` activity-ID scheme already decided is a plain counter, not a random ID, so no random generation is needed inside the loop at all — a quiet benefit of that earlier decision, not a new constraint to design around.
- **All non-deterministic work is an activity, full stop** — model call, every tool call, persist, deliver, and (per compression below) the compression call itself. The loop only ever branches on their *returned*, already-recorded results.
- **Loop length/shape falls out of recorded activity results, not anything computed outside them** — "how many reasoning steps ran" is just what the model activities actually returned (tool calls present → continue; absent → stop). This is a natural consequence of the existing loop shape, not new work, but worth stating explicitly so a future stop-condition addition doesn't accidentally reference unrecorded state.
- **Signal handling must only append to workflow-local state**, never branch non-deterministically on arrival timing — this is exactly what makes the FIFO queue in the signal-coalescing design below safe under replay: appends are deterministic regardless of real-world timing, since Temporal delivers signals in a consistent recorded order.
- **Workflow code changes affecting in-flight turns need `GetVersion`/patching, not just a deploy.** Turn workflows are short-lived so the blast radius is naturally small, but subagents can nest arbitrarily deep and a slow one could still be running when new workflow code deploys. Flagged as a real requirement; not fully resolved — needs its own pass later.

### Resolved: Stop-Condition Logic
Evaluated inline at the top of each loop iteration — a pure check against already-recorded state, no activity needed for the check itself (only for compression, if the check trips it — see below). The loop stops when **any** of the following is true:
- **No tool calls in the model's latest response** — the natural/expected stop.
- **`max_iterations` reached** — caps reasoning-step count, guards against a runaway loop.
- **`max_retries` reached** — a **turn-level** cumulative cap, distinct from the per-activity `MaximumAttempts` ceiling already resolved in `components/activities-outbound-delivery.md`. That earlier cap bounds retries of *one* activity call; this one bounds cumulative retry/failure churn across the whole turn. Kept as a visibly separate knob so the two aren't conflated.
- **Token/cost budget exhausted** — cumulative usage tracked from model-activity results (which already return usage figures), checked against a configured budget each iteration.

Any of these firing ends the loop the same way: the turn completes with whatever partial result it has, not a hard failure — consistent with how cancellation and tool failures are already surfaced as observations elsewhere in this design, rather than as crashes.

### Resolved: Signal Coalescing
Sequential, not batched. A **FIFO queue lives in workflow-local state**, appended to by the signal handler (a deterministic, pure append — see determinism constraints above). At each loop boundary: cancel whatever's currently in flight (existing interrupt mechanism), dequeue exactly **one** message, fold it into context, run the next reasoning step. If the queue is still non-empty afterward, the same cancel → dequeue-one → fold cycle repeats at the next boundary. A burst of rapid messages therefore produces several distinct reasoning passes, one per message, rather than a single merged context update — preserving the model's ability to react to each message individually instead of averaging them into one blob.

### Resolved: Compression / Context Management
Inline gate, activity-backed action — not a contradiction with the determinism constraints above, but a direct application of them:
- **The check** — comparing already-known cumulative token usage (from recorded model-activity results) against the compression threshold — is pure inline workflow logic, evaluated the same way as the stop-condition checks above. No activity needed for the check itself.
- **The compression operation, if the check trips**, is itself a model call (summarization), and therefore must be its own activity — exactly the kind of non-deterministic work the determinism constraints require to stay out of workflow code, not a special case.

### Resolved: Stop-Condition Default Values
- **`max_iterations = 20`**
- **`max_retries = 5`** (turn-level cumulative cap, distinct from the per-activity retry ceiling)
- **Token/cost budget: a generously high placeholder ceiling, not literal infinity.** Considered leaving it unset entirely, rejected: an unset budget makes that clause a permanent no-op and removes the one check in this stop condition that tracks *cost* rather than *count* — `max_iterations`/`max_retries` don't catch a loop that's expensive per-iteration (e.g. large tool results, big subagent fan-outs) rather than merely long-running. A high placeholder (order of magnitude above expected normal usage) keeps the mechanism live and testable now, without constraining real usage, and is tuned down later once real cost data exists — same treatment as the heartbeat-interval numbers, a starting point rather than a final value.

### Resolved: `GetVersion`/Patching Convention (First Pass)
**Rule of thumb — what needs explicit versioning:** any change to the loop's *control flow* — what triggers the loop to continue/stop, the order or presence of activity calls, how signals get handled or dequeued — needs a `workflow.getVersion(changeId, DEFAULT_VERSION, NEW_VERSION)` guard. **What doesn't:** changes fully inside an activity's own implementation (e.g. improving how the model-call activity formats its prompt, or how a tool executes internally) — those are opaque to the workflow's replay history already, so they're safe to deploy directly, no versioning needed. The dividing line is exactly the determinism boundary already established: if it could change *what the workflow code itself decides*, it needs a version gate; if it only changes what an activity does internally, it doesn't.

**Change-ID naming convention:** `{component}-{short-description}`, e.g. `turn-loop-add-cost-budget-check`, `turn-loop-signal-coalescing-v2` — stable, descriptive, never reused for a different change even after the old branch is retired (reusing an ID for an unrelated change would corrupt version interpretation for any workflow history still referencing the original meaning).

**Cleanup:** an old version branch can only be deleted once no execution that could still be replaying against it remains possible — in practice, once every turn/subagent workflow started before the change has completed. Given turns are short-lived this is usually a short window, but subagent nesting means it isn't a guaranteed one, so cleanup should be a deliberate, checked step (e.g. confirming no open workflow executions reference the old version) rather than an assumed-safe cadence.

**Left genuinely open:** no tooling/process is proposed yet for *tracking* which change-IDs are still load-bearing (i.e., an actual registry or checklist) — this first pass establishes the rule and naming convention, not the operational tracking mechanism.

### Resolved: Reference-Passing Contract (Content Never Enters Workflow Memory)
**Introduced 2026-08-14**, as the mechanism that lets the loop-worker pool be shared across tenants (`components/multi-tenancy.md`) instead of dedicated per tenant. Applies to every activity this workflow calls that touches conversation content: `ModelCall`, `ToolCall`, and their inputs/outputs.

- **Activity inputs are references, not content.** The workflow passes `{turn_id, message_id}` (or equivalent) into `ModelCall`, not the actual message text. The activity does its own read against that tenant's Postgres before doing any real work.
- **Activity outputs are references back, not content.** `ModelCall` writes the model's response into Postgres itself and returns a reference (plus the small set of workflow-control-relevant fields below) — not the response text.
- **What the workflow is allowed to hold, because control flow structurally requires it:**
  - Tool **names** (to decide activity vs. child-workflow dispatch, and which heartbeat tier applies).
  - Tool **count / presence** (the `len(response.ToolCalls) == 0` stop-condition check).
  - Token usage figures (for the budget check) — numbers, not content.
  - `retry_hint` metadata, if the model supplies one — a protocol-level control value, not content.
- **What the workflow must never hold:** tool call **arguments**, tool call **results**, message **content**, subagent transcripts. All of these are reference-only, read/written directly by activities against Postgres or, for large payloads, the session filesystem PV (claim-check pattern — see `components/session-filesystem.md`).
- **Large payloads (big tool outputs, file diffs) route through the PV, not Postgres** — this was already the direction flagged as an open concern under "workflow history size / large payloads" before multi-tenancy motivated it further; now resolved as: Postgres holds structured/modest-sized content (messages, tool metadata), the PV (via the existing session-filesystem lease mechanism) holds large blobs, and the workflow holds a reference to whichever store actually has the bytes.
- **Panic suppression is defense-in-depth here, not the primary mechanism.** Because content isn't in the workflow's memory on the success path (the dominant path), an unhandled panic in an activity has structurally less to leak than it would in an activity that held real content. The one residual seam: this only fully holds if activity **inputs** are reference-only too, not just outputs — a serialization failure on a content-bearing input could still surface content in a Temporal-generated failure. Activities should still catch and sanitize their own panics as good practice, but it's a hardening layer, not what makes sharing the pool safe.
- **New per-call cost accepted:** every content-touching activity now does at least one Postgres/PV read at the start and a write at the end that didn't previously exist on this path — single-digit-ms overhead against multi-second model/tool calls, the same "rounding error" reasoning already applied to outbound-queue latency in `components/activities-outbound-delivery.md`. This is Temporal's own documented "claim check" pattern for large/sensitive payloads, not a workaround — durability and replay are unaffected, since Temporal only ever needed a deterministic record that a call happened and what reference it returned, never the content itself.

### Resolved: Reference/ID Schema, and Two Consequences the Contract Forces
**Introduced 2026-08-14**, closing the "exact `args_ref`/`ModelResponse` reference schema" open question below. Working through the actual mechanics surfaced two real consequences the contract forces, not just a field-naming exercise:

**1. The inbound message write moves from end-of-turn to start-of-turn.** Previously, the persist activity wrote the whole turn's messages (inbound + outbound) in one transaction at the end. Under reference-passing, `ModelCall`'s very first call needs the inbound message *already in Postgres* to read — there's no workflow-held content left to hand it. So: the gateway's `SignalWithStart` payload (already durable via Temporal's own signal history — no double-write) is written to `messages` by a small activity at the **start** of the turn, before the first `ModelCall`, not batched with the rest at the end. `Persist` at end-of-turn still exists, but now only covers what accumulated *after* that first write (assistant/tool messages) — a narrower activity than before, not a removed one.

**2. `ModelCall` mints tool-call and subagent IDs, not the workflow.** Previously the workflow assigned `{turn_id}:act:{n}` when starting each activity. Under reference-passing, `ModelCall` is the one writing the `tool_calls` row (since it owns the response content, including arguments) — so it has to mint the ID as part of that write, and hand the ID back to the workflow as part of its reference-only return. The workflow still owns *dispatch* (activity vs. child workflow, per tool name) — it just no longer owns *ID assignment*. `SubagentTurnID` minting shifts the same way, for the same reason.

**Resolved shapes:**
```
ModelCallInput  { turn_id, context_seq }         # context_seq: how many messages ModelCall should read, an int — not a payload
ModelCallOutput { has_tool_calls: bool,
                  tool_calls: [{tool_call_id, tool_name, is_subagent}],  # names/IDs only — no arguments field
                  usage: {input_tokens, output_tokens} }
ToolCallInput   { tool_call_id }                  # ToolCall reads its own arguments from Postgres via this ID — no arguments field
ToolCallOutput  { tool_call_id, status }           # ok | error | cancelled — result/reason/side_effect stay in Postgres, workflow only sees status
```
`TurnInput` (session coordinator → turn workflow) shrinks correspondingly: `{session_key, turn_id, parent_type}` — no `InitialMessage`, no content of any kind. The turn workflow's very first step becomes "run the start-of-turn message-write activity," not "start reasoning with content already in hand."

**3. Test-fixture content (scripted `ModelCall` responses, used for local/CI testing per the repo's `workflows/scenarios/`) is itself content, and can't pass through the workflow either without quietly violating the contract it's supposed to demonstrate.** Resolved: the starter CLI writes the scripted-response sequence to a clearly-named, non-production table (`_test_scripted_responses`, keyed by `turn_id`) *before* signaling, in the same step that writes the inbound message. `ModelCallInput.context_seq` doubles as the fixture's index when a turn has fixture rows — `ModelCall` checks `_test_scripted_responses` first (if any row exists for this `turn_id`), falling back to a real model call otherwise. No separate scripted-vs-real code path in the workflow itself — the workflow always just calls `ModelCall`, exactly as it does today; only `ModelCall`'s own implementation branches, and only on data, not on workflow input.

### Considered and Deferred: Task Queue Separation (`agent-loop` / `agent-tools`)
**Considered 2026-08-15, reverted the same day before any implementation landed.** Briefly designed (and documented here as "Resolved") splitting the single `agent-loop` task queue into `agent-loop` (workflows, `ModelCall`, bookkeeping) and a new `agent-tools` (`ToolCall` only), reasoning that real tool execution (`shell_exec`) has a genuinely different resource profile than everything else on the queue. Reconsidered and reverted: that argument was theoretically reasonable but never backed by any real contention data — inconsistent with how every other numeric/operational decision in this doc is treated (heartbeat tuning, token budget, `GetVersion` tracking — all explicitly deferred pending real usage data, not decided on structural argument alone). The concrete, decisive reason to revert: it would have meant a **third pod per tenant** (a separate `ToolCall`-only Deployment, on top of the tenant-worker and Postgres pods already required), multiplying linearly across every tenant at real scale, for a benefit with no evidence behind it yet.

**Current state: one queue, `agent-loop`, carries everything** — `CoordinatorWorkflow`, `TurnWorkflow`, `ModelCall`, `ToolCall`, `InsertMessage`, `Persist`, `Deliver`, `CompressContext`. All tenant-side activities run in one `tenant-worker` fleet (`deploy/helm/agent-harness-tenant`), same as before this was ever considered.

**What's still worth keeping from the exercise — the general test, not the conclusion:** a new task queue is warranted when something's resource profile genuinely diverges from what's already on an existing queue (arbitrary local CPU/memory/duration vs. network-bound calls or quick Postgres writes, for example) — not merely because it's a new capability, and not on structural argument alone without real data behind it. Applying this test to a hypothetical Temporal-Schedules-based agent-reminder capability (discussed alongside this): a reminder-creation tool is just another `ToolCall`-dispatched tool, and the workflow a fired Schedule starts to deliver a reminder is a tiny, tenant-agnostic "signal this session's Coordinator" workflow with the same profile as `CoordinatorWorkflow`/`TurnWorkflow` — neither needs a queue of its own either. Revisit `ToolCall`'s queue placement specifically once real concurrency/duration data shows it actually contending with the rest of the loop in practice — the mechanism to split it later is cheap (one queue name, one `ActivityOptions.TaskQueue` override, one new Deployment reusing the existing container image) and was fully designed during this exercise, just not applied.

Separately, and unaffected by this reversal: workers were renamed for clarity — `workflow-worker` → **`loop-worker`**, `activity-worker` → **`tenant-worker`** — describing each one's actual architectural role (shared reasoning-loop engine vs. per-tenant fleet) rather than its Temporal mechanics.

### Resolved: Recursion Termination Guard
**Built 2026-08-29** — closes a real, previously-named-and-parked gap (`docs/future-work.md`'s 2026-08-06/08-07 Notes Log entries: "No depth/fan-out cap on subagent recursion," flagged again after comparing against OpenClaw's own one-level depth cap, "worth revisiting later," unrevisited since). Adopts LCM/Volt's own Task-tool mechanism (Ehrlich & Blackman 2026) directly: a subagent that wants to delegate to a *further* subagent must declare `delegated_scope` (the specific slice being handed off) and `kept_work` (what it's keeping for itself) — a call that can't articulate real `kept_work` is structurally rejected rather than dispatched, per the paper's own framing ("if the caller cannot articulate what it is keeping... the call is rejected with the instruction to perform the work directly").

**A real prerequisite gap was found and closed along the way, not assumed already true**: before this change, `is_subagent` was hardcoded `False` on every tool call parsed from a real model response, in both providers (`openai_provider.py`/`anthropic_provider.py`, streaming and non-streaming paths — four call sites total). No live model could spawn a subagent at all; `is_subagent: true` only ever appeared in test-fixture JSON (`workflows/scenarios/*.json`). This doc's own 2026-08-15 Notes Log entry already flagged this honestly ("no `spawn_subagent` tool offered to the model yet; subagent dispatch keeps working today via the fixture path only") but it went unaddressed for two weeks. Fixed as part of this change — `is_subagent` is now derived from whether the model actually called `spawn_subagent` (both providers gained a `_SPAWN_SUBAGENT_TOOL_NAME` constant, same duplicated-constant convention already used for `_NEXT_STEP_HINT_TOOL_NAME`), and `spawn_subagent` is a real `TOOLS_SCHEMA` entry for the first time. Named to match the existing fixture's own established convention (tool name `spawn_subagent`, `arguments.prompt`) and this codebase's own vocabulary (`is_subagent`, `subagent_turn_id`, `merge_subagent_output`), not the paper's literal "Task."

**No separate "Tasks" (parallel array) tool was added.** `turn.go`'s own tool-call fan-out already dispatches multiple subagent child workflows concurrently within one reasoning step whenever the model calls `spawn_subagent` more than once in the same response — the paper's "Tasks" shape, for free, with no second tool needed. This also settles how the paper's "the guard is not applied to parallel tasks, as they represent sibling decomposition rather than nested delegation" carve-out maps here: since there's no separate fan-out tool to exempt, the guard is scoped by **the caller's own position in the tree**, not by how many `spawn_subagent` calls appear in one response — every call issued by a turn whose own `parent_type == 'turn'` (i.e. the caller is itself a subagent) is nested delegation and requires `delegated_scope`/`kept_work`, regardless of whether it's solo or one of several in that step; every call issued by the root turn is exempt, regardless of how many siblings it spawns alongside it.

**Two-layer enforcement, schema first, mint-time second:**
1. **Schema-level**: `llm.tools_schema_for(is_subagent)` now also substitutes `spawn_subagent`'s definition — the root variant (`prompt` only) for a root-issued call, a second variant requiring `delegated_scope`/`kept_work` for a subagent-issued call. A real model literally cannot omit the fields and still match its own offered schema.
2. **Mint-time, in `model_call.py`**: schema conformance alone can't be trusted to hold for every real model on every call, so `_validate_subagent_delegation` re-checks `delegated_scope`/`kept_work` are both present and non-blank (after stripping whitespace) at the point `ModelCall` mints tool-call rows — the only place in the whole call chain that has both the raw arguments and the caller's own subagent-ness at once. A subagent dispatch is a **child workflow**, not a `ToolCall` activity, so this can't be enforced inside a tool handler the way an ordinary validation error would be — `turn.go` decides Activity-vs-child-workflow purely from `ToolCallRef.IsSubagent` with no validation step of its own. A rejected call is resolved directly at mint time (`tool_calls` row inserted with `status='error'` and a real result already set, `ids.activity_id` rather than `ids.subagent_turn_id` since it never becomes a real subagent) and is **not** included in the `ToolCallRef`s returned to the workflow — so the workflow never dispatches anything for it, neither an activity nor a child workflow. The rejection surfaces to the model on its next call through the exact same path an ordinary failed tool call already takes (`lcm.assemble`'s existing `status != 'ok'` branch) — no new delivery mechanism needed.

**Deliberately a presence/non-blank check, not a semantic "did you keep enough" judgment.** The paper's own wording ("cannot articulate what it is keeping") names the failure mode as an inability to state anything at all, not a quality bar on what's stated, and doesn't specify an algorithm for judging the latter. Building a semantic check would mean a second LLM call judging the first's output — real new cost and complexity this project's own standing anti-over-engineering discipline (the `shell_exec` per-command classifier, rejected on the same grounds) argues against building speculatively, especially with no evidence yet that presence-only checking is insufficient in practice.

**Deliberately no read-only-exploration-agent exemption.** The paper exempts a specific subagent flavor (one with no `Task` tool in its own schema at all, so it structurally cannot recurse) from ever needing to supply the params. This codebase has no notion of subagent "flavors" today — every subagent gets the identical `tools_schema_for(is_subagent=True)` schema. Introducing a role/flavor system was out of scope for this change (asked for the recursion guard specifically, not a new subagent-typing mechanism) — named honestly here rather than silently assumed away; a real future item if a genuinely read-only subagent shape is ever wanted.

**No additional hard numeric depth cap layered on top.** The paper doesn't describe one either (confirmed directly against the source — this detail is left unspecified there), framing the declaration-and-rejection mechanism itself as what makes "recursion... well-founded and must bottom out regardless of depth." This is a **soft** guarantee — it relies on the model's own honesty when describing `delegated_scope`/`kept_work`, not a numeric ceiling a runaway or adversarial model couldn't talk its way past turn after turn. Named as a real, live risk, not glossed over — a hard depth backstop remains a legitimate follow-up if real usage ever shows the soft guarantee insufficient (see Open Questions).

**Zero Go-side changes.** `turn.go`'s dispatch is already generic on `ToolCallRef.IsSubagent`, with no per-tool-name special-casing — the entire guard lives in Python (`llm.py` schema substitution, `model_call.py` mint-time validation, both providers' `is_subagent` derivation fix). `merge_subagent_output`/`tools.py`/`TOOL_REGISTRY` also untouched — `spawn_subagent` was never routed through `ToolCall`/`TOOL_REGISTRY` at all; it's dispatched by `turn.go` directly as a child workflow, same as before this change, just now reachable by a real model instead of fixtures only.

**Verified**: `py_compile` clean across every touched file; a real mocked `OpenAIProvider.call_model` call (fake API response choosing between `shell_exec` and `spawn_subagent`) confirms `is_subagent` is now correctly derived from the tool the model actually called, not hardcoded — the core prerequisite bug, proven fixed, not just code-reviewed; `tools_schema_for`'s root/subagent substitution confirmed via direct schema inspection (root variant `required: [prompt]`, subagent variant `required: [prompt, delegated_scope, kept_work]`); `_validate_subagent_delegation` confirmed accepting genuine narrowing and rejecting missing/whitespace-only fields. Checked every existing fixture that spawns a subagent (`subagent-spawn.json` and all three `subagent-merge-*.json` scenarios) for nested (subagent-issued) `spawn_subagent` calls that this guard could newly affect — none exist; every fixture spawn is root-issued, so the whole existing scenario suite is unaffected by this change. **Not yet verified against a real live deployment** — this changes real model dispatch behavior (a live model can now genuinely spawn a child workflow for the first time), a bigger behavioral change than the LCM Memory-Access Tools, so it wasn't pushed to the tenant unprompted; needs a deploy + a real live test (a real subagent attempting further delegation with and without genuine `delegated_scope`/`kept_work`) before this can be called fully closed.

### Open Questions / To Design

- **Whether a read-only/exploration subagent flavor (no `spawn_subagent` in its own schema, structurally unable to recurse at all) is ever worth adding** — the paper has one, this codebase doesn't; out of scope for the recursion-guard change itself, named honestly as unaddressed rather than silently assumed unnecessary.
