### Role (one line)
A reusable primitive letting a turn — or one of several parallel tool calls within it — pause and ask the human something (an approval, a choice, a clarifying decision), then durably wait for a response no matter how long that takes, and resume exactly where it left off. Permission gating for destructive tool calls is the first, motivating consumer; decision requests for genuinely ambiguous mid-task choices are a second, structurally identical one.

### Why this exists (recap)
Originally scoped narrowly as "permission gating for destructive tool calls" (`future-work.md` §4, unresolved since 2026-08-07: *"does it ever need a human-approval round-trip mid-turn... not covered by the existing interrupt design"*). Surfaced as a real, concrete gap while designing the Gateway's Web platform (`components/gateway/web.md`) and working through a mid-turn-approval scenario directly: a tool call needs to pause waiting on a human, possibly for hours or days, and resume exactly where it left off once answered — not get cooperatively cancelled and folded in as a new turn iteration, which is what today's *existing* interrupt mechanism does for an unrelated new message. That's a genuinely different operation. Generalized from there, in conversation, once it became clear the same "pause, wait indefinitely, resume exactly there" shape applies to any mid-turn human interaction, not just approvals.

### Resolved: Why an Activity Can't Do This, a Workflow Can
The gating/decision *check* has to inspect real content (e.g. a shell command's actual arguments) — content that only ever lives in Postgres, never in the workflow's own memory (`temporal-workflow.md`'s reference-passing contract) — so the check itself has to be an activity. But the *wait* cannot be: an activity blocking for hours/days ties up a worker slot, doesn't fit Temporal's heartbeat/timeout model for genuinely open-ended waits, and doesn't survive worker restarts cleanly. A **workflow-level signal wait** (`workflow.GetSignalChannel(ctx, "UserInputResponse").Receive(ctx, &response)`) does exactly this natively — blocks cheaply and indefinitely, resumes exactly where it left off the instant the signal arrives, no reconstruction needed. This is Temporal's own flagship pattern for long-running human-in-the-loop workflows, not something bolted on.

### Resolved: Core Mechanism — `UserInputRequestWorkflow`
A small, generic child workflow, reused identically regardless of which consumer (permission gating, a decision request, anything similar) is driving it — mirrors how a subagent is dispatched as a child workflow (`is_subagent: true`), not a new dispatch shape.

**Request/response shape** — kind-agnostic; `context` carries whatever the specific consumer needs and is opaque to this mechanism:
```
UserInputRequest {
  request_id: string          // real correlation key — how a response finds its way back to the exact waiting workflow
  kind: string                 // "permission" | "decision" | ... — open-ended, not a closed enum
  prompt: string                // "Run `rm -rf /tmp/foo`?" / "Which approach should I take?"
  options: [{id, label}]        // the selectable choices
  allow_free_text: bool          // whether a free-form reply is also acceptable, not just one of options
  context: jsonb                  // kind-specific payload (e.g. permission: {server, tool, tool_call_id}); opaque here
}
UserInputResponse {
  request_id: string
  selected_option_id: string | null
  free_text: string | null
}
```

**Flow, with all three ways the wait can end, all handled the same way (revised — see Notes Log):**
1. `RequestUserInput` activity: writes a `user_input_requests` Postgres row (`status='pending'`). For a connection-based platform, `UserInputRequestWorkflow` then dispatches a real interim-delivery activity to actually show the prompt/options to the user — see "Resolved: Mid-Turn Interim Delivery — Push Half" below. Web needs no push at all (`handlePoll` already surfaces `pending_input` on its own).
2. The workflow blocks on a `Selector` across three things: the response signal, a **1-hour timeout** (`UserInputRequestTimeout`, given directly, not deferred pending real usage data like most numeric thresholds in this project), and cancellation (`ctx.Done()`).
3. Whichever fires, a single `CloseUserInput` activity closes the row out — `answered` (a real response arrived) or `cancelled` (timeout or interrupt) — before the workflow returns anything. This uniform close-out is a deliberate fix, not the original design: an earlier version only updated Postgres on the happy path, leaving a row (and, separately, the originating `tool_calls` row) stuck at `'pending'` forever on cancellation — found via live testing, not reasoning, and fixed by routing every exit through the same activity call.

**Why always a child workflow, even when it should block the whole turn**: uniformity, not a special case per use. A decision that should halt the entire turn just gets spawned as one child and immediately awaited before continuing — functionally blocking, architecturally identical to permission gating, where it's spawned as *one of several* parallel tool-call futures, letting sibling calls proceed normally while this one waits. One mechanism, two calling patterns, no duplicated wait/signal logic maintained separately.

**An unrelated new message DOES cancel a pending request** — resolved (was an open question): the same cooperative-cancellation mechanism that already interrupts any other in-flight tool call also reaches a pending `UserInputRequestWorkflow`, since it's dispatched as a child under the turn's own `cancelCtx` like everything else. Folded in as a real `status='cancelled'` outcome on both `user_input_requests` and the originating `tool_calls` row, not silently dropped.

**Response routing**: not through the Coordinator's ordinary "forward a new message into the active turn" signal path (`NewMessageSignalName`) — that's for regular chat, folded into the next reasoning step. A response to a pending request carries its `request_id`; the Gateway looks up the actual target workflow ID from `user_input_requests` and calls `SignalWorkflow` directly against that specific execution — not `SignalWithStart`, since it must already exist and be waiting.

### Resolved: An Approval Request IS a User Input Request — One Workflow, Not Two
An earlier version of this design kept permission gating as a separate `ApprovalGatedToolCallWorkflow`, nested as its own child *inside* a `UserInputRequestWorkflow` call — specifically so a plain decision-request consumer wouldn't carry tool-call-dispatch behavior it didn't need. Reconsidered directly: an approval request genuinely *is* a user input request, not a different kind of thing layered on top of one. Collapsed into a single workflow type — `UserInputRequestWorkflowInput` carries an optional `ApprovalGatedCall {tool_call_id, tool_name}`; when set, this same workflow, after the wait resolves, also dispatches the real `ToolCall` activity if approved (or `DenyToolCall` if not/expired/cancelled) before returning. A plain decision-request consumer simply never sets that field and gets a clean response back — the genericity holds without a redundant nested child-workflow hop, one fewer workflow type to maintain, one fewer place the same wait/close logic could drift out of sync.

### Resolved: Permission Gating as the First Consumer — Fully Decoupled Permission List
**Considered and rejected along the way**: attaching a `requires_approval` property directly to each `shell_hub.py`/`mcp_hub.py` catalog/tool entry. Rejected on two grounds, both real: (1) it conflates a tool's own discovery/definition (intrinsic, owned by whoever built the catalog) with a deployment's approval *policy* (extrinsic, tenant-specific, ought to change independently); (2) it would have tied gating semantics to the same structure used for `search_tools`' embedding/search index, which should stay a pure discovery mechanism — `search_tools` returns relevant tools, nothing about whether they're gated.

**Resolved instead**: a standalone permission list, independent of both tool sources, reusing the exact `{server, tool}` identity vocabulary `search_tools`/`call_tool` already use — `server = "shell"` for shell-sourced commands:
```python
@dataclass(frozen=True)
class PermissionRule:
    server: str   # "shell" | an mcp-hub server name
    tool: str     # command name (shell) | tool name (mcp-hub)

PERMISSION_LIST: list[PermissionRule] = []  # empty — no tools populated yet, populated from a runtime-edited file (see "Resolved: Config Delivery" below)

def requires_approval(server: str, tool: str) -> bool:
    return any(r.server == server and r.tool == tool for r in PERMISSION_LIST)
```
Consulted only from the two execution paths, never from `search_tools`:
- `call_tool`: `requires_approval(server, tool)` — exact, no ambiguity, since `call_tool`'s `{server, tool}` identity is already precise.
- `shell_exec`: `requires_approval("shell", first_whitespace_token_of(arguments.command))` — deliberately simple, no real shell parsing. `shell_exec` is one generic tool covering any command string, so there's no exact tool identity to match the way `call_tool` has one; reducing to the first token is a conscious simplification, not a claim of correctness for compound/piped commands — explicitly not solving that now (see Open Questions).

`shell_hub.py`/`mcp_hub.py` are untouched by this — both stay pure discovery/proxy, no permission concept added to either.

### Resolved: Config Delivery — a Runtime-Edited File, Not a Helm Value
`PERMISSION_LIST` loads from a plain JSON file (`activities/activities/permissions.py`'s `_load_permission_list`) at `TOOL_PERMISSION_LIST_FILE` — a fixed path on the tenant's own PV (`deploy/helm/agent-harness-tenant`'s existing `tenantVolume`, the session-filesystem PVC, under its own disjoint `configSubPath` so it never collides with real session data). Missing file (the normal starting state — nothing pre-populates it) or invalid JSON both mean an empty list, not an error.

**Deliberately not a Helm value populating the content**, unlike most other per-tenant config in this project: there's nothing tenant-identity-shaped about a mutable policy list the way there is about, say, an LLM API key or a Postgres password — it's operational state someone edits directly (`kubectl exec`, or in principle the tenant's own `shell_exec`, worth noting as a real "the agent could loosen its own gating" edge case, not addressed here), read once at process startup. A Helm value would just be a second, driftable copy of whatever's actually on disk, and every edit would need a redeploy to take effect.

This closes what was an explicitly-flagged gap (see prior Notes Log entry): the mechanism was live-verified end to end before this, but had no Helm wiring making the *file itself* (mount, path, env var) actually reach a real pod.

### Resolved: Mid-Turn Interim Delivery — Push Half
**Built 2026-08-27.** Two genuinely separate problems were bundled under this one open item — a push side (how does the prompt actually reach the user mid-turn, before the turn ends) and a response-routing side (how does the human's reply get recognized as answering *this* pending request rather than starting an ordinary new turn). This pass closes only the first.

**Web needed nothing new at all** — checked directly rather than assumed: `gateway/web.md`'s `handlePoll` already reads `user_input_requests` alongside turns on every poll tick (its own comment: *"closes docs/components/user-input.md's 'mid-turn interim delivery' open item for Web specifically"*), and `handleRespond`/`respond.go` already resolves `request_id → workflow_id` and calls `SignalWorkflow` directly. Delivery "collapses" for Web the same way ordinary turn delivery already does (`gateway/web.md`'s own finding) — this doc's Open Questions bullet describing the gap as blocking "any real platform" was stale by the time it was re-read; corrected here.

**The real remaining gap was connection-based platforms only** — Discord text and Discord voice, where `RequestUserInputActivity` only logged what it would have shown. Fixed by reusing the exact embedded-per-connection-worker/deterministic-task-queue delivery mechanism `gateway.md`'s "Resolved: Outbound Flow" already built for `Deliver`/`DeliverChunk`, rather than inventing a second push mechanism:

- `UserInputRequestWorkflowInput` gained `SessionKey`/`ConnectionID` (workflow-dispatch-only routing metadata, kept off the persisted `UserInputRequest` struct itself, same scoping precedent as `ApprovalGatedCall`) — threaded through from `TurnWorkflow`'s own `input.SessionKey`/`input.ConnectionID` at the one dispatch site (the approval-gated tool-call path). Needed because Temporal requires the task queue (`deliver:{platform}:{connection_id}`) to be chosen at `ExecuteActivity` call time, not decided from inside the activity — the same reason `turn.go`'s own `deliverConnectionBased` resolves platform/connection_id before dispatch.
- `UserInputRequestWorkflow` now calls a new `dispatchInterimDelivery` right after `RequestUserInput` succeeds — a literal per-platform lookup (`connectionInterimDeliveryActivity`, mirroring `connectionDeliveryActivity`/`connectionDeliveryChunkActivity`'s own "two platforms exist today, a third is a one-line addition" reasoning) resolves the activity name/timeout, empty `ConnectionID` (Web, or a future platform with no connection-lease concept) short-circuiting to a no-op.
- New activities, registered on the same embedded per-connection worker `Deliver`/`DeliverChunk` already use (same live session, no new worker lifecycle to manage): `DiscordDeliverInterim` (`deliver_discord.go`) reads the request's `prompt`/`options` plus routing (`channel_id`, `session_key`) via one join off `request_id`, sends plain numbered-option text (deliberately not Discord message components/buttons — that's the harder, separate response-routing half, untouched here), and — same fix already applied to the bot's regular replies — records the sent message into `discord_ambient_messages` via the existing `recordAmbientBotMessage`, so a reply to *this* message doesn't reopen the "bot messages have no ambient row" gap closed earlier. `VoiceDeliverInterim` (`deliver_voice.go`) speaks the prompt + numbered options via the same `synthesizeSpeechPCM`/`streamPCMToOpus`/barge-in machinery `Deliver` already uses, deliberately the simplest possible rendering (no attempt at natural phrasing).
- **Own idempotency, deliberately independent of both `delivered_responses` (turn-final-answer only) and `user_input_requests.status`**: new `prompt_delivered_at` column (`008_user_input_interim_delivery.sql`) — "was the prompt pushed" and "has the human answered" are different questions; a Temporal retry of the dispatching call must not re-send the prompt while `status` is still legitimately `'pending'`. Same check-before-send/mark-after-send-succeeds shape as `Deliver`'s own previously-fixed idempotency bug — never claim delivery before the real send succeeds.
- **Best-effort by design**: a failure to push logs and is swallowed, never fails the whole `UserInputRequestWorkflow` — the request is already durably recorded regardless, and (for Web) doesn't depend on this push existing at all.

**Deliberately not attempted this pass**: response-routing. A human answering a pushed Discord-text or Discord-voice prompt still has no way to have that reply recognized as an answer rather than an ordinary new turn — real, separate, harder future scope (see Open Questions below).

Verified two ways: a unit test against `connectionInterimDeliveryActivity`'s own lookup table (all platform/no-platform cases, deleted after passing), and a real `BEGIN`/`ROLLBACK` SQL round trip against the live `abishekk` Postgres — applied the actual migration, inserted a real fixture row, and confirmed both new activities' exact queries (idempotency check before/after, the `user_input_requests → turns → sessions` routing join, the simpler options-only voice read) return the right shape; nothing left behind. `go build`/`go vet`/`gofmt` clean on the whole `workflows` module. **Not yet verified against a real live gated tool call on Discord** — needs a redeploy (including the new migration) and an actual approval-gated `shell_exec`/`call_tool` invocation through a real Discord bot to confirm end to end.

### Open Questions / To Design
- **Response-routing for push platforms.** Now that Discord text/voice actually push a pending request's prompt (see "Resolved: Mid-Turn Interim Delivery — Push Half" above), there's still no mechanism recognizing a human's reply as answering that specific request rather than starting an ordinary new turn. Two platform-specific shapes considered, neither built: Discord text could use real message components (buttons, `custom_id = request_id`) — clean, no ambiguity, extending `discord.go`'s existing `InteractionCreate` handler (today slash-command-only) — or a plain-text "reply 1 or 2" convention, which reopens ambiguity a gate would need to resolve before treating an inbound message as a new turn. Discord voice has no button equivalent at all — the only shape is gating the next utterance against a pending request before dispatching it as a new turn, with fuzzy-matching a spoken word to an option label. Not designed in depth yet, just named here as the real next half of this gap.
- **Exact `user_input_requests` Postgres schema is now implemented**, not just conceptual — `activities/migrations/003_user_input_requests.sql`.
- ~~UI response mechanics per platform~~ — **resolved for Web, 2026-08-24**: `PendingInputCard` in `agent-web`'s `Chat.tsx`, wired to the Gateway's `POST /respond` (`workflows/cmd/gateway/respond.go`), which resolves `request_id` → `workflow_id` and calls `SignalWorkflow` for real — no longer just the `temporal workflow signal` CLI standing in. Live-verified with a real approval click, not a simulated one — see Notes Log. Still open for any other platform kind (Discord/Slack buttons, slash commands) — not a real build target yet.
- **`shell_exec`'s first-token reduction is a known, accepted simplification, not a solved problem** — a compound command (`rm -rf /tmp/foo && curl ...`) or one invoked via `sh -c "..."` won't be caught by matching only the first token. Left deliberately simple per direct instruction; a real fix (if ever needed) would require actual shell parsing, not attempted here.
- **1-hour timeout is a flat constant, not configurable per-deployment or per-request-kind** — a decision request might reasonably want a different wait than a destructive-command approval. Not raised as a problem, just not yet distinguished.
