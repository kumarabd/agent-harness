# Gateway: Discord Voice

## (Connection-Based, Per-Channel, Command-Triggered)

> STATUS: LIVE — the bot has actually joined a real Discord voice channel and this pipeline is real production traffic, not just verified-in-isolation code (2026-08-26). Follows `../gateway.md`'s cascaded architecture: Voice Client → Media Gateway → STT Service → Voice Orchestrator → LLM → TTS Service → Audio Player. Bidirectional realtime STT is built (WhisperLive, not the originally-planned `/v1/realtime` — see "Resolved: True bidirectional realtime STT"), Silero VAD is built and deployed as a sidecar, ModelCall streaming (2026-08-26: now wired into voice too — `VoiceDeliverChunk` synthesizes and plays each sentence as it's generated instead of waiting for the whole response; `../gateway.md`'s own Notes Log has the full detail, including a real cross-platform race it closed along the way). Several real, only-visible-once-live bugs have already been found and fixed against real production traffic: a Discord DAVE/E2EE protocol break requiring a `discordgo` fork (`go.mod`'s own comment), the bot joining self-deafened (`ChannelVoiceJoin`'s `deaf` flag), missing `SPEECH_API_KEY`/`TTS_VOICE` Helm wiring (both silently never configured), a real sample-rate mismatch that made delivered speech unintelligible ("Resolved: Sample Rate / Format Conversion" below has the full story — a duration-math verification from 2026-08-25 turned out to be wrong), and an idempotency-claimed-before-real-work bug that made Temporal's own automatic retry silently skip redelivery after a genuine mid-flight failure (found via `temporal workflow show`'s event history, not logs alone). This doc's own Notes Log has the dated detail for each. `ffmpeg` stays removed from the image (see that same section for why, corrected). Fast-path barge-in built and verified with real `-race` concurrency tests.

### Role (one line)

Speech-to-text ingestion and text-to-speech delivery for a Discord voice channel this tenant's bot has joined — this doc's own instance of `../gateway.md`'s generic cascaded pipeline, reusing the exact same downstream `MessageEvent`/session/turn pipeline every other platform does for the Voice Orchestrator/LLM stages; Media Gateway, STT Service, TTS Service, and Audio Player are what's genuinely new here.

### Why this doc exists separately from `gateway/discord.md`

Same bot, same token, same Discord application — but a fundamentally different connection shape. Text is one persistent gateway websocket per bot, sending/receiving JSON events. Voice is per-*channel*: a bot can hold a simultaneous voice connection in every guild it's in, each its own RTP/UDP audio stream, established as a child of the already-open text gateway connection (Discord's own protocol requires an active main gateway session to negotiate a voice connection at all — you can't join voice without it). That 1:many-per-bot shape, plus an entirely different pipeline (audio in, audio out, no literal "mention" object to check), is enough of a different mechanism to warrant its own doc, same reasoning `discord.md` itself gives for splitting out of `../gateway.md`.

### Resolved: Join Trigger — Command-Triggered, Not Auto-Join

A slash command (`/join`, invoked by a user already in a voice channel) is what gets the bot into a voice channel — not automatically joining whenever any human enters one. Considered and rejected auto-join: it's a more intrusive default (an always-listening bot nobody explicitly invited into that specific conversation) and doesn't match the personal/small-tenant deployment model text already established (`discord.md`'s own "Resolved: Auth" — the operator/user explicitly invites the bot in, not the other way around). A command is an explicit, per-conversation opt-in, same spirit.

Leaving is symmetric: an explicit `/leave` command, not auto-leave when the channel empties. Same reasoning as the join side — an explicit action either way, not the bot inferring intent from channel occupancy.

### Resolved: Connection Model — Per-Voice-Channel, Downstream of the Text Connection

Each joined voice channel is its own live connection (`discordgo`'s `Session.ChannelVoiceJoin(guildID, channelID, ...)`, returning a `*discordgo.VoiceConnection`), not something shared across channels the way the text gateway websocket is shared across a whole bot. Since `ChannelVoiceJoin` is a method on the *same* `*discordgo.Session` the text connection already holds open, **only the replica currently holding that bot's text connection lease can ever join a voice channel for it at all** — there's no live `dg` session to join with otherwise. This means the "two replicas racing to hold the same connection" failure mode `../gateway.md`'s "Resolved: Connection Leasing" originally designed the lease to prevent can't actually happen for voice — it's already serialized through the one live text session.

The lease is still worth keeping, for a different reason than race-prevention: it's the addressing/discovery mechanism the turn workflow needs at delivery time (which replica, if any, currently has this specific voice channel joined), and it gives voice connections the same renewal/heartbeat/crash-cleanup story text already has for free. Reuses `gateway_connection_leases` as-is (`platform = 'discord-voice'`) — no new table. `connection_id` is `{bot_id}:{voice_channel_id}` (`../gateway.md`'s composable-`connection_id` amendment) — both halves platform-provided, addressing one specific live connection rather than "this bot" as a whole, which is what lets the same bot hold leases for several guilds' voice channels simultaneously without collision.

### Resolved: STT/TTS as a Standard, Provider-Agnostic Contract

Not a Whisper/Kokoro-specific integration — designed against the OpenAI-compatible Audio API shape (`POST /v1/audio/transcriptions`, `POST /v1/audio/speech`) that's become the de facto standard most STT/TTS providers implement, the same way `activities/activities/llm.py`/`workers/mining_common/llm.py` are already designed against the OpenAI-compatible chat-completions shape rather than a specific model's own API. This is what actually makes it provider-independent: swapping Whisper for a different transcription model, or Kokoro for a different TTS voice, is a config change (base URL + model name), not a code change, as long as the replacement speaks the same standard shape. `whisper-large-v3` (`whisper-svc.core.svc:8000`) and `kokoro` (`kokoro-svc.core.svc:8880`) are already registered on the shared `litellm` proxy specifically because litellm's whole purpose is normalizing diverse backends behind this exact contract — real, running infra, nothing new to stand up. Confirming the exact live request/response shape against both (litellm's `litellm_params` entries imply it, don't guarantee it byte-for-byte) is a pre-implementation verification step, not a design decision — listed under Open Questions below as a checklist item, not an unresolved fork.

### Resolved: Audio Pipeline Shape

- **Capture**: `VoiceConnection.OpusRecv` delivers Opus-encoded RTP packets per speaker (`SSRC`); `VoiceSpeakingUpdate` maps a given `SSRC` to a Discord user ID as speaking starts/stops.
- **Decode**: Opus → PCM, per speaker, via a cgo `libopus` binding (`layeh.com/gopus` — the standard pairing with `discordgo` for exactly this) rather than a pure-Go decoder. Trades a C toolchain + `libopus` in the build image (`deploy/docker/gateway.Dockerfile` needs updating) for using the real, mature reference implementation rather than a reimplementation.
- **Utterance boundaries**: per-speaker audio scored continuously by a real VAD model — **Silero VAD** (small, ONNX, fast enough for real-time), the same approach modern production voice-agent stacks use (OpenAI's Realtime API, LiveKit Agents, Pipecat, Vocode) rather than a naive fixed-energy-threshold gate, which handles background noise/varying mic levels far worse. An utterance is marked complete after a run of continuous below-threshold frames following some minimum speech duration, with trailing padding to avoid clipping — mirrors why text buffers per-message rather than per-keystroke. The exact millisecond thresholds (silence duration, padding) are numeric tuning, deferred pending real usage like every other undecided interval in this project — the VAD *algorithm* choice is what's resolved here, not those numbers.
- **No ambient buffer table needed**: `discord_ambient_messages` exists for text because most messages are *not* triggering, and reply-chain resolution needs those non-triggering ones stored somewhere durable. Under "Resolved: Trigger Detection" below, every voice utterance triggers a real turn — there's no non-triggering category left to buffer, so every utterance already lands durably via the normal turn pipeline's own `messages` table, same as any other turn. An earlier draft of this doc sketched a separate `discord_voice_ambient_utterances` table by analogy to text; no longer needed once gating was deferred entirely.
- **Transcript → the rest of the pipeline**: identical to text past this point — the transcript becomes `MessageEvent.Content`, same `sessionKeyFor`/`Discriminator` mechanism, same Coordinator/Turn workflow, same everything. Voice's channel id is just another `ChannelID` (`discord.md`'s own "falls out naturally" reasoning for DMs applies here too).

### Resolved: Trigger Detection — No Gate, Deferred Pending Real Usage

Every utterance in a joined voice channel is treated as an implicit trigger — no wake-name check, no occupancy check, nothing gating it. A wake-name-substring approach and an occupancy-based gate (mirroring text's personal-vs-group-DM distinction — skip the gate only when the bot and exactly one other human are present, since that's genuinely the same "no addressing ambiguity" case, keep it otherwise) were both considered; deferred in favor of shipping the simplest version first and observing real model behavior before adding gating complexity, same treatment this project already gives other undecided thresholds (don't design the tuning mechanism before there's real data suggesting it's actually needed). Revisit if real usage shows the model responding to things that clearly weren't meant for it.

### Resolved: Outbound — TTS + Opus Playback, Not `ChannelMessageSend`

A new `VoiceDeliver` activity, structurally the same shape as `DiscordDeliver` (`deliver_discord.go`) — checks `delivered_responses` first (unchanged; `response_id = turn_id` is platform-agnostic), reads the turn's final content — but instead of `ChannelMessageSend`, synthesizes it via Kokoro (the standard TTS contract above), converts/encodes it to Discord's required shape (see "Resolved: Sample Rate / Format Conversion" below), and writes it to `VoiceConnection.OpusSend`. Registered on `deliver:discord-voice:{bot_id}:{voice_channel_id}` (the composed `connection_id` above), same embedded-worker-tied-to-the-lease lifecycle `discord.go`'s `runDiscordConnection` already establishes for text — created/started when the voice connection is joined, stopped when it's left or the lease is lost.

### Resolved: Sample Rate / Format Conversion

Discord's side is fixed, not a choice — the voice protocol requires exactly 48kHz, stereo, 16-bit PCM, Opus-encoded, in 20ms frames (960 samples/channel), via `discordgo`'s `OpusSend`/`OpusRecv` contract. The actual decision is how to get arbitrary-shaped audio to/from that fixed target:

- **Ingestion (Discord → Whisper)**: no conversion needed on our side beyond the Opus→PCM decode already happening for VAD — package that 48kHz stereo PCM into a WAV container and upload it as-is; the standard `/v1/audio/transcriptions` contract's server side handles arbitrary input sample rates (the same way OpenAI's own real API does), so client-side resampling isn't needed here.
- **Delivery (Kokoro → Discord)**: originally resolved as shelling out to `ffmpeg` for resampling (mono→stereo, rate conversion), on the assumption Kokoro's own native output rate couldn't be controlled. Superseded 2026-08-25 by a claim that turned out to be wrong, then **corrected again for real 2026-08-26**: the 2026-08-25 verification (a duration-math check against one synthesized sentence) concluded `/v1/audio/speech`'s `sample_rate` parameter was honored — it isn't. Real, live production voice output was garbled (playing back at roughly double speed, "fast noise") until this was re-tested directly: identical byte output from `kokoro-svc` regardless of `sample_rate`'s value or presence, confirmed both through `litellm`'s proxy and calling `kokoro-svc` directly. Kokoro's real native output is 24kHz mono (`voice_convert.go`'s `kokoroSampleRate`, itself verified via duration math against a known sentence, now cross-checked against actually-correct playback). The fix: `deliver_voice.go` reads response chunks sized for 24kHz, and `voice_convert.go`'s `upsample2xPCM` (new — linear interpolation, exactly 2x since 24kHz→48kHz is an exact ratio) runs before the existing `monoToStereoPCM` mono→stereo duplication. `ffmpeg` staying removed from `deploy/docker/gateway.Dockerfile` is still correct — this doesn't need a general-purpose resampler, just the cheap 2x-specific one — but the original "no conversion needed at all" framing was not. Opus encoding itself (Discord's specific 20ms/960-sample framing) stays in Go via `layeh.com/gopus`, unchanged. Real end-to-end verification: a full encode→decode round trip through the actual corrected pipeline against the real live service produced 4.48s of audio for a 13-word sentence — a natural speaking pace, not the ~2x-sped-up duration the bug produced.

### Resolved: Overlapping Speech / Interrupts — Both Paths Closed

`coordinator.go` already forwards any signal on an active turn into the running `TurnWorkflow` (`SignalExternalWorkflow`, "the distributed active-session guard") rather than starting a second turn — a voice utterance becoming a `MessageEvent` inherits that dispatch for free, same as a text follow-up mid-turn. Tracing this directly (2026-08-25) surfaced a real gap: `TurnWorkflow` only drained its `pendingMessages` queue *between* `ModelCall` loop iterations, so a signal arriving while `Deliver`/`VoiceDeliver` was being awaited just sat unread until the workflow returned, then was silently discarded — meaning the *entire duration of voice playback* was exactly the window an interrupting utterance got lost. **Slow path closed the same day**: `turn.go`'s `deliverConnectionBased` (renamed from `deliverToConnectionBasedPlatform`) now races the delivery activity against a buffered, non-blocking-notified channel fed by the same signal-drain goroutine; a signal arriving mid-delivery cancels the in-flight activity and hands the payload back via `types.TurnResult.InterruptedDuringDelivery`, which `coordinator.go` treats exactly like a freshly-arrived signal, starting a new turn with it. Generic mechanism, not Discord-voice-specific — lives in `turn.go`/`coordinator.go`/`types.go`; `../gateway.md`'s own Notes Log has the full detail.

**Fast path closed too, same day.** The slow path alone still requires a complete transcript before anything happens — the bot would keep talking for as long as transcription takes even after the human starts talking over it. `voice_bargein.go`'s `voiceBargeIn` closes that: a purely local, in-process signal (no Temporal, no Postgres) between `voiceCaptureLoop` (fires on every VAD-classified speech frame, a no-op unless this connection is currently playing) and `voiceDeliverActivity.Deliver`'s send loop (selects on the returned channel alongside `ctx.Done()`/`OpusSend`, stops immediately). `../gateway.md`'s own Notes Log has the full mechanism detail and the concurrency-test coverage (`-race`-verified). The two paths remain complementary, not redundant: fast-path only stops local audio output; deciding what to do with whatever the human actually said is still entirely the slow path's job.

### Resolved: Turn Lifecycle Stays Gateway-Local, Not a Shared-Schema Change

Decided directly (2026-08-25): the richer voice lifecycle (`LISTENING → SPEAKING → PROCESSING → GENERATING → SYNTHESIZING → PLAYING → COMPLETED`, `PLAYING → INTERRUPTED` for barge-in) stays entirely inside the Gateway process — in-memory, not a new column on the shared `turns` table. `turns.status` keeps its existing four coarse states (`running`/`completed`/`cancelled`/`failed`), unchanged for every platform including text, which has no use for `SYNTHESIZING`/`PLAYING` at all. Matches the Media Plane/Agent Plane split (`../gateway.md`) directly: this is Media Plane state (what is this connection's speaker/mic doing right now), not Agent Plane state (the shared, cross-platform, durable turn record) — keeping it local is keeping the boundary that split already draws, not a new one.

**Real implementation wrinkle, resolved during the build**: not every state is something the Gateway can observe directly. `LISTENING`/`SPEAKING` (capture) and `SYNTHESIZING`/`PLAYING`/`INTERRUPTED` (delivery) all happen inside the Gateway process itself — trivial to track locally. `PROCESSING` (the STT call) is also Gateway-local (`transcribeAudio` runs here). `GENERATING` (the `ModelCall`/`ToolCall` loop) happens entirely in `tenant-worker`, a separate process reachable only through Temporal — the Gateway never observes that loop directly, so `GENERATING` is approximated as "the STT transcript came back non-empty and a message event was just submitted," not as a real signal crossing the process boundary. Good enough for the "what's this connection roughly doing" logging goal this was scoped for; a real cross-process signal would be a separate, bigger lift.

Built (2026-08-25). `voice_lifecycle.go` (new file): `voiceLifecycleState` (7 states, matching the fork decision's names) and `voiceLifecycle` — connection-scoped (not per-turn/per-speaker, a deliberate simplification, see the file's own comment), in-memory, `sync.Mutex`-guarded, logging every genuine transition (`"discord-voice: connection %s lifecycle %s -> %s"`), skipping no-op same-state calls. Constructed once per connection in `voiceJoin` (`discord_voice.go`), alongside `bargeIn` — same one-instance-per-connection, shared-between-capture-and-delivery treatment. Wired at every real transition point:

- `voiceCaptureLoop`: → `SPEAKING` on every VAD-classified speech frame (same branch as `bargeIn.signalSpeech()`); → `PROCESSING` when an utterance is flushed for transcription; → `GENERATING` once transcription succeeds with non-empty text, right before `submitMessageEvent`; → back to `LISTENING` directly on a failed/empty transcription or a failed `submitMessageEvent` call (no turn started, so `Deliver`'s own reset below never runs for that attempt).
- `deliver_voice.go`'s `Deliver`: → `SYNTHESIZING` before calling `synthesizeSpeechPCM`; → `PLAYING` right after `bargeIn.startPlayback()`; → `INTERRUPTED` in the barge-in `case <-stopChan:` branch; a `defer` set right after the idempotency check passes resets to `LISTENING` on every exit path (success, error, `ctx.Done()`, barge-in) — one line covering all of them rather than repeating a transition at each return.

No getter/accessor added — nothing outside `voiceLifecycle` itself consumes the state yet (logging is the only observer), so no external API surface was built ahead of an actual need. Verified via `CGO_ENABLED=1 go build ./...`, `go vet ./...`, and `gofmt -l` on the whole `workflows` module — all clean. Not yet exercised against a real live Discord voice connection (same gap the rest of this pipeline has — see the "Core pipeline built" entry below).

### Resolved: Turn-Taking Model (LiveKit `turn-detector`, replacing the debounce/filler heuristics, plus a kept-and-extended backchannel mechanism)

Decided directly (2026-08-27), after three hand-rolled heuristics landed in quick succession for the same underlying problem class — `voiceUtteranceMinSpeechFrames` debounce, `voiceFillerWords` transcript filtering, and an about-to-be-built backchannel word list — and the question was asked plainly: is there an industry/research-grade approach instead of an accumulating pile of special cases? There is: **turn-taking / end-of-turn detection** is a real, decades-old research area (spoken dialogue systems), with active current work (Voice Activity Projection / VAP — turn-shift, backchannel, and filled-pause prediction as one model) and real, maintained open implementations from production voice-AI frameworks (LiveKit's `turn-detector`, Pipecat's `smart-turn`).

**Model chosen: LiveKit `turn-detector`, the audio-native `v1-mini` variant** — not the deprecated text-based model (built on something its own maintainer is moving away from defeats the point of choosing a maintained solution), and not the more accurate `v1` (served on LiveKit's own hosted cloud inference, not self-hostable — breaks this project's consistent self-hosting-on-nighthawk-pc discipline, held everywhere else: Whisper, Kokoro, WhisperLive, Silero). `v1-mini` runs CPU-only, ONNX, locally — no new GPU contention, a real plus given the GPU is already shared across Whisper/Kokoro/WhisperLive/Ollama. License is LiveKit's own custom "Model License," not standard OSS — real terms not independently verified in this doc; the user is handling that directly, not a blocker on implementation.

**Real verification against real audio, before any code was wired in (2026-08-27)** — the same "verify the actual model, not just shape-check it" discipline Silero VAD went through: four macOS `say`-synthesized clips (a complete sentence, a deliberately trailed-off sentence, a lone backchannel "Yeah", a lone filler "Um") run through the real `livekit-local-inference` package's `EOT.predict()`, no cloud call, no LiveKit account. Results against the model's own real, calibrated English threshold (0.36, from LiveKit's actual `languages.py` source, not invented here):

| Clip | Probability | vs. 0.36 threshold |
|---|---|---|
| Complete sentence | 0.392 | above — correctly "done" |
| Trailed-off sentence | 0.274 | below — correctly "not done" |
| Lone backchannel ("Yeah") | 0.119 | below — correctly "not done" |
| Lone filler ("Um") | 0.047 | below — correctly "not done" |

All four land on the correct side of the threshold — the model already discriminates these real, live categories correctly before any project-specific tuning. The full gRPC wire round-trip (real Python sidecar process, real client) was verified separately and returned byte-for-byte-identical probabilities to the in-process test, confirming the protocol adds nothing incorrect.

**Honest mapping against the three problems that motivated this** — not all three were solved by the model alone:
- Noise/debounce (brief VAD misfires): **unaffected, as expected** — a different layer (raw speech-presence robustness), Silero VAD's own job; `voiceUtteranceMinSpeechFrames` is untouched.
- Filler-only transcripts ("um"): **the model itself defers rather than finalizes** (0.047, far below threshold) — `voiceFillerWords`/`isFillerOnly` (`voice_filler.go`) stays wired in ahead of it anyway as a cheap deterministic backstop, same defense-in-depth posture as the emoji/markdown sanitizer.
- Backchannel during active bot playback ("yeah" said while the bot is talking): **confirmed, not just suspected, that the model alone does not solve this** — LiveKit's own `languages.py` source states directly that the local mini model produces no backchannel probability (that scoring is cloud/`v1`-only); a lone "Yeah" scoring 0.119 says "utterance not finished," not "this was a backchannel" — those are different questions, and only the latter is what actually matters here. Per the explicit instruction to keep this handled: a new deterministic, **context-gated** backchannel mechanism was built alongside the model rather than dropped (`voice_backchannel.go`, below) — this is the one piece that stays a heuristic on purpose, because the chosen model has no signal for it at all, not because a research-grade answer was skipped.

**What actually changed in `discord_voice.go`**: `voiceUtteranceSilenceFrames`' fixed 700ms countdown is now a hard fail-open *ceiling*, not the only mechanism. Once silence has lasted at least `voiceUtteranceEOTGraceFrames` (200ms, matching LiveKit's own real `MIN_SILENCE_DURATION_MS` reference constant), the capture loop calls the EOT sidecar every `voiceUtteranceEOTCheckIntervalFrames` frames (100ms) on the accumulated utterance's trailing audio; a probability at or above `eotThreshold` (0.36) flushes immediately, otherwise it keeps waiting up to the same 700ms ceiling as before. An EOT sidecar call failure logs once per utterance tail and falls back to the fixed timer for that decision — fail-*open*, deliberately the opposite posture from Silero VAD's own fail-loud teardown, since getting flush *timing* wrong is a much smaller cost than VAD misclassifying real speech as silence.

**The backchannel mechanism, built alongside it** (`voice_backchannel.go`, new): a separate word set from `voiceFillerWords` — real words ("yeah", "yep", "okay", "right", "sure", "mhm", …) that are meaningful in other contexts and must never be filtered unconditionally the way pure fillers are. `isBackchannelOnly` mirrors `isFillerOnly`'s exact strict-match structure. Gated on context, not vocabulary alone: `speakerBuffer` gained a `startedDuringPlayback bool`, captured once at the exact moment an utterance is confirmed (`bargeIn.isPlaying()` read at the debounce-promotion point, not at flush time — by flush time this utterance's own `signalSpeech()` has usually already preempted playback itself, which would make a flush-time check read false almost always regardless of what was true when the user actually started talking). `flush` drops the transcript (no turn dispatched, lifecycle reset to listening) only when both `startedDuringPlayback` and `isBackchannelOnly(text)` hold — the exact same word said while the bot was *not* playing still dispatches normally, since it's then a real one-word answer, not a backchannel. This directly closes the real bug that motivated all of this: the turn where the user said "Yeah." while the bot was mid-response and got back a completely empty assistant response.

**Architecture**: matches the existing Silero VAD sidecar exactly, extended rather than duplicated — `eotsidecar.EOT` (`proto/eot_sidecar.proto`) is a second gRPC service registered on the *same* `vad-sidecar` process/port that already serves `vadsidecar.VAD` (same pod, same container, zero new resource footprint), reusing `VAD_SIDECAR_URL`/`vadSidecarURL()` directly rather than a new env var or Helm value, since there is only one real dial target now serving both services. Go client: `workflows/cmd/gateway/voice_eot.go` (`eotClient`, one shared instance per connection — every `Predict` call is a fresh, independent classification with no per-speaker state to protect, unlike the VAD client). Python side: `vad_sidecar/eot_model.py` wraps `livekit.local_inference.EOT` behind a lock (no documented concurrent-call safety, unlike Silero's onnxruntime session), `vad_sidecar/server.py` registers `EOTServicer` alongside the existing `VADServicer` and reports `grpc.health.v1` `SERVING` for both service names plus the overall server.

**Verified**: `go build`/`go vet`/`gofmt` clean on the whole `workflows` module; the Python sidecar installs cleanly (`livekit-local-inference` added to `pyproject.toml`), boots both models, and serves both services with correct health-check responses. Not yet exercised against a real live Discord voice channel with a real bot and real interruption timing — same category of gap the rest of this pipeline has (see "Core pipeline built" below); the four-clip table above is real-model verification, not a live-conversation test.

### Open Questions / To Design

- **VAD / turn-taking threshold tuning** — first real tuning pass done 2026-08-29 against live conversation reports (see Notes Log): `voiceUtteranceSilenceFrames` 35→70, `voiceUtteranceEOTGraceFrames` 10→25, `voiceUtteranceMinSpeechFrames` 13→18, `eotThreshold` 0.36→0.40, all toward patience, all still "generous starting point, tune down against real usage." Structural point surfaced by that pass and still open: the EOT model as wired can only end an utterance *earlier* than `voiceUtteranceSilenceFrames`' ceiling, never extend the wait — so that ceiling, not the model, is the actual patience budget. The algorithm choices themselves (Silero VAD, LiveKit turn-detector) are resolved above; this item is now purely the numbers.
- **Silero VAD — built and verified (2026-08-25).** A Go-native binding (`github.com/yalue/onnxruntime_go`, cgo + runtime `dlopen`) is technically workable but was set aside: it needs the real ONNX Runtime shared library vendored into the image (~50-100MB, not a standard package) and the actual Silero model weights, with zero ability in this environment to verify inference correctness against real audio — deferred rather than built with unverifiable confidence, matching the reasoning that chose `energyVAD` first. Revisited directly afterward with a narrower question — "would Python help just for this?" — and yes: Python has first-class Silero support (the reference implementation, no cgo, no vendored runtime), but that doesn't justify moving Gateway itself to Python (a full Media Plane rewrite — `discordgo`, cgo `libopus`, embedded Temporal workers — for one algorithm). The resolution is a small Python sidecar Gateway calls into, keeping Gateway in Go — and once Python was in play, the "unverifiable in this environment" blocker that shelved the Go route dissolved entirely: `pip install onnxruntime silero-vad` just works, no vendoring, so this was actually built and tested against the real model rather than left as design-only.
  *`*vad-sidecar/`** (new top-level Python package, mirroring `activities/`'s layout): `vad_sidecar/model.py` reimplements Silero's real ONNX I/O contract directly against the raw `onnxruntime.InferenceSession` (bypassing `silero_vad`'s own `OnnxWrapper`, which holds state as hidden instance attributes — exactly wrong for a stateless-over-the-wire service) — verified inputs/outputs by inspecting the bundled model's real session (`input` `[1, 64+512]` float32 = a 64-sample rolling context prepended to each 512-sample/32ms window, `state` `[2,1,128]` float32, `sr` int64; outputs `output` (probability) and `stateN`).
  **Protocol: gRPC**, per `proto/vad_sidecar.proto` (`VAD.Classify`, frame/state/context as raw `bytes` — packed float32, not `repeated float`, to avoid per-element tag overhead on a call made ~50x/sec per speaker) — the initial pass here had shipped plain HTTP+JSON first (this project had no protoc toolchain, and reasoned the toolchain cost didn't pay for a same-pod/unary/~2KB call), but reconsidered directly and switched: `protoc` (Homebrew) plus `protoc-gen-go`/`protoc-gen-go-grpc` (`go install`) turned out to be a one-time, ordinary dev-tool install, not a standing complexity tax, and a typed, versioned `.proto` contract shared by both languages is worth that one-time cost. Health-checking uses the **standard `grpc.health.v1` protocol** (`grpcio-health-checking` on the server, `google.golang.org/grpc/health/grpc_health_v1` on the client) rather than a bespoke endpoint — resolves the "not yet designed: health-check mechanism" question below with the idiomatic answer instead of a custom one. Go stubs generated into `workflows/internal/vadpb/`, Python stubs into `vad_sidecar/pb/` (both committed — regenerating needs `protoc`/`grpc_tools`, which the Docker build stages deliberately don't carry).
