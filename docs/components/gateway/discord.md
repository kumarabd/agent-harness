# Gateway: Discord
## (Connection-Based, Guild + DM Chat)

> STATUS: IN PROGRESS — connected to a real Discord bot/server as of 2026-08-25: connection lease acquire, ingestion, ambient buffering, and mention-triggered turn dispatch all confirmed live against a real message. Outbound delivery (the piece confirmed broken earlier the same day — see Notes Log) is now built: `DiscordDeliver` (`workflows/cmd/gateway/deliver_discord.go`), the Gateway's embedded per-connection Temporal worker, `gateway_connection_leases` widened to `(platform, connection_id)` (migration `005_delivery_routing.sql`), and the turn workflow's task-queue routing (`turn.go`) — Go build/vet/gofmt clean, **not yet verified against a real Discord send** (needs an image rebuild/redeploy first). Session/channel model, response scope, ambient-message handling, the connection lease, and genesis context injection (LCM-copy) are all real and built. Several concrete numeric/format decisions remain open — see Open Questions.

### Role (one line)
The first *connection-based* Gateway platform (`../gateway.md`'s other category, alongside Web's webhook-like/polling one) — a Discord bot that ingests everything said in channels it's added to, but only actually runs the agent when addressed.

### Why this doc exists separately from `gateway.md`
Same reasoning as `gateway/web.md`: each gateway kind talks to its client completely differently (a live Discord Gateway websocket looks nothing like a browser polling HTTP), but both terminate the same way downstream — `SignalWithStart`, the same `MessageEvent`/`ingested_messages`/`sessions` contract. What's genuinely new here, though, isn't really Discord-specific either: planning this platform is what drove `../gateway.md`'s multi-session-channel mechanism (`Discriminator`, `ParentSessionKey`, `parent_session_key`) into existence at all — that mechanism lives in the shared doc since any platform with reply/thread semantics would need it identically. This doc owns only what's actually Discord-specific: how ambient ingestion works, how a Discord reply resolves to a discriminator, auth, and the connection model.

### Resolved: Response Scope — Ingest Everything, Respond Only When Addressed
**Rejected**: responding to every message in a configured channel (wrong for a channel with multiple humans talking to each other, not just to the bot) and "only process messages that mention/reply to the bot" in the stricter sense of *ignoring* everything else (loses context — by the time someone finally mentions the bot, it would have no idea what the preceding conversation was about).

**Resolved instead**: every message in a channel the bot is in gets ingested continuously; only a message that @mentions the bot or replies to one of its own messages actually triggers a real turn (`ModelCall`, a reply). Ambient (non-triggering) messages never reach the Coordinator/Temporal at all — see "Resolved: Ambient Message Buffer" below for why, and `../gateway.md`'s "Resolved: Multi-Session Channels" for how they still end up as usable context once something does trigger.

### Resolved: Ambient Message Buffer — Postgres Inserts, No Temporal Involvement
**Considered and rejected**: making every ambient message its own inert turn (a `turns`/`messages` row, no `ModelCall` ever called) — reuses existing turn/message infra untouched, but creates a real Temporal child workflow per message, expensive in a busy channel where most messages never get a reply. Worse, it would require teaching `coordinator.go`'s existing interrupt-forwarding logic (any signal while a turn is active gets forwarded into it as an interrupt) to distinguish triggering from ambient signals — real, risky surgery on working, already-verified code, since today *any* new signal while a turn is running is treated as "the user is redirecting me." Left as-is: an ambient message from an unrelated user must never interrupt an in-flight response to someone else's mention.

**Considered and rejected**: fetching recent channel history from Discord's own REST API on demand, at the moment a mention triggers a turn, instead of storing anything ourselves. Cheapest option, zero new state — but ambient chatter never lands in our own Postgres, so it's invisible to agent-brain's memory/consolidation pipeline and anything else that reads `messages` later.

**Resolved**: a dedicated table, pure `INSERT`s from the Gateway process directly — no `SignalWithStart`, no Coordinator, no Temporal workflow of any kind for an ambient message:

```sql
CREATE TABLE discord_ambient_messages (
  id                            bigserial PRIMARY KEY,
  channel_id                    text NOT NULL,
  platform_message_id           text NOT NULL,
  reply_to_platform_message_id  text,          -- Discord's own message_reference, when present
  author                        text NOT NULL, -- MessageEvent.User equivalent
  content                       text NOT NULL,
  created_at                    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ON discord_ambient_messages (channel_id, platform_message_id);
CREATE INDEX ON discord_ambient_messages (channel_id, created_at);
```
Dedup (`UNIQUE (channel_id, platform_message_id)`) is the same "real constraint, not app logic" pattern `ingested_messages` already uses. This table is genuinely Discord-specific (not promoted to `../gateway.md`) because the mechanism it supports — "ingest ambiently, trigger selectively" — isn't something every platform needs; Web has no ambient-chatter concept at all.

**Reply resolution reads this table**: given a triggering message with `reply_to_platform_message_id` set, walk that chain backward through `discord_ambient_messages` (falling back to `null`/chain-terminates if a link isn't found — aged out, pruned, or predates the bot joining) until reaching a message with no `reply_to_platform_message_id` of its own — that root's `platform_message_id` becomes `MessageEvent.Discriminator`'s `<id>` (`reply_to_platform_message_id:{rootID}`). This is the Discord-specific *policy* `../gateway.md`'s "Resolved: Multi-Session Channels" describes generically — root-collapse, not immediate-parent — meaning Discord sessions form a flat two-level tree (one main channel session, several flat sibling reply-sessions), and need no reverse message-id→session lookup to compute.

**A genuine Discord Thread** (the platform's own sub-channel feature, distinct from a lightweight reply) needs no special handling here at all — it has its own native `channel_id`, so it's simply a different `MessageEvent.ChannelID`, with its own independent main session and its own ambient buffer. Falls out of the existing per-channel model for free.

### Resolved: Auth — Bot Token(s), Not OAuth Install Flow
One or more bot tokens per tenant (Discord Developer Portal) — a tenant can run more than one Discord bot (e.g. invited to different servers for different purposes), so `gateway.discord` is a list of tokens, not a single value. Currently deployed shape is still the single flat `gateway.discord.botToken` string from before this was designed for multi-bot — widening it to a list is real, unbuilt Helm work, tracked in `../gateway.md`'s own Notes Log alongside the rest of the addressing mechanism it's needed for.

Each configured token is stored the same way `gateway.web.clerkIssuer`/`llm.tiers.<tier>.apiKey` are — a per-tenant Helm value (not a Kubernetes Secret if the token is the only credential and a bot token is already scoped to exactly the servers it's manually invited to — worth confirming against how sensitive this token actually is before finalizing, see Open Questions).

Each token's own **Discord user id** (not anything invented in config) is resolved once at startup via a plain REST call — `GET /users/@me` (`discordgo`: `session.User("@me")`) — before that connection's lease is ever acquired. This becomes `connection_id` in `../gateway.md`'s "Resolved: Outbound Flow"/"Resolved: Connection Leasing": what `gateway_connection_leases` is keyed on, and what the delivery task queue (`deliver:discord:{connection_id}`) is addressed by — the mechanism that lets multiple Discord bots (or one bot across reconnects/replica handoffs) route replies correctly without ambiguity. Reuses an id already read elsewhere for a different purpose: the same `session.State.User.ID` `discordMentionsUser` checks for mention detection.

**Not building a public "Add to Server" OAuth installer flow** — this is a personal/small-tenant deployment model (`multi-tenancy.md`), not a public multi-server bot product; the tenant's own operator invites each bot to their own server(s) manually, same trust model as everything else in this cluster.

### Resolved: Session Scope — Per-Channel Main Session, Reply-Threaded Child Sessions
Directly `../gateway.md`'s "Resolved: Multi-Session Channels" applied: `ChannelID` = the Discord channel ID (guild text channel or DM channel); `Discriminator` = `channel:{channelID}` for the main session, `reply_to_platform_message_id:{rootID}` for a reply-threaded one; `ParentSessionKey` for any reply-threaded session is always that channel's own main session (root-collapse policy, see above — never a deeper chain for Discord). Session key format: `agent:main:discord:channel:{channelID}` (main) / `agent:main:discord:channel:{channelID}:thread:{rootID}` (reply-threaded) — no backward-compatibility constraint the way Web has, so the discriminator shows up directly in the key.

### Resolved: DMs
A DM channel is just another `ChannelID` — no special-casing needed for session/channel scoping. `User` and `ChannelID` end up equal for a DM (mirroring Web's own shape closely, since a DM is inherently 1:1), but nothing in the design assumes that — it falls out naturally rather than being hardcoded.

**Trigger detection is different, though** (added 2026-08-25, this section originally only covered scoping): "Resolved: Response Scope"'s mention/reply gate exists specifically because a guild channel can have other humans talking to each other, not just to the bot — a personal (1:1) DM has no such ambiguity, so requiring an explicit mention there is pure friction with no upside. Every message in a personal DM is treated as an implicit trigger. A **group DM** still requires the normal mention/reply gate — more than one human reintroduces the exact ambiguity the gate exists for, same as a guild channel. Distinguishing the two needs one extra check beyond `GuildID` (empty for both kinds of DM): `discordgo.ChannelTypeDM` vs `discordgo.ChannelTypeGroupDM`, resolved via `isPersonalDM` (state cache first, REST fallback).

### Open Questions / To Design
- **Library and connection model** — `discordgo` (`github.com/bwmarrin/discordgo`, actively maintained, v0.29.0 latest) is the natural choice, not yet confirmed against `../gateway.md`'s connection-lease design (`gateway_connection_leases`) in real code — that table doesn't exist yet (no migration), and neither does the Go-side lease implementation `leases.py`'s pattern would need porting from.
- **Bot token sensitivity / Secret vs. plain value** — stated above as "worth confirming," not actually resolved. A leaked bot token lets someone impersonate the bot in every server it's in; lean toward a Secret (matching the pattern before the Clerk-secret-key mistake this session already made and reverted once) rather than assuming it's fine as a plain value the way `clerkIssuer` genuinely is.
- **Ambient buffer window size / retention** — how many messages or how much time counts as "recent general context" for a plain-mention (non-reply) trigger, and when/whether old rows get pruned. Same numeric-tuning discipline as everything else in this project — deliberately not sized here.
- **Reply-chain walk depth bound** — root-collapse could in principle walk a very long chain; needs a sane max-hops bound so a pathological reply chain doesn't become an unbounded query. Not sized.
- **LCM-copy vs. ambient-fallback threshold specifics** — `../gateway.md` resolves the mechanism (copy LCM if the parent has real turn history, fall back to the ambient buffer if not); the exact blending of "ambient since the parent's last real turn" alongside a copied LCM snapshot is explicitly left open there too.
- **Discord's 2000-character message limit** — how a long agent reply gets delivered (split into multiple messages, truncated, or something else). Not discussed yet.
- **Rate limiting** — Discord's own API rate limits, not addressed at all yet.
- **Attachments/stickers as real triggering content — still planned, deliberately not built.** Out of scope for a first pass, matching Web's own text-only scope. The intent, stated directly: these should eventually be able to trigger a real turn with actual content for the model to respond to, not be silently dropped and not fire a turn with blank content either (today's accepted-but-unaddressed gap). Rough shape for whenever this gets built, kept here as a forward-pointer rather than designed now: (1) **attachments** — pass the Discord CDN URL + filename + content-type into `MessageEvent.Content` (or a structured extension of it) rather than fetching/embedding bytes at the Gateway; whether the model can already dereference the URL itself (a `web_fetch`-shaped tool) or needs the Gateway to pre-fetch small/image attachments is undecided; (2) **stickers** — `m.StickerItems` carries a name/id even with no text content; the cheap first cut is just passing the sticker name through as if it were said text ("sticker: thumbsup"-shaped), no image understanding required. The third item this bullet used to bundle — voice-message attachments — is now built; see "Resolved: Voice-Message Attachments Transcribed" below.
- **Slash command routing** (`/approve`, `/deny`, `/stop`) — still genuinely unresolved, `../gateway.md`'s own long-standing open item, unchanged by anything resolved in this doc.
- **Multi-bot Helm config** — the mechanism (widened lease table, `connection_id`-addressed delivery) now supports more than one Discord bot per tenant; `gateway.discord` is still a single flat `botToken` value in the actual Helm chart, not yet a list. Real, scoped work when a tenant actually needs a second bot, not before.
- **Voice-message attachment failure has no ambient fallback** — a transcription failure still drops the message from `discord_ambient_messages` entirely (no text to record). What changed 2026-08-30 ("Resolved: Per-Channel Reply Mode"): if the message was a real trigger, the user now gets a "couldn't make that out" reply instead of silence. The ambient-row gap itself is unrevisited.
- **Voice-message download/transcribe runs synchronously inside `discordMessageCreate`**, unlike the ack-reaction goroutine right below it in the same handler — a real, accepted latency cost (bounded by `discordVoiceMessageFetchTimeout`, raised to 60s on 2026-08-30) on discordgo's own synchronous event-dispatch path, not yet moved off it. See "Resolved: Voice-Message Attachments Transcribed" below for why this was accepted rather than deferred to a Temporal activity.
- **Voice reply waveform is a static placeholder** — `sendDiscordVoiceMessage` doesn't decode the Ogg/Opus to compute a real amplitude envelope (would need an Ogg demuxer + Opus decoder in the delivery path). Discord renders the placeholder fine; a real waveform is polish, not correctness.
- **Streaming still runs for voice-mode channels** — `turn.go`'s `streamingEligible` gate is platform-only, so a voice-mode Discord channel still generates and signals per-sentence chunks that `DiscordDeliverChunk` then no-ops. Harmless (a segmenter pass + a DB read per chunk), but wasteful; a real gate needs channel-setting knowledge in shared workflow code.

### Resolved: Reply-Chain Resolution Through the Bot's Own Messages
**Built 2026-08-27**, closing a real gap `resolveDiscordThreadRoot`'s own doc comment had flagged since 2026-08-25: the bot's own sent/edited messages had no row in `discord_ambient_messages` at all — `discordMessageCreate` returns immediately for any `m.Author.Bot` message (before any insert), and `deliver_discord.go`'s `Deliver`/`DeliverChunk` never wrote one either. So when a human replied to *the bot's own earlier answer* to continue a thread, `resolveDiscordThreadRoot` hit `pgx.ErrNoRows` on the very first hop and returned `("", nil)` — "unresolvable" — which silently fell back to the **main channel session**, discarding whatever reply-scoped thread the conversation was actually in. No error, no crash, just quiet context loss on exactly the round where a human continues a thread by replying to the bot.

Fixed without a new column: a Discord thread session's `session_key` already durably encodes its own root (`sessionKeyFor`'s real format, `agent:main:discord:channel:{id}:thread:{rootID}`) — `auth.go`'s new `discordThreadRootFromSessionKey` is that format parsed back out (`""` for the main channel session, which has no thread suffix and thus nothing to be a reply to). `deliver_discord.go`'s new `recordAmbientBotMessage` inserts (or updates, on a streamed edit) a `discord_ambient_messages` row for the bot's own message, with `reply_to_platform_message_id` set from that parsed root — called after `Deliver`'s real `ChannelMessageSend`, and at both branches of `DeliverChunk` (message creation *and* every later edit, so the ambient mirror's `content` stays current through a streamed response, not stuck on the first chunk). Both call sites needed `s.session_key` added to their existing `turns JOIN sessions` query — a column that query wasn't previously selecting.

**`ON CONFLICT (channel_id, platform_message_id) DO UPDATE SET content = EXCLUDED.content`, deliberately different from `discordMessageCreate`'s own `DO NOTHING`**: a human message's content is fixed the instant it's sent, but a streamed bot message's content genuinely changes across `DeliverChunk`'s edit-in-place calls — `DO UPDATE` keeps the mirror row's content matching the latest edit rather than freezing it at the first chunk.

**Failure handling, deliberately asymmetric from the inbound side**: `recordAmbientBotMessage` is best-effort — logs and continues rather than returning an error, because by the time it's called the real Discord send has already succeeded; turning a mirror-write failure into an activity error would make Temporal retry the whole `Deliver`/`DeliverChunk` call and **resend a duplicate message to the channel**, a real regression far worse than one missed ambient row.

**Verified two ways, not assumed from code review**: a pure unit test round-tripping `discordThreadRootFromSessionKey` against both hand-written keys and `sessionKeyFor`'s own real output (main-channel → `""`, thread-scoped → the embedded root) — passed first run, deleted after. Separately, the actual SQL — the literal `INSERT ... ON CONFLICT DO UPDATE` and `resolveDiscordThreadRoot`'s own read query — run directly against the real `abishekk` tenant Postgres inside a `BEGIN`/`ROLLBACK` (no data left behind): confirmed one row survives two writes with the second write's content winning, and confirmed `resolveDiscordThreadRoot`'s exact two-hop walk (bot message → its now-real `reply_to_platform_message_id` → the human root's own `NULL`) resolves correctly end to end. `go build`/`go vet`/`gofmt` clean on the whole `workflows` module. **Not yet verified against a real live Discord reply** — needs an image rebuild/redeploy and an actual human reply-to-the-bot's-message to confirm in practice, same category of gap as every other Gateway feature in this doc before its first live test.

### Resolved: Voice-Message Attachments Transcribed
**Built 2026-08-27**, closing the third (and first-built) item of the "Attachments/stickers/audio as real triggering content" plan above. Discord's own voice-message feature (`MessageFlagsIsVoiceMessage`) always sends an empty `m.Content` — the real content only exists as an attached Ogg/Opus clip — so a voice-message `MessageCreate` was previously either silently dropped (once "Resolved: Non-Content `MessageCreate` Events" below is read backwards — no, actually unaffected by that filter, `MessageTypeDefault` covers it) or fired a turn/ambient row with nothing in it.

`discord_voice_message.go` (new): `discordVoiceMessageContent` downloads the message's first attachment (a plain `GET` against Discord's own CDN URL, size-capped at `discordVoiceMessageMaxBytes` = 25MB — matching Whisper's own commonly-documented upload limit, mirroring `tools.py`'s flat truncation safety-cap discipline) and transcribes it via a generalized `transcribeAudioFile` (`voice_stt_tts.go`, `transcribeAudio` reduced to a one-line wrapper around it) — the exact same OpenAI-compatible `/v1/audio/transcriptions` contract `gateway/discord-voice.md` already established, reusing infrastructure rather than inventing a second transcription path. The one real addition `transcribeAudio` itself couldn't express: it always uploaded as `"audio.wav"`, but whisper-svc picks its decode path from the uploaded filename's own extension — a real Ogg/Opus attachment needs its real filename (or a `.ogg` fallback if Discord ever omits one) passed through, not a hardcoded WAV name.

Wired into `discordMessageCreate` (`discord.go`): resolves `content` (transcript if `MessageFlagsIsVoiceMessage` is set, `m.Content` otherwise) once, right after `ctx` is created, before the ambient-message insert and before the `MessageEvent` is built — every downstream use of "this message's content" (ambient buffer, `MessageEvent.Content`) reads the resolved value, not `m.Content` directly, so a voice message now looks exactly like a real text message to everything past this one point.

**Correction, caught by direct question rather than assumed correct the first time: reuses the STT stage only, not the full live pipeline's post-transcription filtering — now fixed to reuse the part that matters.** The first version passed a raw Whisper transcript straight through as `content` with no normalization at all, unlike `discord_voice.go`'s own `flush`, which runs a live utterance's transcript through `isFillerOnly` (drop a pure "um"/"uh") and `isBackchannelOnly` (drop "yeah" said mid-bot-response) before ever building a `MessageEvent`. Revised: `discordMessageCreate` now applies the same `isFillerOnly` check (and an explicit empty-transcript check — Whisper returning `""` for silence/nothing-intelligible) to a voice-message transcript, dropping the message entirely (logged, matching `discord_voice.go`'s own log-and-return-to-listening treatment) rather than recording an ambient row or firing a turn for content nobody actually said. **`isBackchannelOnly` deliberately does NOT apply here** — it's gated on the utterance having started while the bot was actively speaking over a live voice connection (`speakerBuffer.startedDuringPlayback`), a context that structurally doesn't exist for a voice note dropped into a text channel asynchronously; there's no notion of "the bot was mid-response" to backchannel against. VAD/debounce/EOT-model turn-taking likewise don't apply and were never in scope — a voice-message attachment is already a complete, human-chosen recording, not an unbounded live stream needing its own endpoint detection.

**Two real, accepted tradeoffs, named rather than hidden:**
- **A transcription failure drops the message entirely** (logged, no ambient row, no turn) — unlike a plain attachment or sticker, there's no meaningful placeholder text for spoken audio that failed to transcribe, so there's nothing better to fall back to.
- **The download+transcribe round trip runs synchronously inside the `discordMessageCreate` handler**, which discordgo dispatches synchronously off its own event loop — a real latency cost on every voice-message event, bounded by `discordVoiceMessageFetchTimeout` (30s, an unvalidated starting value like every other undecided interval in this project), not moved onto a Temporal activity the way the actual model-call/tool-call work already is. Accepted for this pass because moving it off-handler would mean either a new activity threading transcribed content back into `MessageEvent` before submission (real new machinery) or teaching the Gateway's already-fast "ack and submit" ingestion path to defer content resolution — bigger scope than "build out voice attachments" asked for. `discord_voice.go`'s own live-voice-channel capture loop already calls the same kind of STT client synchronously from its own goroutine, so this isn't a new pattern in this codebase, just applied at a new call site.

Verified with three real, throwaway `httptest`-backed tests (deleted after passing, per this project's own convention): a full round trip through two local HTTP servers standing in for Discord's CDN and the STT service (confirmed the real uploaded bytes and the real filename — `voice-message.ogg`, not `audio.wav` — reach the multipart request, and the real transcript comes back); the non-voice-message short-circuit (zero network calls when `MessageFlagsIsVoiceMessage` isn't set); and the size cap actually rejecting an oversized payload before it ever reaches the STT endpoint. `go build`/`go vet`/`gofmt` clean on the whole `workflows` module. **Not yet verified against a real Discord voice-message attachment** — same category of gap as every other Gateway feature in this doc before its first live test.

### Resolved: Non-Content `MessageCreate` Events Are Filtered by Type
**Built 2026-08-27**, closing a real, observed gap (2026-08-26): `discordMessageCreate` (`discord.go`) checked `m.Author.Bot` but never `m.Type`. In a personal DM specifically, every message is an implicit trigger (no mention needed, by design — "Resolved: DMs"), which also meant a Discord-*generated* message landing in that same DM (an "app added, here's how to get started" card, a call notification, etc.) sailed through and triggered a real turn — confirmed live: inviting the bot kicked off an unnecessary `ModelCall` for content that was never a human saying something.

Fixed narrowly, without touching the mention/DM-gate design at all: `discordMessageCreate` now returns immediately, before the ambient-message insert, unless `m.Type` is `discordgo.MessageTypeDefault` or `discordgo.MessageTypeReply` — the only two types that represent genuine human conversational content. A filtered event leaves no trace at all (not even an ambient-buffer row), matching the fix note's original intent exactly. `go build`/`go vet`/`gofmt` clean on the whole `workflows` module. **Not yet verified live** — needs a real Discord event of a filtered type (a call notification, an app-added card, etc.) actually arriving against a deployed bot to confirm it's dropped in practice, not just by code inspection.

The related, lower-priority case noticed alongside this one — a message with empty text but only an attachment/sticker/embed still firing a turn with nothing for the model to meaningfully respond to — is deliberately **not** fixed by narrowing this filter further (dropping those would contradict the actual intent, see the Open Questions item on attachments/stickers/audio below: these should eventually produce a real, content-bearing turn, not be silently dropped). Left as-is for now.

### Resolved: Per-Channel Reply Mode (`/mode`) + voice-message-failure feedback

**Built 2026-08-30.** Two related pieces, from "when I send an audio recording in a DM it doesn't respond, and I want it to reply with text or voice."

**Reply mode.** `/mode reply:voice|text` (a new global slash command, registered alongside `/join`/`/leave` in `registerVoiceCommands` even though it isn't voice-channel-specific) sets a per-channel reply mode, stored in `discord_reply_mode` (`channel_id` PK, `mode`, `updated_at` — `012_discord_reply_mode.sql`). Absent row = `text`, i.e. no behavior change for any channel that never runs the command. Gateway-owned like every other gateway-observed fact: `handleModeCommand` (`discord_reply_mode.go`) writes it, `DiscordDeliver`/`DiscordDeliverChunk` read it via `discordReplyMode(ctx, pool, channelID)` (which fails closed to `text` on any read error — a text send always works, a voice send has TTS + a raw multipart upload that can each fail).

- **`DiscordDeliver`**, voice mode: `deliverVoiceReply` runs the final answer through `sanitizeForSpeech` (the same emoji/markdown backstop the live-voice path uses), synthesizes it to Ogg/Opus via `synthesizeSpeechOgg` (`/audio/speech`, `response_format: "opus"` — the container Discord's own voice messages use), and posts it as a **native** Discord voice message. discordgo's `MessageSend` can't express the `attachments`-with-`duration_secs`/`waveform` metadata Discord requires alongside the `IS_VOICE_MESSAGE` flag (8192), so `sendDiscordVoiceMessage` (`deliver_discord_voice_msg.go`) builds the multipart body by hand and posts it through `session.RequestRaw` (keeping discordgo's auth + rate-limit handling). Duration is read from the last Ogg page's granule position (48kHz for Opus); the waveform is a static placeholder (no Ogg demux + Opus decode wired into this path — Discord accepts any 1–256 bytes). **Any failure — TTS, upload, Discord rejecting the flag — falls through to the normal text send**, so the answer is never lost, just written instead of spoken.
- **`DiscordDeliverChunk`**, voice mode: returns early (marks the chunk sent, leaves `streamed_message_ref` unset) — a voice-mode channel gets one whole-turn voice message from `Deliver`, not a stream of per-sentence edits. Streaming still runs workflow-side (`turn.go` doesn't know channel settings); the chunk signals are just no-ops at the delivery end. A cleaner gate would need channel-setting knowledge in shared workflow code — not worth it.
- Audio the human sends is transcribed and answered regardless of mode; `/mode` only controls the bot's own reply.

**Voice-message-failure feedback.** The DM case that prompted this: a voice message whose transcription failed did a silent `return` with only a server-side log, so the user waited on a reply that never came. `discordMessageCreate` now computes trigger status (`mentioned`/`repliesToBot`/`personalDM`) *before* the transcription attempt, and on a failure — or an empty transcript — of a message that was actually addressed to the bot, posts a short "I couldn't make that out, try again?" instead of vanishing. A filler-only transcript ("um") still drops silently (it was understood, there's just nothing to answer). Also: `discordVoiceMessageContent`'s download now sends a `User-Agent` (Discord's CDN can 403 without one) and its error carries the CDN status + content-type + size; `discordVoiceMessageFetchTimeout` raised 30s → 60s (the transcribe leg shares a contended GPU). Root cause of the original failure is still unconfirmed (gateway logs weren't reachable) — the likeliest are the `.ogg`/Opus decode path through litellm→whisper-svc (new, never verified live) or the 30s timeout under GPU load; these changes make the next occurrence visible to the user and better-logged rather than silent.

`go build`/`go vet`/`gofmt` clean; throwaway tests covered `oggOpusDurationSecs`, the placeholder waveform's Discord range, and the multipart body shape (`payload_json` carrying `flags:8192` + attachments, `files[0]` part). **Not yet verified against a real Discord voice-message send or a real `/mode voice` reply** — same category of gap as every other feature in this doc before its first live test. Global slash-command registration can take up to ~1h to first appear.
