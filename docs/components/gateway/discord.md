# Gateway: Discord
## (Connection-Based, Guild + DM Chat)

> STATUS: IN PROGRESS — connected to a real Discord bot/server as of 2026-08-25: connection lease acquire, ingestion, ambient buffering, and mention-triggered turn dispatch all confirmed live against a real message. Outbound delivery (the piece confirmed broken earlier the same day — see Notes Log) is now built: `DiscordDeliver` (`workflows/cmd/gateway/deliver_discord.go`), the Gateway's embedded per-connection Temporal worker, `gateway_connection_leases` widened to `(platform, connection_id)` (migration `005_delivery_routing.sql`), and the turn workflow's task-queue routing (`turn.go`) — Go build/vet/gofmt clean, **not yet verified against a real Discord send** (needs an image rebuild/redeploy first). Session/channel model, response scope, ambient-message handling, the connection lease, and genesis context injection (LCM-copy) are all real and built. Several concrete numeric/format decisions remain open — see Open Questions.

### Role (one line)
The first *connection-based* Gateway platform (`../gateway.md`'s other category, alongside Web's webhook-like/polling one) — a Discord bot that ingests everything said in channels it's added to, but only actually runs the agent when addressed.

### Why this doc exists separately from `gateway.md`
Same reasoning as `gateway/web.md`: each gateway kind talks to its client completely differently (a live Discord Gateway websocket looks nothing like a browser polling HTTP), but both terminate the same way downstream — `SignalWithStart`, the same `MessageEvent`/`ingested_messages`/`sessions` contract. What's genuinely new here, though, isn't really Discord-specific either: planning this platform is what drove `../gateway.md`'s multi-session-channel mechanism (`Discriminator`, `ParentSessionKey`, `parent_session_key`) into existence at all — that mechanism lives in the shared doc since any platform with reply/thread semantics would need it identically. This doc owns only what's actually Discord-specific: how ambient ingestion works, how a Discord reply resolves to a discriminator, auth, and the connection model.

### Resolved: Response Scope — Ingest Everything, Respond Only When Addressed
**Rejected**: responding to every message in a configured channel (wrong for a channel with multiple humans talking to each other, not just to the bot) and "only process messages that mention/reply to the bot" in the stricter sense of *ignoring* everything else (loses context — by the time someone finally mentions the bot, it would have no idea what the preceding conversation was about).

**Resolved instead**: every message in a channel the bot is in gets ingested continuously; only a message that @mentions the bot or replies to one of its own messages actually triggers a real turn (`ModelCall`, a reply). Ambient (non-triggering) messages never reach the Coordinator/Temporal at all — see "Resolved: Ambient Message Buffer" below for why, and `../gateway.md`'s "Resolved: Multi-Session Channels" for how they still end up as usable context once something does trigger.

### Resolved: Ambient Message Buffer — Postgres Inserts, No Temporal Involvement
**Considered and rejected**: making every ambient message its own inert turn (a `turns`/`messages` row, no `ModelCall` ever called) — reuses existing turn/message infra untouched, but creates a real Temporal child workflow per message, expensive in a busy channel where most messages never get a reply. Worse, it would require teaching `coordinator.go`'s existing interrupt-forwarding logic (any signal while a turn is active gets forwarded into it as an interrupt) to distinguish triggering from ambient signals — real, risky surgery on working, already-verified code, since today *any* new signal while a turn is running is treated as "the user is redirecting me." Left as-is: an ambient message from an unrelated user must never interrupt an in-flight response to someone else's mention.

**Considered and rejected**: fetching recent channel history from Discord's own REST API on demand, at the moment a mention triggers a turn, instead of storing anything ourselves. Cheapest option, zero new state — but ambient chatter never lands in our own Postgres, so it's invisible to agent-brain's memory/consolidation pipeline and anything else that reads `messages` later.

**Resolved**: a dedicated table, pure `INSERT`s from the Gateway process directly — no `SignalWithStart`, no Coordinator, no Temporal workflow of any kind for an ambient message:

```sql
CREATE TABLE discord_ambient_messages (
  id                            bigserial PRIMARY KEY,
  channel_id                    text NOT NULL,
  platform_message_id           text NOT NULL,
  reply_to_platform_message_id  text,          -- Discord's own message_reference, when present
  author                        text NOT NULL, -- MessageEvent.User equivalent
  content                       text NOT NULL,
  created_at                    timestamptz NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX ON discord_ambient_messages (channel_id, platform_message_id);
CREATE INDEX ON discord_ambient_messages (channel_id, created_at);
```
Dedup (`UNIQUE (channel_id, platform_message_id)`) is the same "real constraint, not app logic" pattern `ingested_messages` already uses. This table is genuinely Discord-specific (not promoted to `../gateway.md`) because the mechanism it supports — "ingest ambiently, trigger selectively" — isn't something every platform needs; Web has no ambient-chatter concept at all.

**Reply resolution reads this table**: given a triggering message with `reply_to_platform_message_id` set, walk that chain backward through `discord_ambient_messages` (falling back to `null`/chain-terminates if a link isn't found — aged out, pruned, or predates the bot joining) until reaching a message with no `reply_to_platform_message_id` of its own — that root's `platform_message_id` becomes `MessageEvent.Discriminator`'s `<id>` (`reply_to_platform_message_id:{rootID}`). This is the Discord-specific *policy* `../gateway.md`'s "Resolved: Multi-Session Channels" describes generically — root-collapse, not immediate-parent — meaning Discord sessions form a flat two-level tree (one main channel session, several flat sibling reply-sessions), and need no reverse message-id→session lookup to compute.

**A genuine Discord Thread** (the platform's own sub-channel feature, distinct from a lightweight reply) needs no special handling here at all — it has its own native `channel_id`, so it's simply a different `MessageEvent.ChannelID`, with its own independent main session and its own ambient buffer. Falls out of the existing per-channel model for free.

### Resolved: Auth — Bot Token(s), Not OAuth Install Flow
One or more bot tokens per tenant (Discord Developer Portal) — a tenant can run more than one Discord bot (e.g. invited to different servers for different purposes), so `gateway.discord` is a list of tokens, not a single value. Currently deployed shape is still the single flat `gateway.discord.botToken` string from before this was designed for multi-bot — widening it to a list is real, unbuilt Helm work, tracked in `../gateway.md`'s own Notes Log alongside the rest of the addressing mechanism it's needed for.

Each configured token is stored the same way `gateway.web.clerkIssuer`/`llm.openai.apiKey` are — a per-tenant Helm value (not a Kubernetes Secret if the token is the only credential and a bot token is already scoped to exactly the servers it's manually invited to — worth confirming against how sensitive this token actually is before finalizing, see Open Questions).

Each token's own **Discord user id** (not anything invented in config) is resolved once at startup via a plain REST call — `GET /users/@me` (`discordgo`: `session.User("@me")`) — before that connection's lease is ever acquired. This becomes `connection_id` in `../gateway.md`'s "Resolved: Outbound Flow"/"Resolved: Connection Leasing": what `gateway_connection_leases` is keyed on, and what the delivery task queue (`deliver:discord:{connection_id}`) is addressed by — the mechanism that lets multiple Discord bots (or one bot across reconnects/replica handoffs) route replies correctly without ambiguity. Reuses an id already read elsewhere for a different purpose: the same `session.State.User.ID` `discordMentionsUser` checks for mention detection.

**Not building a public "Add to Server" OAuth installer flow** — this is a personal/small-tenant deployment model (`multi-tenancy.md`), not a public multi-server bot product; the tenant's own operator invites each bot to their own server(s) manually, same trust model as everything else in this cluster.

### Resolved: Session Scope — Per-Channel Main Session, Reply-Threaded Child Sessions
Directly `../gateway.md`'s "Resolved: Multi-Session Channels" applied: `ChannelID` = the Discord channel ID (guild text channel or DM channel); `Discriminator` = `channel:{channelID}` for the main session, `reply_to_platform_message_id:{rootID}` for a reply-threaded one; `ParentSessionKey` for any reply-threaded session is always that channel's own main session (root-collapse policy, see above — never a deeper chain for Discord). Session key format: `agent:main:discord:channel:{channelID}` (main) / `agent:main:discord:channel:{channelID}:thread:{rootID}` (reply-threaded) — no backward-compatibility constraint the way Web has, so the discriminator shows up directly in the key.

### Resolved: DMs
A DM channel is just another `ChannelID` — no special-casing needed for session/channel scoping. `User` and `ChannelID` end up equal for a DM (mirroring Web's own shape closely, since a DM is inherently 1:1), but nothing in the design assumes that — it falls out naturally rather than being hardcoded.

**Trigger detection is different, though** (added 2026-08-25, this section originally only covered scoping): "Resolved: Response Scope"'s mention/reply gate exists specifically because a guild channel can have other humans talking to each other, not just to the bot — a personal (1:1) DM has no such ambiguity, so requiring an explicit mention there is pure friction with no upside. Every message in a personal DM is treated as an implicit trigger. A **group DM** still requires the normal mention/reply gate — more than one human reintroduces the exact ambiguity the gate exists for, same as a guild channel. Distinguishing the two needs one extra check beyond `GuildID` (empty for both kinds of DM): `discordgo.ChannelTypeDM` vs `discordgo.ChannelTypeGroupDM`, resolved via `isPersonalDM` (state cache first, REST fallback).

### Open Questions / To Design
- **Library and connection model** — `discordgo` (`github.com/bwmarrin/discordgo`, actively maintained, v0.29.0 latest) is the natural choice, not yet confirmed against `../gateway.md`'s connection-lease design (`gateway_connection_leases`) in real code — that table doesn't exist yet (no migration), and neither does the Go-side lease implementation `leases.py`'s pattern would need porting from.
- **Bot token sensitivity / Secret vs. plain value** — stated above as "worth confirming," not actually resolved. A leaked bot token lets someone impersonate the bot in every server it's in; lean toward a Secret (matching the pattern before the Clerk-secret-key mistake this session already made and reverted once) rather than assuming it's fine as a plain value the way `clerkIssuer` genuinely is.
- **Ambient buffer window size / retention** — how many messages or how much time counts as "recent general context" for a plain-mention (non-reply) trigger, and when/whether old rows get pruned. Same numeric-tuning discipline as everything else in this project — deliberately not sized here.
- **Reply-chain walk depth bound** — root-collapse could in principle walk a very long chain; needs a sane max-hops bound so a pathological reply chain doesn't become an unbounded query. Not sized.
- **LCM-copy vs. ambient-fallback threshold specifics** — `../gateway.md` resolves the mechanism (copy LCM if the parent has real turn history, fall back to the ambient buffer if not); the exact blending of "ambient since the parent's last real turn" alongside a copied LCM snapshot is explicitly left open there too.
- **Discord's 2000-character message limit** — how a long agent reply gets delivered (split into multiple messages, truncated, or something else). Not discussed yet.
- **Rate limiting** — Discord's own API rate limits, not addressed at all yet.
- **Attachments/embeds** — out of scope for a first pass, matching Web's own text-only scope; not formally confirmed.
- **Slash command routing** (`/approve`, `/deny`, `/stop`) — still genuinely unresolved, `../gateway.md`'s own long-standing open item, unchanged by anything resolved in this doc.
- **Multi-bot Helm config** — the mechanism (widened lease table, `connection_id`-addressed delivery) now supports more than one Discord bot per tenant; `gateway.discord` is still a single flat `botToken` value in the actual Helm chart, not yet a list. Real, scoped work when a tenant actually needs a second bot, not before.
- **Discord-side reply-chain resolution past the bot's own messages** — `resolveDiscordThreadRoot`'s own doc comment: a reply to the bot's own earlier reply won't resolve correctly until the bot's outbound sends also land in `discord_ambient_messages`. `DiscordDeliver` (built 2026-08-25) doesn't do this yet.
- **Non-content `MessageCreate` events aren't filtered by type, only by author** — real, observed gap (2026-08-26): `discordMessageCreate` (`discord.go`) checks `m.Author.Bot` but never `m.Type`. In a personal DM specifically, every message is an implicit trigger (no mention needed, by design — "Resolved: DMs"), which also means a Discord-*generated* message landing in that same DM (an "app added, here's how to get started" card, a call notification, etc.) sails through and triggers a real turn — confirmed live: inviting the bot kicked off an unnecessary `ModelCall` for content that was never a human saying something. The fix is narrow and doesn't touch the mention/DM-gate design at all: filter on `m.Type` before anything else runs (`discordgo.MessageTypeDefault`/`MessageTypeReply` are the only two types that represent genuine human conversational content; drop everything else before it even reaches `discord_ambient_messages`). Related, lower-priority case noticed at the same time: a message with empty content but only an attachment/sticker/embed still fires a real turn today with nothing for the model to meaningfully respond to — worth the same pass, not filed separately. Not built yet — deliberately deferred as a future item, not urgent enough to interrupt current work for.
