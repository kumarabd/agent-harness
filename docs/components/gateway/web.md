### Role (one line)
The first real Gateway platform, and the first real inbound path into agent-harness at all — until this exists, `starter` (`workflows/cmd/starter`) is the only way to submit a message. Backs a new chat page in `agent-web` (currently a memory-explorer UI for agent-brain, gaining a chat page here), not a third-party platform.

### Why this doc exists separately from `gateway.md`
Each gateway kind talks to its client completely differently (a browser polling an HTTP API looks nothing like a Discord websocket), but all of them terminate the same way downstream — `SignalWithStart` against the Session Coordinator, delivery via a deterministically-addressed Temporal activity, the same `ingested_messages`/`delivered_responses`/`gateway_shard_state` schema. `gateway.md` owns that shared contract; this doc owns everything upstream of it that's genuinely Web-specific.

### Resolved: Not a Third-Party Platform — A New Category
`gateway.md`'s existing split (connection-based vs. webhook-based) was designed around third-party platforms with their own redelivery/partitioning semantics (Discord's shards, WhatsApp's webhook retries). Neither fits: this is a first-party client, so there's no external redelivery to defend against — a client-generated message ID handles idempotent resends instead of a platform's own at-least-once guarantee. **Resolved as its own category, webhook-like for infrastructure purposes**: stateless `Deployment` (not `StatefulSet`), no shard concept, any replica serves any request — it just gets there because we control both ends, not because a platform's own protocol happens to be stateless.

### Resolved: Delivery — Short-Polling, Not a Live Connection
**Considered:** a live push connection (WebSocket/SSE) so a response appears the instant a turn completes. **Rejected**, because a browser landing on an arbitrary replica behind a load balancer has no deterministic formula for "which replica holds this connection" the way Discord's `guild_id % num_shards` does — making live push work would require building a new dynamic connection registry (e.g. Redis pub/sub, or a Postgres-backed registry translating "connection X" → "replica Y"), which is exactly the kind of extra coordination machinery this project has repeatedly chosen not to build when a simpler mechanism suffices (static StatefulSet shard identity over a dynamic lease table; task-queue routing over a message broker — both `gateway.md`).

**Resolved instead: the browser short-polls an HTTP endpoint.** Any replica can serve any poll request — same statelessness as the webhook-like inbound path. Trade-off stated plainly: a small poll-interval delay instead of instant push. Exact poll interval not yet decided — see Open Questions.

**Separately, worth being explicit about:** this harness has no token-level streaming today regardless of transport — `ModelCall` returns one complete response per reasoning step, nothing streams through Temporal activities token-by-token. So even with a live push connection, a response would still appear all at once when the turn completes, not typed character-by-character. Polling doesn't cost anything relative to a live connection on this specific dimension; both would show the same "appears all at once" behavior. True streaming would be a separate, much bigger change to the `ModelCall`/turn-loop layer, not a Gateway concern.

**Real simplification this unlocks, found while designing the per-tenant deployment (`../gateway.md`)**: `gateway.md`'s general Outbound Flow (embedded Temporal worker, `DeliverActivity`, deterministic task-queue routing) exists to reach one *specific* live socket — a concern connection-based platforms genuinely have and Web genuinely doesn't. For a polling client, delivery mostly collapses: the moment a turn's content is written to `messages`/`turns` (already happening today, regardless of any Gateway), it's already there for the poll endpoint to read directly — no `DeliverActivity` dispatch, no embedded Temporal worker, no task-queue routing needed for Web at all. The poll endpoint is a plain Postgres read (`SELECT` new turns/messages for this session since the client's last-seen position), nothing Temporal-shaped about it. `gateway.md`'s general mechanism stays correct and necessary for a future connection-based platform; it just doesn't apply here.

`agent-web` already authenticates its existing memory-explorer pages via Clerk (`@clerk/clerk-react`). Reused directly for the chat page rather than introducing a second auth mechanism — same "reuse, don't reinvent" pattern this project applies everywhere else (the `LLM_PROVIDER_*`/`AGENT_BRAIN_*` credential-wiring convention — renamed from `PIONEER_*` on 2026-08-28 as part of completing the model-registry migration, see `../model-registry.md`; the LLM-key Secret pattern reused verbatim for agent-brain's own per-tenant auth). ### Resolved: One Continuous Session Per User — No Reset, No Threads
**Revised 2026-08-24 — see "Resolved: Multi-Session Support" below.** This section's reasoning is still exactly right for what it actually rejected: no *automatic*, arbitrary, cost-motivated resets. What changed is different in kind, not a reversal — once `../gateway.md`'s multi-session-channel mechanism existed for Discord's native reply-threading, generalizing it to Web too (a real, deliberate, user-initiated "branch from here" action, not a reset) turned out to be nearly free to support, since the mechanism itself already didn't assume Discord-only. The default/main session described below is completely unchanged — still one `session_key` per user, forever, no automatic reset — this is now just no longer the *only* session a user can have. Kept below for the historical reasoning (why "reset on timeout" specifically was wrong), which remains true.

**Explicitly not ChatGPT-style** (no user-initiated "new chat," no multiple conversations, no client-generated conversation ID). **Explicitly not time-boxed either** (an earlier direction considered introducing a separate, longer idle-reset threshold specifically for this platform, distinct from the Session Coordinator's own short-lived workflow-lifecycle `idleTTL` — reconsidered and dropped, see below). Landed on: **one `session_key` per user, forever** — `session_key = "agent:main:web:user:{clerk_user_id}"`, `channel_id = clerk_user_id`. Behaves like a single, permanent Discord channel: always available, message anytime, always continues where it left off. A Session Coordinator idling out and restarting (today's `idleTTL`, 30s locally / 5–15 min real design) is purely workflow-lifecycle — the same `session_key`'s Postgres history is untouched, and `context-slot.md`'s session-wide `assemble()` (built and verified earlier this session) already means a turn after a coordinator restart still has full context, not a blank slate.

**Why "reset into a new thread on timeout" was considered and dropped:** the original motivation was a real cost concern — wouldn't a session that never resets accumulate ever-more-frequent compactions and ever-growing token consumption compared to periodically starting fresh? Investigated directly rather than assumed, and it surfaced a real, separate bug: `lcm.py`'s summary-DAG folding only ever re-folded `kind='leaf'` rows, never `kind='condensed'` ones, so a long-running session's summary DAG really would have grown without bound over a long enough timeline (see `components/context-slot.md`'s 2026-08-23 Notes Log entry, "prompted by planning the Gateway's Web platform"). **Fixed at the root** (recursive condensed-of-condensed folding, live-verified) rather than worked around with periodic resets — a reset would have thrown away real conversational continuity to paper over a cost bug that had an actual fix. With that fixed, an always-on, never-resets session is genuinely cost-safe long-term — this is still exactly true; it's *why* nothing here ever resets automatically, unchanged by the multi-session support below.

### Resolved: Multi-Session Support — a Real, User-Initiated Branch, Not a Reset
`../gateway.md`'s "Resolved: Multi-Session Channels" mechanism, generalized to Web. `websession.go`:
- `webMainSessionID = "main"` — a stable, addressable sentinel for the default/user-initiated-branch-free session above, instead of relying on an implicit empty-string case. Internally still produces the exact unchanged `agent:main:web:user:{id}` session_key, byte-for-byte — the already-running real production session is untouched.
- `webDiscriminator(channelID, sessionID)` — empty or `"main"` → `"channel:{channelID}"` (the default session); anything else → `"session:{sessionID}"`, embedded directly into the key as `agent:main:web:user:{channelID}:session:{sessionID}`. Unlike Discord, Web has no platform-native reply/thread concept to deterministically derive a discriminator from — `sessionID` is simply whatever opaque value the client generated itself when the user branched, remembered and resent by the client on every later message for that session (no server-side lookup needed to resolve it, same property Discord's deterministic reply-chain root has, just sourced differently: client-generated instead of computed from platform data).
- `webSessionIDFromKey` — the reverse mapping, `GET /sessions`' own need.

**API surface**: `/send` gains `session_id`/`parent_session_id` (both optional; empty reproduces today's exact single-session behavior); `/poll` gains a `session_id` query param; `/respond` gains a `session_id` field; new `GET /sessions` lists this authenticated user's own sessions only (`WHERE platform='web' AND channel_id={their own Clerk user_id}` — never another user's). `parent_session_id` is only meaningful the first time a given `session_id` is sent — `submitMessageEvent`'s own genesis detection (`../gateway.md`) is what actually makes this take effect, so the client doesn't need to be careful about sending it exactly once.

`GET /skills` (2026-09-01) is unrelated to the session model — a flat read-only list of the agent's current procedures (`../skill-subsystem.md`), tenant-global (no per-user filter), for agent-web's `/skills` page.

**Genesis context injection**: built and live-verified — `../gateway.md`'s own Notes Log has the full detail (`SeedChildSessionContext` activity, `coordinator.go`'s own gating). Platform-agnostic, so a newly-branched Web session gets it exactly the same way a Discord thread-session does, no Web-specific code needed for this part at all.
