### Role (one line)
The first real Gateway platform, and the first real inbound path into agent-harness at all — until this exists, `starter` (`workflows/cmd/starter`) is the only way to submit a message. Backs a new chat page in `agent-web` (currently a memory-explorer UI for agent-brain, gaining a chat page here), not a third-party platform.

### Why this doc exists separately from `gateway.md`
Each gateway kind talks to its client completely differently (a browser polling an HTTP API looks nothing like a Discord websocket), but all of them terminate the same way downstream — `SignalWithStart` against the Session Coordinator, delivery via a deterministically-addressed Temporal activity, the same `ingested_messages`/`delivered_responses`/`gateway_shard_state` schema. `gateway.md` owns that shared contract; this doc owns everything upstream of it that's genuinely Web-specific.

### Resolved: Not a Third-Party Platform — A New Category
`gateway.md`'s existing split (connection-based vs. webhook-based) was designed around third-party platforms with their own redelivery/partitioning semantics (Discord's shards, WhatsApp's webhook retries). Neither fits: this is a first-party client, so there's no external redelivery to defend against — a client-generated message ID handles idempotent resends instead of a platform's own at-least-once guarantee. **Resolved as its own category, webhook-like for infrastructure purposes**: stateless `Deployment` (not `StatefulSet`), no shard concept, any replica serves any request — it just gets there because we control both ends, not because a platform's own protocol happens to be stateless.

### Legacy delivery decision — short-polling
**Considered:** a live push connection (WebSocket/SSE) so a response appears the instant a turn completes. **Rejected**, because a browser landing on an arbitrary replica behind a load balancer has no deterministic formula for "which replica holds this connection" the way Discord's `guild_id % num_shards` does — making live push work would require building a new dynamic connection registry (e.g. Redis pub/sub, or a Postgres-backed registry translating "connection X" → "replica Y"), which is exactly the kind of extra coordination machinery this project has repeatedly chosen not to build when a simpler mechanism suffices (static StatefulSet shard identity over a dynamic lease table; task-queue routing over a message broker — both `gateway.md`).

**Resolved instead: the browser short-polls an HTTP endpoint.** Any replica can serve any poll request — same statelessness as the webhook-like inbound path. Trade-off stated plainly: a small poll-interval delay instead of instant push. Exact poll interval not yet decided — see Open Questions.

**Separately, worth being explicit about:** this harness has no token-level streaming today regardless of transport — `ModelCall` returns one complete response per reasoning step, nothing streams through Temporal activities token-by-token. So even with a live push connection, a response would still appear all at once when the turn completes, not typed character-by-character. Polling doesn't cost anything relative to a live connection on this specific dimension; both would show the same "appears all at once" behavior. True streaming would be a separate, much bigger change to the `ModelCall`/turn-loop layer, not a Gateway concern.

**Real simplification this unlocks, found while designing the per-tenant deployment (`../gateway.md`)**: `gateway.md`'s general Outbound Flow (embedded Temporal worker, `DeliverActivity`, deterministic task-queue routing) exists to reach one *specific* live socket — a concern connection-based platforms genuinely have and Web genuinely doesn't. For a polling client, delivery mostly collapses: the moment a turn's content is written to `messages`/`turns` (already happening today, regardless of any Gateway), it's already there for the poll endpoint to read directly — no `DeliverActivity` dispatch, no embedded Temporal worker, no task-queue routing needed for Web at all. The poll endpoint is a plain Postgres read (`SELECT` new turns/messages for this session since the client's last-seen position), nothing Temporal-shaped about it. `gateway.md`'s general mechanism stays correct and necessary for a future connection-based platform; it just doesn't apply here.

### Resolved: One Continuous Session Per User — No Reset, No Threads
**Revised 2026-08-24 — see "Resolved: Multi-Session Support" below.** This section's reasoning is still exactly right for what it actually rejected: no *automatic*, arbitrary, cost-motivated resets. What changed is different in kind, not a reversal — once `../gateway.md`'s multi-session-channel mechanism existed for Discord's native reply-threading, generalizing it to Web too (a real, deliberate, user-initiated "branch from here" action, not a reset) turned out to be nearly free to support, since the mechanism itself already didn't assume Discord-only. The default/main session described below is completely unchanged — still one `session_key` per user, forever, no automatic reset — this is now just no longer the *only* session a user can have. Kept below for the historical reasoning (why "reset on timeout" specifically was wrong), which remains true.

**Explicitly not ChatGPT-style** (no user-initiated "new chat," no multiple conversations, no client-generated conversation ID). **Explicitly not time-boxed either** (an earlier direction considered introducing a separate, longer idle-reset threshold specifically for this platform, distinct from the Session Coordinator's own short-lived workflow-lifecycle `idleTTL` — reconsidered and dropped, see below). Landed on: **one `session_key` per user, forever** — `session_key = "agent:main:web:user:{clerk_user_id}"`, `channel_id = clerk_user_id`. Behaves like a single, permanent Discord channel: always available, message anytime, always continues where it left off. A Session Coordinator idling out and restarting (today's `idleTTL`, 30s locally / 5–15 min real design) is purely workflow-lifecycle — the same `session_key`'s Postgres history is untouched, and `context-slot.md`'s session-wide `assemble()` (built and verified earlier this session) already means a turn after a coordinator restart still has full context, not a blank slate.

**Why "reset into a new thread on timeout" was considered and dropped:** the original motivation was a real cost concern — wouldn't a session that never resets accumulate ever-more-frequent compactions and ever-growing token consumption compared to periodically starting fresh? Investigated directly rather than assumed, and it surfaced a real, separate bug: `lcm.py`'s summary-DAG folding only ever re-folded `kind='leaf'` rows, never `kind='condensed'` ones, so a long-running session's summary DAG really would have grown without bound over a long enough timeline (see `components/context-slot.md`'s 2026-08-23 Notes Log entry, "prompted by planning the Gateway's Web platform"). **Fixed at the root** (recursive condensed-of-condensed folding, live-verified) rather than worked around with periodic resets — a reset would have thrown away real conversational continuity to paper over a cost bug that had an actual fix. With that fixed, an always-on, never-resets session is genuinely cost-safe long-term — this is still exactly true; it's *why* nothing here ever resets automatically, unchanged by the multi-session support below.

### Resolved: Multi-Session Support — a Real, User-Initiated Branch, Not a Reset
`../gateway.md`'s "Resolved: Multi-Session Channels" mechanism, generalized to Web. `websession.go`:
- `webMainSessionID = "main"` — a stable, addressable sentinel for the default/user-initiated-branch-free session above, instead of relying on an implicit empty-string case. Internally still produces the exact unchanged `agent:main:web:user:{id}` session_key, byte-for-byte — the already-running real production session is untouched.
- `webDiscriminator(channelID, sessionID)` — empty or `"main"` → `"channel:{channelID}"` (the default session); anything else → `"session:{sessionID}"`, embedded directly into the key as `agent:main:web:user:{channelID}:session:{sessionID}`. Unlike Discord, Web has no platform-native reply/thread concept to deterministically derive a discriminator from — `sessionID` is simply whatever opaque value the client generated itself when the user branched, remembered and resent by the client on every later message for that session (no server-side lookup needed to resolve it, same property Discord's deterministic reply-chain root has, just sourced differently: client-generated instead of computed from platform data).
- `webSessionIDFromKey` — the reverse mapping, `GET /sessions`' own need.

**API surface**: `/send` gains `session_id`/`parent_session_id` (both optional; empty reproduces today's exact single-session behavior); `/poll` gains a `session_id` query param; `/respond` gains a `session_id` field; new `GET /sessions` lists this authenticated user's own sessions only (`WHERE platform='web' AND channel_id={their own Clerk user_id}` — never another user's). Each summary includes a first-message-derived title, latest-message preview, `updated_at`, and whether a turn is running, all read from durable server state rather than browser storage. `parent_session_id` is only meaningful the first time a given `session_id` is sent — `submitMessageEvent`'s own genesis detection (`../gateway.md`) is what actually makes this take effect, so the client doesn't need to be careful about sending it exactly once.

### Resolved: Shared `agent-web` + Identity-Routing Router (2026-09-24)
`agent-web` used to be one deployment per tenant inside `agent-harness-tenant` (`templates/agent-web-{deployment,service}.yaml`, now deleted), hardcoding that one tenant's own `agent-brain`/Gateway Service URLs via `AGENT_BRAIN_API_URL`/`GATEWAY_API_URL`. Moved to a single shared deployment in `agent-harness-shared` instead (`templates/web-{deployment,service}.yaml`), fronted by a new shared **router** (`workflows/cmd/router`, `templates/router-{deployment,service}.yaml`, `deploy/docker/router.Dockerfile`) — also one release for the whole cluster, alongside `loop-worker`.

The Gateway process itself (this doc's own subject) is **unaffected** — still one process per tenant, still holding only that tenant's own credentials, per `../gateway.md`'s "Resolved: Per-Tenant Deployment". Only `agent-web`'s own home changed.

**How the router resolves "which tenant"**: it verifies the caller's Clerk session JWT (`workflows/internal/gateway/clerkauth`, reused as-is — same JWKS-only verification, no secret key) and reads the token's active-organization claim (`workflows/internal/router/core`'s `orgIDFromClaims`) — a **single shared Clerk project across every tenant now**, not one Clerk project per tenant as `abishekk` originally had; tenant identity is Clerk **Organization** membership. It looks that org id up in its own `tenant_registry` Postgres table (`workflows/internal/router/registry`, `deploy/helm/agent-harness-shared/files/001_tenant_registry.sql`) — a real table, not a values.yaml list, specifically so registering a new tenant never requires redeploying this chart — and reverse-proxies to that tenant's real `Gateway`/`agent-brain` Services by their cross-namespace DNS name, forwarding the original `Authorization` header unchanged. The downstream Gateway/agent-brain keep verifying that same JWT themselves exactly as before; the router only adds one more check in front (does this caller belong to any tenant at all), it never becomes a trust boundary on its own.

**Superseded same day: the nginx reverse-proxy hop was cut entirely, not just patched.** An intermediate version of this design kept `agent-web`'s own nginx as a same-origin reverse proxy in front of the router (`AGENT_BRAIN_API_URL`/`GATEWAY_API_URL` pointed at the router with `/brain`/`/gateway` path prefixes baked in, `proxy_pass`-based) — that surfaced one real nginx-template bug (a bare-variable `proxy_pass` with no literal path suffix glues the remaining request URI onto the variable's resolved path with no separating slash, so a prefixed `AGENT_BRAIN_API_URL` produced `/brainagents/list` instead of `/brain/v1/agents/list`), which was fixed and verified, but then the whole hop was judged unnecessary: the router is now itself a real, identity-aware, publicly-reachable service, so there's no reason left for `agent-web`'s nginx to sit in front of it. **Final design**: `agent-web`'s nginx (`docker/nginx.conf.template`) is a pure static-file server now — no `proxy_pass` blocks at all — and the browser calls the router's real public URL directly, cross-origin.

Since the router's real URL is only known at Helm-deploy time (one published `agent-web` image reused across deployments, same runtime-over-build-time-config philosophy as every other credential/URL in this system), it's threaded through as a small **runtime-injected config** rather than a Vite build-time env var: `agent-harness-shared`'s `web-deployment.yaml` sets one new env var, `ROUTER_PUBLIC_URL` (replacing `AGENT_BRAIN_API_URL`/`GATEWAY_API_URL` entirely, `router.publicURL` in `values.yaml`) — `agent-web`'s `docker-entrypoint.sh` renders it via `envsubst` into a new `docker/runtime-config.js.template` → `/usr/share/nginx/html/runtime-config.js`, loaded by `index.html` as a plain classic `<script>` (synchronous, ahead of the deferred module bundle) that sets `window.__RUNTIME_CONFIG__ = {GATEWAY_API_URL, AGENT_BRAIN_API_URL}`. `src/lib/gateway.ts`/`src/lib/api.ts` read that global ahead of their existing `import.meta.env.VITE_*_BASE_URL` fallback, so local `vite dev` (where the file 404s harmlessly, a `public/runtime-config.js` stub keeps it a clean no-op rather than a real 404 in dev/CI builds) is unaffected. Request paths themselves (`POST /send`, `GET /poll`, `/v1/explorer/...`) are unchanged — only the base URL resolution moved.

**New: CORS on the router** (`workflows/internal/router/core/cors.go`) — this is the first genuinely cross-origin traffic anywhere in this codebase, so the router needs to allow it explicitly. `ROUTER_ALLOWED_ORIGINS` (`router.allowedOrigins` in values, comma-separated exact origins or `"*"`) — parsed the same way `workflows/internal/gateway/web/web.go`'s sibling `GATEWAY_WEB_ALLOWED_ORIGINS` already is (split/trim/exact-match, same convention, different scope: that one only gates a WebSocket upgrade's `CheckOrigin`, this one is a full REST CORS middleware, structurally mirroring agent-brain's own real `internal/cors/middleware.go`). Allowed headers include `X-API-Key` alongside `Authorization`, since `api.ts`'s separate token-exchange auth scheme against agent-brain flows through this same router now too.

**New: the router needs a real public URL**, unlike every other component in this system so far (`loop-worker`, `tenant-worker`, Gateway — all purely in-cluster). `router.ingress.*` (a new `Ingress` template, `templates/router-ingress.yaml` — the first `Ingress` anywhere in `agent-harness`; mirrored from the one existing precedent, `agent-web`'s own `charts/agent-web/templates/ingress.yaml`, since nothing else established a convention to follow) exposes it. `web-deployment.yaml` now fails its own Helm render if `agentWeb.enabled=true` and `router.publicURL` is unset — a real, required piece of new infrastructure, not optional wiring.

Both the router-side changes above live in this repo (agent-harness). The `agent-web`-side changes (`nginx.conf.template`, `docker-entrypoint.sh`, `Dockerfile`, `runtime-config.js.template`, `index.html`, `src/lib/{gateway,api}.ts`) live in the separate sibling repo `/Users/abishekkumar/Documents/agent-web` — verified there (`tsc --noEmit`, `npm run build`, both clean) but **uncommitted in that repo as of this writing**, left for you to review/commit separately.

A user with a valid Clerk session but no active organization (freshly signed up, not yet onboarded) gets a `404 {"error":"no_tenant"}` from the router, not a `401` — the token is fine, there's just nothing to route to yet. That's the hook the onboarding flow (still to be built — see Open Questions) attaches to.

### Resolved: Self-Serve Tenant Onboarding (2026-09-24)
The backend half of docs/components/gateway/web.md's Phase 2: a new `automation` Temporal worker (`workflows/cmd/automation`) running `TenantOnboardingWorkflow` (`workflows/internal/automation/workflow`), on its own dedicated `system` Temporal namespace and task queue — separate from every tenant's own `agent-loop` queue, so a runaway/backed-up onboarding can never starve real turn traffic and vice versa. `system` is a one-time, manually-created namespace (same bootstrap step every other namespace gets), not something this worker creates for itself.

**Submission path** (`workflows/internal/router/core/onboarding.go`) mirrors `core.Ingest`/`send.go` exactly: `POST /onboard` dedups on a client-generated `request_id` (`ON CONFLICT DO NOTHING` against `tenant_onboarding_requests`, same idempotency shape as `ingested_messages`), then `SignalWithStartWorkflow`s with `WORKFLOW_ID_REUSE_POLICY_ALLOW_DUPLICATE`, workflow ID `tenant-onboard:<slug>`. `GET /onboard/{request_id}` polls progress — ownership-checked against the requester's own Clerk `sub` (a request_id is guessable, existence alone isn't enough, same discipline `core/access.go`'s session ownership already applies). Both routes use a new `authenticateUser` (verifies the JWT, returns just `sub`) rather than `authenticate` (which also requires an active org) — a user submitting an onboarding request is by definition someone who doesn't have a tenant/org yet.

**The ten provisioning activities** (`workflows/internal/automation/activities`), in order: `ValidateRequest` (fails fast on a malformed request, before anything with a side effect runs) → `RegisterTemporalNamespace` (via `client.NewNamespaceClient` — NOT `OperatorService`, which has no namespace-create RPC; this is the first place in the codebase that automates what `multi-tenancy.md` documents as a manual `temporal operator namespace create` step) → `CreateK8sNamespace` → `StageTenantSecrets` → `HelmInstallTenant` → **[human-approval gate, see below]** → `RegisterSharedPoolNamespace` → `CreateClerkOrganization` → `RegisterTenantInRegistry` → `HealthCheck`, with `CleanupStagedSecret` running unconditionally on every exit path (success or failure). `k8s.go`/`helm.go` shell out to real `kubectl`/`helm` binaries (`exec.go`'s `runCommand`/`runCommandStdin`, heartbeating every 10s) baked into the worker's own image alongside vendored copies of both charts (`deploy/docker/automation.Dockerfile`) — the exact command sequence `deploy/helm/tenants/README.md` already documents as the manual process, not a `k8s.io/client-go`/`helm.sh/helm/v3` reimplementation of it.

**Keeping secrets bounded in Temporal history**: every activity after `StageTenantSecrets` takes a `PublicRef` (just `request_id`/`requester_user_id`/`tenant_slug`, none sensitive) instead of the full input — Temporal records every activity's input verbatim in the workflow's own event history, so this bounds the real secret payload's appearance to exactly one activity call (`StageTenantSecrets`, which writes everything into a short-lived Kubernetes `Secret` via `stringData` over `kubectl apply -f -`'s stdin — deliberately never a `--from-literal` CLI flag, which would leak into the child process's own argv). `HelmInstallTenant` re-reads that `Secret` directly from Kubernetes, never from workflow input. Full elimination would need a Temporal Codec Server — out of scope for this pass, a known, disclosed limitation, not an oversight.

**Human-approval gate**: `RegisterSharedPoolNamespace` — the one step that rolls the single, cluster-wide `agent-harness-shared` release every other tenant's turns already depend on — waits on `ApproveSharedPoolRolloutSignal` (`workflow.GetSignalChannel(ctx, "approve-shared-pool-rollout")`) before running. Every other step is safely scoped to just the new tenant's own namespace; this one alone touches shared state, so it's a deliberate, reviewable pause, not an oversight — `temporal workflow signal --workflow-id tenant-onboard:<slug> --name approve-shared-pool-rollout --namespace system`.

**New RBAC, new secret**: a dedicated `ServiceAccount` + `ClusterRole`/`ClusterRoleBinding` (`automation-rbac.yaml`) scoped to only this worker — the single biggest new privilege surface in this codebase, isolated from the shared bare SA loop-worker/web/router use (which stays `automountServiceAccountToken: false`). `CLERK_SECRET_KEY` (`automation-secret.yaml`) is the first real Clerk secret key anywhere in this codebase — every other Clerk integration deliberately needs only the project's public JWKS; `CreateClerkOrganization` (`activities/clerk.go`, plain `net/http` against Clerk's Backend REST API, no SDK) is the one legitimate exception.

**Progress tracking** (`workflows/internal/onboarding`, shared by both the router and the automation worker so they agree on one schema): `tenant_onboarding_requests` (coarse status: pending → running → awaiting_approval → completed/failed) and `tenant_onboarding_steps` (fine-grained, one row per activity's running/done/failed transition, written by `activities.go`'s shared `runStep` wrapper — the step name comes from `activity.GetInfo(ctx).ActivityType.Name`, so it always matches the Go method that actually ran). Both tables live in the router's own control-plane Postgres (`agent-harness-shared`'s own `postgresql` subchart, `files/002_tenant_onboarding.sql`) — never a tenant's own data.

Not live-verified against a real cluster/Temporal server/Clerk project in this pass — `go build`/`vet`/`test` and `helm lint`/`helm template` (including all fail-guards) verified locally only, same caveat as the Phase 1 Notes Log entry below.
