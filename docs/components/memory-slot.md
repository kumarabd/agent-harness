# Component: Memory Slot
## (Long-Term Memory — Runtime Retrieval Across Sessions)

> STATUS: IN PROGRESS — **opinionated to agent-brain (hippocampus), not a pluggable backend abstraction.** Retrieval triggers (including session-start gating), typed-content model, direct integration shape, write-path construction, participant mapping (v1), per-tenant auth, extraction-model choice, type mapping, and failure handling resolved. Cross-session linking / entity resolution is explicitly out of scope (2026-08-23) — agent-brain's own concern, not this component's. `dreaming.md` superseded the same day, folded into here.

### Role (one line)
The runtime, turn-facing counterpart to `components/dreaming.md`'s batch producer: the interface a live session actually uses to pull relevant long-term memory — consolidated episodes, domain knowledge, persona/behavior preferences — into its context, scoped to *across sessions*, the complement of `components/context-slot.md`'s *within one session* scope.

### Why this exists (recap)
`components/dreaming.md` resolved the *producer* side of long-term memory (a daily per-tenant job compacting idle sessions into "episodes," pushed to a memory backend) but explicitly left retrieval open — *"how a future turn's context-hydration step actually draws on consolidated episodes."* Separately, `activities/activities/llm.py`'s `build_conversation` had zero cross-session memory in the live path at all. This component closes that gap.

### Resolved: Two Retrieval Triggers, Matching `components/context-slot.md`
- **Session start** — automatic, no model decision. Fires when a session has zero prior turns (not on every Coordinator respawn, which is workflow-lifecycle noise unrelated to whether this is a genuinely new line of inquiry).
- **Mid-session, model-initiated** — the model calls a tool (`components/tool-registry.md`'s concern) when it decides it needs something; the result comes back as an ordinary tool observation, not a special context-injection path.
- **Explicitly deferred**: a cheap, non-LLM, always-on relevance pre-filter that could also trigger retrieval automatically, without the model having to think to ask — parked as future work, not designed this pass (see `components/context-slot.md`'s matching entry for the full reasoning).

Continuous, per-`ModelCall` re-evaluation of what's relevant was explicitly rejected — it breaks prompt-cache stability, which is `context-slot.md`'s concern but binds this component's trigger design too, since memory-slot has no reason to be more eagerly re-queried than context-slot's own assembly step allows.

**Session-start retrieval is unconditional** — every zero-prior-turn session triggers a real `search`/`expand` call, no cheap pre-check gate first. Accepted cost: a wasted call on trivial first messages ("hi," "what's 2+2"). Preferred over building and tuning a gating heuristic ahead of any evidence the wasted-call cost actually matters — same discipline as everything else in this project that's deferred numeric/gating decisions pending real usage data.

### Resolved: Retrieved Content Is Typed, Not Flat
One retrieval mechanism serves several kinds of content, distinguished by a `type` field — at minimum:
- `type: episode` — `dreaming.md`'s existing output (a distilled, consolidated session).
- `type: domain-fact` — background/expertise content relevant to what's currently being discussed (e.g. a health-related question pulling in health-appropriate framing). Resolves what was initially framed as "should the system prompt dynamically shift by topic" — it doesn't; the right content gets retrieved and the model adapts, no prompt rewriting required.
- `type: persona-rule` — situational behavior/style preferences, as opposed to the small, static, always-present core identity block that stays in `context-slot.md`'s system prompt. Only pulled in when relevant, not paid for on every turn regardless of task.

This directly answers the "is this a system-prompt thing or a memory thing" question raised during design: it's memory, structurally — persona/domain content is relevance-filtered exactly like episodes, not treated as a special case.

### Superseded: OKF as the Storage-Format Candidate
**No longer the plan** — kept here as history, not deleted. OKF was adopted as an interim answer to `dreaming.md`'s two longest-open questions (episode schema, backend integration contract) before a real backend existed to check it against. A real backend now exists: **agent-brain (hippocampus)**, a separate, mature, already-substantially-built memory service (see `/Users/abishekkumar/Documents/agent-brain`), evaluated in depth and adopted below instead. Its native content shape — structured facts plus embedding channels, with bi-temporal validity intervals and content-addressed node identity (`docs/superpowers/specs/2026-08-17-semantic-layer-construction-design.md`) — is more mature than an OKF bundle would have been, grounded directly in current research (HippoRAG, NeurIPS 2024) and production practice (Zep/Graphiti), not just this project's own reasoning. OKF may still have narrow value as a portable export format someday, but it is not the storage layer.

### Resolved: agent-brain Is the Memory Backend — No Interface Abstraction
**Revised.** This component previously defined a generic `MemoryBackend` interface, framed as "agent-brain is the only adapter implemented, for now" — implying a pluggable abstraction other backends could eventually satisfy. That framing is dropped. There is no interface, no second-backend hook, no adapter concept. This component *is* the agent-brain integration, directly:

```
write_episode(event) -> event_id
search(query, session_context) -> [candidate]   # shallow: scored candidates, content attached where available
expand(ref) -> content                            # deep: full raw content, unconditional, no parameter
```

These three operations are agent-harness's actual, direct calls to agent-brain's `memory_write`/`memory_search`/`memory_expand` MCP tools — not an interface agent-brain happens to satisfy. Two tiers (shallow/deep), matching agent-brain's own resolved shape exactly (`docs/superpowers/specs/2026-08-17-recall-depth-design.md`), no generic "effort" parameter.

**Why the pivot, stated plainly:** the interface framing was generating real design cost — a normalization boundary, a "does context-slot need a backend-agnostic shared representation too" scope question, complexity that only exists to keep a hypothetical second backend possible. There is no second backend, none is planned, and this project has already repeatedly declined to design ahead of real need (the model-registry second-adapter question, the write-format question, both resolved the same way). Being explicitly opinionated — this component knows it's talking to agent-brain, uses agent-brain's actual shapes directly, no translation layer pretending otherwise — removes that cost entirely. Integration is direct: agent-harness's tenant-worker activities call agent-brain's MCP endpoint, `user_id` mapped directly to tenant. Losslessness, typed content, bi-temporal validity are simply true of this system, not "properties of the currently-selected adapter."

### Resolved: Staleness Is Handled by Placement, Not Contradiction-Detection
When retrieved memory conflicts with what a session has since established (e.g. a three-month-old episode says X, the last five live turns already established Y), no algorithmic contradiction-detection is planned. Retrieved content is placed and clearly labeled as background/prior knowledge, positioned before live session turns in the assembled prompt — the model's own recency-weighting does the rest. This is `context-slot.md`'s assembly responsibility to implement, but the underlying decision belongs here since it's about how memory-slot's output should be treated once retrieved.

### Resolved: Search/Expand Tools — Both Unrestricted
Belongs to `components/tool-registry.md` structurally, but the shape is resolved here since it maps directly onto the two calls above:
- **`search`** — available to both the main agent and subagents, finds relevant content without full recovery.
- **`expand`** — **also unrestricted**, not gated to subagents. This revises an earlier plan (modeled on LCM's `lcm_expand`, which *is* subagent-only) — agent-brain's own resolved design explicitly kept its `memory_expand` unrestricted, on the grounds that multiple-trace theory's point (the hippocampus stays available for high-fidelity specific recall even after semanticization) shouldn't be walled off behind a hard access boundary. Since `expand` in agent-brain's v1 has no depth parameter to escalate — it always returns the same bounded thing, raw episodes for one reference — the unbounded-re-expansion risk that motivated LCM's restriction doesn't apply the same way here; there's no larger tier for an unrestricted caller to keep climbing into.

### Resolved: Write-Path Construction
Constructs directly against agent-brain's `memory_write` event shape — no generic intermediate representation, because there's nothing to be generic *for*.

**A new activity (`WriteMemory`, name TBD), triggered by `Persist` without being awaited — genuinely fire-and-forget in the Temporal sense.** `Persist` calls `ExecuteActivity` but doesn't `Get()` the result before completing its own work; the activity still gets Temporal's normal tracking/retry, its outcome just doesn't gate the turn. Scope proposed as top-level turns only (subagent turns don't get independently written) — a reasonable default, not explicitly confirmed, worth revisiting if subagent-level memory turns out to matter.

**Extraction happens inside this activity, via a separate model — not the main reasoning model.** Fire-and-forget removes the latency argument against a real LLM extraction step (facts, entities, participants) — it costs money, not response time, since it's off the turn's critical path. Resolved: extraction reuses `components/model-registry.md`'s `fast` language tier directly — no separate named purpose or hint needed, since extraction has no complexity variance to route on the way a reasoning step's `next_step_hint` does; it's always the same kind of cheap, structured task.

**One turn can produce multiple events, not one.** Extraction may yield 0, 1, or several candidate events from a single turn; each gets its own `memory_write` call — agent-brain has no batch write API (`memory_write_batch` was explicitly removed per its own spec). `event_id` accordingly can't be the bare `turn_id` — it's **`turn_id:event:N`**, mirroring the ID-suffix convention already used elsewhere in this project (`turn:1:act:2`, `turn:1:sub:1`).

**Retry-safety via staging, not relying on extraction being deterministic.** An LLM extraction call isn't guaranteed to produce the same events on a Temporal-driven retry (e.g. after a transient failure calling agent-brain). Two-phase fix: extraction writes its candidate events to a local Postgres staging table first (durable, agent-harness-owned); a separate, genuinely idempotent step reads the staged rows and calls `memory_write` per event. A retry of the whole activity re-reads already-staged output instead of re-running the LLM, so retries are safe without needing extraction itself to be deterministic.

### Resolved: Participant Mapping (v1 — Known Limitation, Not a Full Fix)
Checked against the actual schema, not assumed: `messages` has only `role` (`user`/`assistant`/`tool`) — no author/sender field at all (`activities/migrations/001_initial_schema.sql`). This is a genuine data gap, not a mapping choice to be clever about — agent-harness cannot identify *which individual human* sent a message today, only that a message came from "the user side" of a channel.

**v1: use `session_key` as the "self" participant identity** — `participants: [{"id": session_key, "type": "self"}, {"id": "<agent-name>", "type": "agent"}]`. Known, accepted limitation: this conflates every human posting in a multi-user channel (e.g. a shared Discord guild channel) into one identity. Not fixed here — the real fix is a Gateway component capturing real per-message author identity and threading it through to `messages`, which doesn't exist yet (`components/gateway.md`, `future-work.md`). This is the correct, honest v1 answer given what data actually exists, not a permanent design decision.

### Resolved: Per-Tenant Auth
Reuses the exact pattern already established for the LLM key (`deploy/helm/tenants/README.md`'s convention, following the security fix earlier in this project's history): a new `agentBrain:` block in `agent-harness-tenant`'s `values.yaml`, chart defaults disabled/empty (`enabled: false`, `baseURL: ""`, `apiKey: ""`) with the same "do not commit a real key here" warning comment the `llm:` block already carries; the real per-tenant value goes in `deploy/helm/tenants/<tenant>.yaml` (already gitignored). A chart-managed Secret (`agent-brain-secret.yaml`, mirroring `llm-secret.yaml`) delivers it to the tenant-worker as env vars — `AGENT_BRAIN_BASE_URL`/`AGENT_BRAIN_API_KEY`, matching the existing `PIONEER_*` naming convention. API-key auth (agent-brain's `X-API-Key` header) chosen over JWT for consistency with how the LLM credential already works, not because JWT's per-request claims (`X-Agent-Id`/`X-Session-Id`) are ruled out — revisit if those turn out to matter.

### Resolved: Subagent-Turn Write Scope
Top-level turns only. A subagent's turn does not independently call `write_episode` — its work enters memory only indirectly, if the parent turn's own extraction happens to pick it up from the folded-back result. Consistent with subagent isolation being a standing principle elsewhere in this design (`components/session-filesystem.md`): a subagent's internal exploration stays private by default, not automatically memory-worthy on its own.

### Resolved: Failure Handling
Bounded retry, then degrade gracefully rather than fail the turn — splits into two mechanisms depending on the call:
- **`search`/`expand` as a mid-session tool call**: inherits the existing tool-failure pattern already resolved in `components/temporal-workflow.md` — a failed tool call surfaces as an error observation to the model, not a turn failure. `MaximumAttempts: 3`, matching `ToolCall`'s existing retry policy. No new mechanism.
- **Session-start automatic retrieval**: not a tool call, so this needed its own answer — bounded retry (same `MaximumAttempts: 3`), and on exhaustion, context-slot assembles the prompt with no retrieved background rather than failing the turn.
- **`write_episode` (fire-and-forget)**: already doesn't block the turn, so "proceed without memory" doesn't apply the same way. What retry exhaustion actually means here: a staged-but-never-pushed episode row. Left genuinely open below — a backfill sweep vs. abandonment after a retention window is a real decision, not yet made.

### Resolved: Type Mapping — Tagged at Write Time, Not Inferred
Agent-brain's own typing (`event_type`, `entity_type`, predicate vocabulary) was designed for its own graph/EMU/semantic-layer needs, independent of this component's `episode`/`domain-fact`/`persona-rule` taxonomy — the two were never going to line up by inference. Resolved instead via round-trip tagging: the `WriteMemory` activity stamps `attributes.harness_type` (agent-brain's own `events.attributes` JSONB, *"arbitrary metadata"* per its schema) with one of the three values at write time; retrieval reads the same field back. No reconciliation against agent-brain's native type system needed.

**One gap this doesn't cover**: content agent-brain synthesizes itself (`Task3`'s promoted semantic facts) was never written by agent-harness, so there's no `harness_type` tag to read back. Default: `domain-fact` — a generalized semantic fact reads closer to background knowledge than to a specific episode or a persona rule.

**Normalization boundary**: agent-brain's own return shapes genuinely differ by design (a semantic fact from `search` is structured SPO + bi-temporal validity; raw content from `expand` is the full event schema) — that's real, deliberate layering on agent-brain's side, not something to hide. This component's job is normalizing whatever comes back (either shape) into one consistent tagged item — `{content, harness_type}` — before handing it to `context-slot.md`, so the assembly step never needs to know which agent-brain shape a given item originated from. Scoped to memory-slot's own output only; unifying this further with context-slot's own native content (turns, summary-DAG nodes) into one shared representation was raised but not adopted — out of scope unless a real need for it shows up.

### Explicitly Out of Scope: Cross-Session Linking / Entity Resolution
**2026-08-23.** Previously tracked as an open question here (and, before that, inherited from the now-superseded `dreaming.md`). Reclassified as out of scope for this component entirely, not merely deferred — consistent with this doc's own standing stance ("opinionated to agent-brain... no interface abstraction, no second-guessing agent-brain's own resolved shapes"). Both of the two real gaps identified while investigating this are agent-brain's own concerns, not agent-harness's:
1. **Entity conflation/fragmentation resolution** — a real, detected-but-human-gated workflow entirely on agent-brain's side (`docs/superpowers/specs/2026-07-25-dream-review-queue-design.md`, resolved via `agent-web`). Agent-harness has no reason to build anything to work around this; if it matters for a given tenant, that's an agent-brain operations question, not a design gap here.
2. **Cross-session retrieval quality** ("does `memory_search` surface relevant content from a different session that obliquely relates to this one") — a property of agent-brain's own retrieval/ranking algorithm. Agent-harness's job is calling `memory_search` correctly and handing results to the model; if retrieval quality is ever found lacking, that's agent-brain's tuning problem to fix, not a reason for agent-harness to build compensating machinery on top of a system it's already deliberately not abstracting away from.

### Open Questions / To Design
- **The deferred cheap Tier-1 trigger** — shared, deferred, with `context-slot.md`.
- **Staged-but-unpushed episode rows after retry exhaustion** — backfill sweep vs. abandonment, not decided.
