### Role (one line)
The runtime, turn-facing counterpart to `components/dreaming.md`'s batch producer: the interface a live session actually uses to pull relevant long-term memory — consolidated episodes, domain knowledge, persona/behavior preferences — into its context, scoped to *across sessions*, the complement of `components/context-slot.md`'s *within one session* scope.

### Why this exists (recap)
`components/dreaming.md` resolved the *producer* side of long-term memory (a daily per-tenant job compacting idle sessions into "episodes," pushed to a memory backend) but explicitly left retrieval open — *"how a future turn's context-hydration step actually draws on consolidated episodes."* Separately, `activities/activities/llm.py`'s `build_conversation` had zero cross-session memory in the live path at all. This component closes that gap.

### Resolved: Two Retrieval Triggers, Matching `components/context-slot.md`
> **Superseded 2026-08-31 for the automatic trigger** — it is now the request
> pipeline's step 4 (`components/request-pipeline/04-memory-retrieval.md`):
> `MemoryRetrieve` runs **once per turn** (not only the session's first), keyed
> to step 2's distilled `retrieval_query`, and `prompt.assemble` injects the
> results into that turn's conversation directly. (**REVISION 2026-09-02**: the
> earlier design staged results to a `turn_retrieval` table read every ModelCall;
> that table is dropped — see `request-pipeline/08-planning.md` — and retrieval
> is per-turn, not a `RoutingWorkflow` fan-out.) The "session start only" framing
> below is the earliest design; the "unconditional, accept the wasted call"
> reasoning still holds, just per-turn now (a `conversational` turn skips it).
> The mid-session model-initiated `memory_search` tool is unchanged.

- **Session start** — automatic, no model decision. Fires when a session has zero prior turns (not on every Coordinator respawn, which is workflow-lifecycle noise unrelated to whether this is a genuinely new line of inquiry).
- **Mid-session, model-initiated** — the model calls a tool (`components/tool-registry.md`'s concern) when it decides it needs something; the result comes back as an ordinary tool observation, not a special context-injection path.
- **Explicitly deferred**: a cheap, non-LLM, always-on relevance pre-filter that could also trigger retrieval automatically, without the model having to think to ask — parked as future work, not designed this pass (see `components/context-slot.md`'s matching entry for the full reasoning).

Continuous, per-`ModelCall` re-evaluation of what's relevant was explicitly rejected — it breaks prompt-cache stability, which is `context-slot.md`'s concern but binds this component's trigger design too, since memory-slot has no reason to be more eagerly re-queried than context-slot's own assembly step allows.

**Session-start retrieval is unconditional** — every zero-prior-turn session triggers a real `search`/`expand` call, no cheap pre-check gate first. Accepted cost: a wasted call on trivial first messages ("hi," "what's 2+2"). Preferred over building and tuning a gating heuristic ahead of any evidence the wasted-call cost actually matters — same discipline as everything else in this project that's deferred numeric/gating decisions pending real usage data.

### Resolved: Retrieved Content Is Typed, Not Flat
One retrieval mechanism serves several kinds of content, distinguished by a `type` field — at minimum:
- `type: episode` — `dreaming.md`'s existing output (a distilled, consolidated session).
- `type: domain-fact` — background/expertise content relevant to what's currently being discussed (e.g. a health-related question pulling in health-appropriate framing). Resolves what was initially framed as "should the system prompt dynamically shift by topic" — it doesn't; the right content gets retrieved and the model adapts, no prompt rewriting required.
- `type: persona-rule` — situational behavior/style preferences, as opposed to the small, static, always-present core identity block that stays in `context-slot.md`'s system prompt. Only pulled in when relevant, not paid for on every turn regardless of task.

This directly answers the "is this a system-prompt thing or a memory thing" question raised during design: it's memory, structurally — persona/domain content is relevance-filtered exactly like episodes, not treated as a special case.

OKF may still have narrow value as a portable export format someday, but it is not the storage layer.

### Resolved: agent-brain Is the Memory Backend — No Interface Abstraction
**Revised.** This component previously defined a generic `MemoryBackend` interface, framed as "agent-brain is the only adapter implemented, for now" — implying a pluggable abstraction other backends could eventually satisfy. That framing is dropped. There is no interface, no second-backend hook, no adapter concept. This component *is* the agent-brain integration, directly:

```
write_episode(event) -> event_id
search(query, session_context) -> [candidate]   # shallow: scored candidates, content attached where available
expand(ref) -> content                            # deep: full raw content, unconditional, no parameter
```

These three operations are agent-harness's actual, direct calls to agent-brain's `memory_write`/`memory_search`/`memory_expand` MCP tools — not an interface agent-brain happens to satisfy. Two tiers (shallow/deep), matching agent-brain's own resolved shape exactly (`docs/superpowers/specs/2026-08-17-recall-depth-design.md`), no generic "effort" parameter.

**Why the pivot, stated plainly:** the interface framing was generating real design cost — a normalization boundary, a "does context-slot need a backend-agnostic shared representation too" scope question, complexity that only exists to keep a hypothetical second backend possible. There is no second backend, none is planned, and this project has already repeatedly declined to design ahead of real need (the model-registry second-adapter question, the write-format question, both resolved the same way). Being explicitly opinionated — this component knows it's talking to agent-brain, uses agent-brain's actual shapes directly, no translation layer pretending otherwise — removes that cost entirely. Integration is direct: agent-harness's tenant-worker activities call agent-brain's MCP endpoint, `user_id` mapped directly to tenant. Losslessness, typed content, bi-temporal validity are simply true of this system, not "properties of the currently-selected adapter."

### Resolved: Staleness Is Handled by Placement, Not Contradiction-Detection
When retrieved memory conflicts with what a session has since established (e.g. a three-month-old episode says X, the last five live turns already established Y), no algorithmic contradiction-detection is planned. Retrieved content is placed and clearly labeled as background/prior knowledge, positioned before live session turns in the assembled prompt — the model's own recency-weighting does the rest. This is `context-slot.md`'s assembly responsibility to implement, but the underlying decision belongs here since it's about how memory-slot's output should be treated once retrieved.

### Resolved: Search/Expand Tools — Both Unrestricted
Belongs to `components/tool-registry.md` structurally, but the shape is resolved here since it maps directly onto the two calls above:
- **`search`** — available to both the main agent and subagents, finds relevant content without full recovery.
- **`expand`** — **also unrestricted**, not gated to subagents. This revises an earlier plan (modeled on LCM's `lcm_expand`, which *is* subagent-only) — agent-brain's own resolved design explicitly kept its `memory_expand` unrestricted, on the grounds that multiple-trace theory's point (the hippocampus stays available for high-fidelity specific recall even after semanticization) shouldn't be walled off behind a hard access boundary. Since `expand` in agent-brain's v1 has no depth parameter to escalate — it always returns the same bounded thing, raw episodes for one reference — the unbounded-re-expansion risk that motivated LCM's restriction doesn't apply the same way here; there's no larger tier for an unrestricted caller to keep climbing into.

### Resolved: Write-Path Construction
**Stale as of agent-brain's own 2026-08-21 mining-pipeline redesign — corrected here 2026-08-29, caught while investigating recall latency (see "Resolved: Recall Latency" below).** Everything in this section describes the *originally planned* write path; the real, shipped one (`activities/activities/write_memory.py`) is simpler in three concrete ways, each because agent-brain's own `memory_write` contract changed underneath this design, not because agent-harness chose to simplify unprompted:

1. **No caller-side LLM extraction, no staging table.** `memory_write`'s own real description is explicit: *"This does not extract structured knowledge... write the complete raw trigger text, since it's the only input the mining pipeline sees."* Agent-brain's own downstream mining pipeline (entities/facts/rules workers) does the extraction now — a caller-side extraction step would be redundant work fighting the actual contract. This also removes the retry-safety problem the staging table existed to solve: `memory_write`'s `event_id` is already a caller-supplied idempotency key, so a deterministic `{turn_id}:event:1` makes a Temporal-driven retry of the whole activity safe by construction.
2. **One event per top-level turn, not "0, 1, or several."** A direct consequence of #1 — no extraction step is deciding how many candidate events to split into.
3. **No participants sent by default.** `memory_write`'s real description: *"Participants are third parties the event is about — never yourself, and never the user."* This section's originally-proposed v1 mapping (`session_key` as a "self" participant) was exactly the opposite of that; agent-brain resolves both the authenticated user and the writing agent's own identity automatically now. **Revisited 2026-09-05** — see "Resolved: Per-Message Speaker Identity" below: this assumed one fixed identity per authenticated call, which breaks once a shared channel can have multiple distinct real human speakers; `participants` needs to start carrying real per-event speaker identity again, just not the v1 `session_key` mapping this originally rejected.

The real activity: fire-and-forget from `turn.go` (a detached child workflow, `ParentClosePolicy: ABANDON` — a bare unawaited activity was tried first and found NOT reliably fire-and-forget, since its completion gets reported against an already-closed parent and silently discarded; see `gateway.md`'s own Notes Log), top-level turns only, sends the turn's raw conversational transcript (user/assistant message text, not tool-call mechanics) as `trigger.content` in one `memory_write` call.

**Fixed the same day, once named.** agent-brain's own mining-pipeline-redesign doc's Harness Integration Guide says plainly *"Don't call it per-turn or per-tool-call... that's exactly the granularity this redesign moved away from"* — it wants writes at session-completion and context-compaction boundaries instead. `WriteMemory` no longer dispatches from `turn.go`'s own end-of-turn block at all (the per-turn `ExecuteChildWorkflow(cctx, WriteMemoryWorkflow, input.TurnID)` call is gone). It now fires from exactly the two places the contract names:
- **Session completion** — `coordinator.go`'s idle-timeout exit, right before the coordinator returns.
- **Context compaction** — `turn.go`'s hard-compression branch (`compressionState(...) == "hard"`), *not* the soft path (which fires every iteration as a usually-cheap no-op — dispatching there would just reintroduce near-per-turn granularity through a different door).

`WriteMemoryActivity` itself changed to match: it now takes `session_key`, not `turn_id`. **Revised again the same day, second time — fully stateless now, no watermark at all** (the watermark column above, `sessions.memory_write_watermark_turn_seq`, was live for under a day before being dropped — migration `011_drop_memory_write_watermark.sql`). Prompted directly: a watermarked *delta* of raw messages was blind to `context-slot.md`'s own compaction — if a span had already been condensed into a leaf summary by the time `WriteMemory` ran, the old design re-read and re-shipped that span as raw text anyway, never touching `context_summaries` at all.

The real, current design: **the event this activity writes IS the session's current active context**, not a delta against anything. Every dispatch merges (1) every currently-active summary (`context_summaries WHERE folded_into IS NULL` — already the cheapest, most-current representation of whatever it covers, by construction, needing no "is this wholly new" analysis) with (2) every raw message never covered by any leaf summary at all (`covers` is immutable once a leaf is created, so this is exactly "compaction hasn't touched this yet" — not window-limited the way `assemble()` is, since mining wants everything uncovered, not just what fits a live model call), ordered oldest-to-newest (summaries by `created_at`, which tracks their underlying chronological position even after folding; the raw tail by `turn_seq`/`seq`), into one transcript sent as `trigger.content`. `event_id` is a hash of that merged content, not a turn range — genuinely idempotent (identical content in, identical `event_id` out) without any session-side state to compute it.

Accepted cost, named explicitly: a session with more than one hard-compaction event will re-send a merge that overlaps a prior call's merge — whatever summaries didn't change between the two calls get sent again. Relies on agent-brain's own extraction pipeline being dedup-safe against restated/overlapping content, a property any real memory-consolidation pipeline needs regardless of this design (a person restating something already said within one real conversation isn't a new problem this introduces).

Verified with a real `BEGIN`/`ROLLBACK` round trip against the live `abishekk` Postgres, using this checkout's own code (`agent_brain.call_tool` monkeypatched to capture the call rather than hit a real service): confirmed the merge includes an active condensed summary but *not* the leaf folded into it, includes the uncovered raw tail verbatim, excludes raw text for anything already covered, orders the summary block before the raw tail, and produces a deterministic content-hash `event_id`. `go build`/`go vet`/`gofmt` and `py_compile` clean.

### Resolved: Recall Latency — Real-Time Trigger, Not a 6-Hour Wait
**2026-08-29.** Traced the real write→recall path end to end, prompted directly by a concrete question ("if I send instructions in conversation, does it surface later on recall?") — the honest answer at the time was **no, not for hours**: `memory_search` (agent-brain's `SearchFused`) only ever queries six tables (`emu`, `semantic_nodes`, `domain_edges`, `facts`, `semantic_rules`, `concept_definitions`), every one populated exclusively by agent-brain's own mining/EMU-construction Temporal Schedules — `"25 */6 * * *"` for `mining-rules`, the stage that would turn a real standing instruction into a retrievable rule. The raw event a write actually lands in first is never itself searched. So the real floor on "can this be recalled at all" was the cron interval, not anything about the content.

**Fixed on agent-brain's own side, not by changing anything here.** Full design and implementation in agent-brain's `docs/superpowers/specs/2026-08-29-write-triggered-mining-design.md`: `memory_write`'s own Go handler now triggers agent-brain's already-built (but previously never-invoked) `MiningPipelineWorkflow` directly, per user, in real time — a channel-owned goroutine, a Temporal client constructed once at startup (not per write), and a deterministic per-user workflow ID that gives debounce for free from Temporal's own "already running" rejection, no timer/coalescing logic needed. The 6-hourly cron Schedules are kept, unchanged, as a backstop (covers a dropped trigger or a period Temporal was unreachable) — not removed.

**What this actually changes here**: nothing needed to change in this component's own retrieval mechanism (`memory_search`/`memory_expand`, "Resolved: Two Retrieval Triggers" above) — the fix is entirely upstream, in how soon written content becomes searchable at all. Once mined (now near-real-time instead of up to 6 hours later), it surfaces through the exact same triggers this doc already resolved: automatic at session start, or mid-session when the model itself calls `memory_search`. **Still not synchronous** — a real async round trip (write → trigger → a real `MiningPipelineWorkflow` execution → mined rows → searchable) still has to happen; "real-time" here means seconds to low minutes under normal load, not instant, and still depends on the model actually calling `memory_search` at all (this component's own session-start-automatic trigger is the one exception that doesn't need the model to decide anything).

### Resolved: Participant Mapping (v1 — Known Limitation, Not a Full Fix)
Checked against the actual schema, not assumed: `messages` has only `role` (`user`/`assistant`/`tool`) — no author/sender field at all (`activities/migrations/001_initial_schema.sql`). This is a genuine data gap, not a mapping choice to be clever about — agent-harness cannot identify *which individual human* sent a message today, only that a message came from "the user side" of a channel.

**v1: use `session_key` as the "self" participant identity** — `participants: [{"id": session_key, "type": "self"}, {"id": "<agent-name>", "type": "agent"}]`. Known, accepted limitation: this conflates every human posting in a multi-user channel (e.g. a shared Discord guild channel) into one identity. Not fixed here — the real fix is a Gateway component capturing real per-message author identity and threading it through to `messages`, which doesn't exist yet (`components/gateway.md`, `future-work.md`). This is the correct, honest v1 answer given what data actually exists, not a permanent design decision.

### Resolved: Per-Message Speaker Identity (Subject Model, v2 — 2026-09-05)
**Supersedes the v1 mapping above.** Prompted by tracing a live bug (`create_intention`'s `fire_at` computed against a hallucinated date, since no current-date value reaches the model anywhere — found via a real live-cluster investigation, not speculation) into a much broader question: what "detail the agent needs" should flow through memory at all, and how.

**`user` is a role, not a privileged owner identity.** Any human participant in any conversation gets it when they're the one speaking — there is no canonical single "the user" entity to resolve to. This matters concretely because Discord and Discord-voice sessions are already, today, shared across every human posting in a channel (`gateway.md`'s `SessionKeyFor` — one `session_key` per channel, not per user) — a scenario this system already has live, not a hypothetical multi-tenant future.

**"I" resolution must be per-message, not per-session.** Whoever actually authored a given message is who a first-person claim in it is about — could be the channel owner, could be someone else entirely posting in a shared channel, could be the agent itself (an assistant-authored message). No fixed identity can stand in for this.

**Only the Gateway can supply it.** The mining pipeline only ever sees transcript text — it cannot recover real per-speaker identity from prose alone. The Gateway already resolves the real platform-native sender id at ingestion (Discord's `message.Author.ID`, Discord voice's speaking-user id) and even durably records it elsewhere (`discord_ambient_messages.author`) — it's just discarded one line before reaching `InsertMessage` today. See `gateway.md`'s updated "Resolved: Generic `MessageEvent` Shape" for the concrete plan: a new `messages.speaker_id` column, threaded from `MessageEvent.User` through `types.Message`/`InsertMessageInput`, no new identity-capture mechanism needed.

**Structural consequence for `write_memory.py`**: "Resolved: Write-Path Construction" above (point 3, "no participants sent by default") assumed agent-brain "resolves both the authenticated user and the writing agent's own identity automatically" — correct for a single fixed caller identity per authenticated request, wrong once a shared channel can have several distinct real speakers, none of whom is necessarily the tenant's own auth identity. Once `messages.speaker_id` exists, `write_memory.py` needs to populate `memory_write`'s `participants` field with the real per-event speaker identity, structurally (not folded into the transcript text as an inferred "Alice: ..." prefix) — agent-brain's own side of this (its `memory_write` handler's implicit-user-resolution assumption) is scoped in that repo's own docs (`docs/superpowers/specs/2026-09-05-entity-attribution-and-single-tenant-model-design.md`), not duplicated here.

**Agent's own self-facts split in two, only one half a memory concern at all:**
- *Static* identity/persona/config ("built on Claude Sonnet 5," base role framing) is never observed — it's deployment config, true a priori regardless of who's asking. Stays exactly where it already lives (the static system prompt, `context-slot.md`'s concern), never touches agent-brain.
- *Dynamic* self-observations (a commitment made within a specific channel, a correction learned through actually operating) are real mined facts — and once agent-brain's tenancy was confirmed single-instance-per-tenant (each deployment already serves exactly one real owner, mirroring this project's own per-tenant Helm pattern), these need no reserved/global synthetic entity at all: the agent is simply another entity (`role: agent`) inside that one instance's graph, using the exact same mechanism as any other entity. An earlier "global self-entity shared across every tenant" framing was considered and dropped once single-tenancy was confirmed — noted here only for the trail, not the design. Full detail: agent-brain's own `docs/superpowers/specs/2026-09-05-entity-attribution-and-single-tenant-model-design.md`.

**Entity resolution, not digest scoping, is what a matched procedure needs from this.** An earlier pass of this doc framed the open question as "which participants' digests to inject" (a genesis-time enumeration problem, solved for free by the session/LCM window). That framing is gone along with the bespoke digest itself — see "Resolved: Entity Facts as a Task-Matched Procedure" below. What's left instead: when a task-matched procedure fires and needs to look someone up, it needs to resolve *which* `entities` row a given conversation participant is — `entity_identities`/per-message speaker resolution (above) is what makes that resolution deterministic rather than a fresh fuzzy match every time.

Not yet decided, left genuinely open: whether `messages.speaker_id` resolves 1:1 to a stable agent-brain `entities` row per real-world speaker at write time, or whether that resolution stays fuzzy/emergent the way it is today (agent-brain's own concern, not scoped further here).

### Resolved: Per-Tenant Auth
Reuses the exact pattern already established for the LLM key (`deploy/helm/tenants/README.md`'s convention, following the security fix earlier in this project's history): a new `agentBrain:` block in `agent-harness-tenant`'s `values.yaml`, chart defaults disabled/empty (`enabled: false`, `baseURL: ""`, `apiKey: ""`) with the same "do not commit a real key here" warning comment the `llm:` block already carries; the real per-tenant value goes in `deploy/helm/tenants/<tenant>.yaml` (already gitignored). A chart-managed Secret (`agent-brain-secret.yaml`, mirroring `llm-secret.yaml`) delivers it to the tenant-worker as env vars — `AGENT_BRAIN_BASE_URL`/`AGENT_BRAIN_API_KEY`, matching the existing `LLM_PROVIDER_*` naming convention (renamed from `PIONEER_*` on 2026-08-28, see `model-registry.md`'s Notes Log). API-key auth (agent-brain's `X-API-Key` header) chosen over JWT for consistency with how the LLM credential already works, not because JWT's per-request claims (`X-Agent-Id`/`X-Session-Id`) are ruled out — revisit if those turn out to matter.

### Resolved: Subagent-Turn Write Scope
Top-level turns only. A subagent's turn does not independently call `write_episode` — its work enters memory only indirectly, if the parent turn's own extraction happens to pick it up from the folded-back result. Consistent with subagent isolation being a standing principle elsewhere in this design (`components/session-filesystem.md`): a subagent's internal exploration stays private by default, not automatically memory-worthy on its own.

### Resolved: Failure Handling
Bounded retry, then degrade gracefully rather than fail the turn — splits into two mechanisms depending on the call:
- **`search`/`expand` as a mid-session tool call**: inherits the existing tool-failure pattern already resolved in `components/temporal-workflow.md` — a failed tool call surfaces as an error observation to the model, not a turn failure. `MaximumAttempts: 3`, matching `ToolCall`'s existing retry policy. No new mechanism.
- **Session-start automatic retrieval**: not a tool call, so this needed its own answer — bounded retry (same `MaximumAttempts: 3`), and on exhaustion, context-slot assembles the prompt with no retrieved background rather than failing the turn.
- **`write_episode` (fire-and-forget)**: already doesn't block the turn, so "proceed without memory" doesn't apply the same way. What retry exhaustion actually means here: a staged-but-never-pushed episode row. Left genuinely open below — a backfill sweep vs. abandonment after a retention window is a real decision, not yet made.

### Resolved: Type Mapping — Tagged at Write Time, Not Inferred
Agent-brain's own typing (`event_type`, `entity_type`, predicate vocabulary) was designed for its own graph/EMU/semantic-layer needs, independent of this component's `episode`/`domain-fact`/`persona-rule` taxonomy — the two were never going to line up by inference. Resolved instead via round-trip tagging: the `WriteMemory` activity stamps `attributes.harness_type` (agent-brain's own `events.attributes` JSONB, *"arbitrary metadata"* per its schema) with one of the three values at write time; retrieval reads the same field back. No reconciliation against agent-brain's native type system needed.

**One gap this doesn't cover**: content agent-brain synthesizes itself (`Task3`'s promoted semantic facts) was never written by agent-harness, so there's no `harness_type` tag to read back. Default: `domain-fact` — a generalized semantic fact reads closer to background knowledge than to a specific episode or a persona rule.

**Normalization boundary**: agent-brain's own return shapes genuinely differ by design (a semantic fact from `search` is structured SPO + bi-temporal validity; raw content from `expand` is the full event schema) — that's real, deliberate layering on agent-brain's side, not something to hide. This component's job is normalizing whatever comes back (either shape) into one consistent tagged item — `{content, harness_type}` — before handing it to `context-slot.md`, so the assembly step never needs to know which agent-brain shape a given item originated from. Scoped to memory-slot's own output only; unifying this further with context-slot's own native content (turns, summary-DAG nodes) into one shared representation was raised but not adopted — out of scope unless a real need for it shows up.

### Resolved: Entity Facts as a Task-Matched Procedure — No First-Class Digest (2026-09-05, later)
**Superseded, same day: a bespoke, always-present, genesis-populated, non-shed "profile digest."** An earlier pass of this section split user's-world facts into an "ambient" digest (special-cased, first-class, exempt from retrieval and shedding) versus everything else being ordinary on-demand retrieval — the same asymmetry the agent's-world section below never needed, since its "confidently wrong" case (current date/time) is closed by an ordinary task-matched procedure, not bespoke infrastructure. Examined directly rather than left standing: is that asymmetry actually justified, or is it just extra machinery defending against a risk that's acceptable to just... accept? **Decided: accept it, consciously — not overlooked.** Entity facts about conversation participants become the same shape of thing as the agent's-world date-check procedure: a task-matched procedure ("when a task refers to a known participant's standing attributes, look them up via the structured read path below, not `memory_search`"), retrieved the same way any other skill is — same retrieval/synthesis/composition-budget dependency named at the top of this section, same accepted risk that a turn needing it can fail to trigger it if nothing about the turn matches strongly enough. A well-designed procedure (clear trigger phrasing, well-generalized) is the actual mitigation, not a structural guarantee.

**What survives from the earlier design, because it was never really about *when* the lookup happens:** the *read path*. A structured, predicate-filterable, complete enumeration against agent-brain's `facts`/`entity_identities` (scoped in that repo's own spec) is still correct and still needed — `memory_search`'s top-K ANN ranking still can't guarantee "give me everything about entity X" regardless of whether the caller is a first-class always-present digest or an ordinary task-matched procedure firing mid-conversation. The distinction that mattered was always *what kind* of lookup runs once triggered, not the trigger mechanism itself.

**What's dropped, as a direct and genuinely simplifying consequence:** no session-genesis population step, no `digest_computed_at`/staleness-refresh cache, no dedicated always-present `prompt.assemble` section exempt from `_SHED_ORDER`. There's nothing to keep fresh because nothing is cached — the structured lookup runs live whenever the procedure fires. The "don't guess, ask-or-intend" norm below still applies on top, for a different failure than this section's own accepted one: this section's risk is the lookup never triggering at all; the ask-or-intend norm covers the case where a correctly-triggered lookup comes back genuinely empty because the fact was never learned in the first place.
Opened by a concrete, live bug: an agent computing `create_intention`'s `fire_at` for "tomorrow at 10 AM PST" produced a timestamp over a year in the past. Traced end to end (a live-cluster Temporal workflow-history read, not speculation) — `fire_at` was hallucinated because **no current-date/time value exists anywhere in this pipeline**: not in `prompt.py`'s section assembly, not in `DEFAULT_SYSTEM_PROMPT`/`PLANNING_SYSTEM_PROMPT` (`llm.py`), not in the per-platform system prompt (frozen once at session genesis, per `sessions.system_prompt`), not in message history, not in the `fire_at` tool-schema description itself. The model had no grounding for "today" beyond a training-data prior.

**Fully symmetric now — both content domains are purely task-matched/on-demand, no ambient cell in either.** They split only by *mechanism*, not by presence-guarantee:

**User's world (facts about the entities in the conversation — timezone, preferences, name):**
- A task-matched procedure ("when a task refers to a known participant's standing attributes, look them up via the structured read path, not `memory_search`") — see "Resolved: Entity Facts as a Task-Matched Procedure" above for why this replaced the earlier bespoke digest, and what it still needs from agent-brain's own read path (below).
- Beneath that, a real behavioral norm rather than a passive "the model may look things up if it decides to": **if the lookup (structured procedure or plain `memory_search`) comes back insufficient, the agent doesn't guess** — it either asks directly in its response (task is blocking/urgent) or creates an intention to follow up (task isn't blocking right now). This only works when the model correctly perceives it doesn't know something — which, for facts *about a person*, it usually does; the model is well-calibrated about not knowing someone's timezone the same way it's not calibrated about not knowing today's date.

**Agent's world (the environment/ecosystem the agent itself runs in — current time, OS, disk, installed tools)** — same shape, split by *why* the model would fail to check on its own:
- **Genuinely-perceived unknowns** ("is `ffmpeg` installed") — `shell_exec`, nudged by a system-prompt instruction ("you have shell access — use it to check the environment when relevant"), the same mechanism as any tool-use decision the model is actually calibrated to make.
- **"Confidently wrong" unknowns** (current date/time is the paradigm case — checked directly: `shell_exec` was already a generally-available, actively-used tool in this exact agent's toolset at the time of the original bug, `capabilities.py`'s `Layer.INTERFACE`, non-plan-restricted, and still wasn't reached for — the model was never uncertain, so no nudge fires) — a **procedural skill**: a task-type-triggered checklist ("when computing a relative date, verify current date via `shell_exec` first"), surfaced because the *task* matched at skill-retrieval/composition time, not because the model noticed anything about itself. **Real, explicitly open limitation, not addressed in this pass, and applying equally to the user's-world procedure above**: this only works once the mistake pattern (or, for user's-world, the useful trigger phrasing) has been seen/authored at least once, and only fires when retrieval actually matches it to the current turn — cold start, and the missed-match risk itself, are both left open deliberately rather than solved by bespoke always-present machinery.

**What still needs a real read path, regardless of trigger mechanism:** `memory_search`'s top-K ANN ranking still can't guarantee "give me everything about entity X" — a real fact can simply fail to rank in the top-K against whatever a turn's query happens to embed near (this is, concretely, why the harness can't reliably answer "what timezone is this user in" today — the original failure mode motivating this whole redesign). The user's-world procedure above needs a structured, predicate-filterable, complete enumeration instead — `entity_id`/`predicate`-keyed, not similarity-ranked. That read-path/schema side is scoped in agent-brain's own docs (`docs/superpowers/specs/2026-09-05-entity-attribution-and-single-tenant-model-design.md`), not duplicated here; this component's job is calling it from within the matched procedure, the same "opinionated to agent-brain, no interface abstraction" stance this doc already holds for `search`/`expand`.

**Not yet decided**: the exact wording/authoring of the user's-world procedure (what trigger phrasing reliably matches "this task needs a participant's standing facts"), and how a matched procedure resolves *which* entity to look up (likely via `entity_identities`/per-message speaker resolution — see "Resolved: Per-Message Speaker Identity" above — but not pinned down as part of the procedure's own design here). Scoping/design only — no schema, no code, nothing implemented in this pass.
