# Component: Gateway
## (Per-Platform Ingestion & Delivery)

> STATUS: IN PROGRESS — **now an index doc, 2026-08-23** (see Notes Log). Core flow, deployment model, and reliability model resolved here as the shared contract every gateway kind implements. **Deployment topology revised the same day (later)**: per-tenant, not shared-per-platform — see "Resolved: Per-Tenant Deployment" below, which supersedes the original "one gateway type per platform, shared across tenants" framing (a real, previously-unreconciled conflict with `multi-tenancy.md`'s credential-isolation principle, caught directly rather than carried forward silently). ### Role (one line)
The platform-integration boundary: normalizes whatever a messaging platform sends into a generic `MessageEvent`, submits it durably into Temporal, and delivers the eventual response back to the client. Deliberately platform-generic engineering at this level — nothing in *this* doc is agent-specific or platform-specific; it's the same shared contract any chat-connected system's gateway layer would need, regardless of which platforms sit on top of it.

### Superseded: One Gateway Type Per Platform, Shared Across Tenants
**2026-08-23.** Originally framed as "one gateway per source" meaning one process per channel/chat, then revised to "the deployment unit is one gateway type per platform (`DiscordGateway`, `WhatsAppGateway`, ...), each independently horizontally scaled — internally handling many users/channels/*tenants* at once." That framing is wrong, caught directly rather than carried forward: it means one shared process holding real per-tenant secrets (Postgres passwords, platform API tokens, Clerk keys) for *every* tenant it serves — a direct conflict with `multi-tenancy.md`'s own core principle, *"no process, database, or worker ever holds more than one tenant's credentials or raw content,"* never reconciled against this doc because this doc predates that principle being fully worked out. See "Resolved: Per-Tenant Deployment" below for the corrected shape.

The distinction this section *did* get right, and which still matters under the corrected shape: the right replication/addressing strategy differs fundamentally by platform category —
- **Connection-based platforms** (Discord, Slack Socket Mode, Signal) hold a live, stateful socket. Something has to arbitrate which process holds it — originally "the platform's own shard partitioning," now "a Postgres-backed connection lease," see below.
- **Webhook-based platforms** (WhatsApp Business API, Telegram, Slack Events API, and first-party polling clients like `gateway/web.md`) have no persistent connection — inbound arrives as a stateless HTTP POST, outbound is a stateless HTTP call (or, for a polling client, no outbound call at all — see `gateway/web.md`'s "delivery collapses" finding). No partitioning concept exists; replicas are fully interchangeable.

### Resolved: Per-Tenant Deployment — One Gateway Process Per Tenant, Every Platform Kind via Goroutines
Not shared across tenants (see Superseded section above), and not one process per (tenant × platform) either — **one Gateway process per tenant**, written in Go, deployed as part of the `agent-harness-tenant` chart (alongside `tenant-worker` and that tenant's own Postgres — *not* part of `agent-harness-shared`), holding only that one tenant's own credentials. Internally, it runs one goroutine (or HTTP handler) per platform kind that tenant has actually configured — a tenant using both Web and Discord runs both inside the *same* process, not two separate deployments.

This isn't a new pattern — it directly mirrors something already built and running in this codebase: `loop-worker` already runs one `Client`+`Worker` pair per tenant namespace it serves, concurrently, in the same process, via static config at deploy time (`multi-tenancy.md`'s "Mechanics — resolved 2026-08-14, static config"). Same shape here, just "per configured platform kind" instead of "per tenant namespace," and per-tenant instead of shared.

**Why Go, and why this resolves cleanly**: the language choice (Go, matching `loop-worker`, at the user's direction) initially seemed to conflict with per-tenant credential isolation — Go's *shared* process (`loop-worker`) is deliberately kept credential-free under the reference-passing contract. But that conflict only existed because "Go" and "shared across tenants" were being conflated. A Gateway written in Go that's *also* deployed per-tenant (its own binary, its own deployment, this tenant's own credentials only) has exactly the same isolation shape `tenant-worker` (Python, per-tenant) already has — the language was never the actual constraint.

### Resolved: Always Async — No Sync-Required Platforms Supported
Even platforms that *offer* a synchronous response path (e.g. Slack slash commands, technically answerable within the same request) are deliberately treated as async here: ack fast, deliver the real answer later via whatever async mechanism the platform provides (a callback URL, a separate outbound API, the platform's own live connection). Holding an HTTP request or blocking a thread open for the duration of a full agentic turn (possibly involving deep tool-call sequences or subagent recursion) doesn't scale and doesn't fit this design's turn-duration profile.

**Explicit scope boundary:** a platform with *no* async mechanism at all — the full final answer must be returned on the same inbound request, no callback URL, no separate send API — is simply **not supported** by this gateway design. This was considered (a request-scoped Postgres `LISTEN`/`NOTIFY` wait with a bounded timeout was designed as a possible mechanism) and explicitly rejected in favor of keeping the gateway uniformly async. Stated plainly so it isn't rediscovered as a surprise later.

### Resolved: Inbound Flow
1. Raw event arrives at a gateway replica — via its own websocket (connection-based, only reaches the replica currently holding that platform's connection lease) or via HTTP POST (webhook-based, any replica, load-balanced).
2. Normalize into a `MessageEvent` — the generic/agentic boundary. Nothing past this step is platform-specific.
3. Resolve `session_key`, run the auth check.
4. **Dedup check-then-insert against `ingested_messages(platform, platform_message_id)`** — a ledger symmetric to `delivered_responses` on the outbound side. Needed because webhook platforms redeliver at-least-once; without this, a redelivered webhook would double-signal. If already present, skip to step 6 (ack only) — the message was already durably submitted.
5. `SignalWithStart` the session coordinator (workflow ID = `session_key`), passing the message content as the signal payload. This is the durable submission — Temporal records the payload in workflow history, so **the gateway does not separately write the message body to Postgres.** The full-content persist into `messages` happens later, as an activity inside the coordinator/turn flow, sourced from the signal payload — not duplicated at the gateway. (This removes a real redundancy an earlier version of this design had: writing the same payload durably twice, once to Postgres directly and once via the signal.)
6. Ack the platform (webhook: return 200 now; connection-based: no separate ack, just don't block).
7. Gateway's job for this message ends here — no correlation state kept, no waiting on the turn to finish. This is what "always async" buys structurally: nothing pending, nothing to garbage-collect if the gateway restarts.

*(Slash commands like `/approve`/`/stop` still route differently — unresolved, unchanged by this design.)*

### Resolved: Generic `MessageEvent` Shape
Grounded in what `gateway/web.md`'s real implementation actually needs, extended once a second real platform (`gateway/discord.md`) needed two more fields — not speculated ahead of either:

```go
type MessageEvent struct {
    Platform          string // "web" today, "discord" designed next
    ChannelID         string // scopes the CHANNEL — shared across every user posting in it
    User              string // who sent THIS message, within ChannelID — orthogonal to channel scoping
    Content           string
    PlatformMessageID string // dedup key — step 4's ingested_messages(platform, platform_message_id)
    Discriminator     string // which of possibly-many sessions in this channel — see "Resolved: Multi-Session Channels" below
    ParentSessionKey  string // set only when Discriminator resolves to a NEW session — which session it branched from
}
```

`ChannelID` and `User` are deliberately separate fields, not one: a session is scoped to the *conversation*, not to whichever user happens to send a given message — see "Resolved: Multi-Session Channels" below for what "the conversation" means once a channel can hold more than one. Collapsing the two would merge different users' DMs into one session on a platform where channel and user diverge. Web happens to have `ChannelID == User` (no group-chat concept there), which is exactly why this distinction was easy to miss until named directly — Web's own instance can't surface the bug this would cause elsewhere.

`session_key` itself is *not* a `MessageEvent` field — it's derived downstream (`sessionKeyFor(event.Platform, event.ChannelID, event.Discriminator)`), not resolved per-platform and threaded through as a redundant, driftable value.

**Known gap, not fixed by this shape:** `User` isn't persisted anywhere past `MessageEvent` for Web today — `messages` has no `author`/`platform_user_id` column, only `role`. Real for group-chat attribution, and `gateway/discord.md`'s own ambient-message buffer *does* capture it (needed for reply-chain resolution regardless) — but nothing folds it into the `messages` table itself yet. Left as a follow-on for whichever platform first needs the transcript itself to carry authorship, not built ahead of that need.

Implementation: `workflows/cmd/gateway/inbound.go` (`MessageEvent`, `submitMessageEvent` — steps 3-6 above, platform-agnostic, real for both platforms now). Web's own normalize (`send.go`) always sends `Discriminator: "channel:" + ChannelID`, `ParentSessionKey: ""`, matching its existing single-session-per-user behavior exactly (live-verified: format unchanged). Discord's own normalize (`discord.go`) computes both for real — root-collapse discriminator resolution against `discord_ambient_messages` — live-verified against real Postgres/Temporal, though not yet against a real Discord connection (`gateway/discord.md`'s own Notes Log has the detail).

### Resolved: Multi-Session Channels — Sessions as a Graph, Not a List
A channel (Web's own private per-user "channel," a Discord guild text channel, a Slack channel) can hold more than one session. `gateway/discord.md`'s reply-threading requirement is the concrete driver: a reply to some earlier message starts a conversation that should have its own scoped context, distinct from the channel's general ongoing conversation — a session *graph* per channel, not one flat session.

**`Discriminator` — which session, within a channel, does this message belong to.** Always populated, `<type>:<id>` format, never a magic empty-string special case:
- The channel's own main/default session: `channel:{channelID}` — stable and deterministic, since `channelID` is always known directly from the message, no lookup needed.
- A reply-scoped sub-session: `<type>:<id>` sourced from whatever platform-native reply anchor exists — e.g. Discord's `reply_to_platform_message_id:{rootMessageID}`, a hypothetical Slack integration's `thread_ts:{ts}`. The exact resolution *policy* (which id, resolved how) is platform-specific and lives in each platform's own `gateway/<kind>.md`, not here.

`session_key` itself still gets built per-platform (`sessionKeyFor(platform, channelID, discriminator)` in `workflows/cmd/gateway/auth.go`), and for Web specifically the *string format* stays exactly what it is today (`agent:main:web:user:{id}`, no discriminator suffix) even though `Discriminator` is now always conceptually `channel:{id}` under the hood — purely to avoid changing the format of an already-running, already-verified real session. A brand-new platform (Discord) has no such constraint and can embed the discriminator directly, e.g. `agent:main:discord:channel:{channelID}` vs. `agent:main:discord:channel:{channelID}:thread:{rootID}`.

**`ParentSessionKey` — the graph structure, and why it's Postgres data, not a Temporal parent/child relationship.** When `Discriminator` resolves to a session that doesn't exist yet, `ParentSessionKey` names which session it branched from; `sessions` gets a new nullable `parent_session_key` column recording it. Considered and rejected: making a reply-session a genuine Temporal *child workflow* of the channel's main session's `CoordinatorWorkflow`. Rejected because `CoordinatorWorkflow` routinely self-terminates on idle timeout and gets recreated fresh via `SignalWithStart` (same Workflow ID, new Run ID) — normal, expected, not a crash. A reply-session's lifetime isn't bounded by any single Coordinator execution the way a subagent's child `TurnWorkflow` is genuinely bounded by its one parent turn (that *is* the right use of Temporal child workflows — see `components/temporal-workflow.md`); a reply-thread should keep existing and evolving regardless of whether the channel's main-session Coordinator happens to be alive, idle, or mid-restart at any given moment. So the relationship is expressed as durable Postgres data instead — same principle this project already applies elsewhere (session-filesystem leases, connection leases: durable relationships live in Postgres, never in worker-pinned or workflow-coupled state) — and each session, main or reply-scoped, stays a fully independent `CoordinatorWorkflow` with its own lifecycle exactly as today.

**Depth is inherent to the mechanism, not fixed by it.** `parent_session_key` chains support arbitrary depth for free — nothing enforces two levels. How deep a given platform's sessions actually nest is purely a consequence of that platform's own discriminator-resolution policy: Discord's (see `gateway/discord.md`) walks a reply chain all the way to its root and collapses every reply in that chain onto one session, which happens to produce a flat two-level tree (one main session, several flat sibling reply-sessions) — not a design limit, just that policy's own outcome. A platform wanting real multi-level branching would instead resolve `ParentSessionKey` to whatever session the *immediately*-replied-to message already belongs to (not the root), chaining one level deeper per reply-to-a-reply. Real cost difference worth naming, not glossed over: root-collapse needs no lookup at all (pure computation from message IDs the platform already hands over); immediate-parent resolution needs a reverse lookup (given a message ID, which session does it belong to) that root-collapse doesn't. Not built for any platform yet — deferred deliberately, not a gap to rediscover later.

**Genesis detection — free, from state already being written.** `submitMessageEvent`'s own `INSERT INTO sessions ... ON CONFLICT DO NOTHING` already runs for every message; checking whether that insert actually affected a row (mirroring the dedup insert's own existing `RowsAffected()` check, just applied to the other insert in the same function) tells you, for free, whether this is genuinely the first message this session_key has ever seen — exactly the one moment context injection needs to happen, no separate existence check needed.

**Context injection at genesis — copy the parent's current LCM state.** Implemented: `SeedChildSessionContextActivity` (`activities/activities/seed_child_session.py`), called from `coordinator.go` — `CoordinatorWorkflow` now takes an optional `ParentSessionKey` on `CoordinatorInput`, set by `submitMessageEvent` ONLY on the exact genesis condition above (never on a later message for an already-existing session, and never re-fires on this session's own future idle-timeout restarts, since the Gateway — not Temporal — is what decides whether to include it, gated on its own Postgres-level genesis check rather than any Temporal-level "did this call actually start the workflow" assumption). The activity calls `lcm.assemble()` (the exact function `ModelCall` itself uses — no separate/duplicated logic) against the parent session with an empty system prompt, strips the system-message wrapper `assemble()` always prepends, and writes the remainder — summary-DAG content and the parent's verbatim recent-message window, combined, exactly as `assemble()` already combines them for real inference — as a single new `kind='leaf'` `context_summaries` row for the child, `covers = '{}'` (a genesis snapshot references no specific message_ids under the child's own turn tree, since it has none yet). A genuine duplicate, not a shared reference: the child evolves independently afterward via its own future `compact()` calls, no mutable state shared between sessions. Live-verified directly against the real cluster using the real, already-running production session as the parent (16 real messages, real tool-call history) — confirmed the child got a real leaf summary containing that actual conversation content, correct `token_count`, empty `covers`.

If the parent has no real turn history yet (nothing has triggered it — plausible for a channel that's had only ambient chatter so far, see `gateway/discord.md`), `assemble()` naturally returns nothing to copy and the activity is a deliberate no-op (logged, not an error) — the child just starts with no injected context, same as before this feature existed. **Not resolved, deliberately deferred**: a copied LCM snapshot is "as of the parent's last real turn," which could be stale if ambient activity happened after that — blending in "ambient buffer since the parent's last real turn" alongside the copy, or accepting the gap as-is; small enough to defer without weakening the core mechanism, and genuinely platform-specific (Web has no ambient buffer at all) rather than something this generic activity should own.

### Resolved: Outbound Flow — Delivery as a Colocated/Separate Temporal Worker, Not a Broker
**Superseded design choice:** the original plan used a message broker (Redis Streams/NATS) as an "outbound queue" between the deliver activity and the gateway. Reconsidered and dropped — it solved a problem created by assuming delivery runs on a generic worker pool physically separate from the gateway. A simpler mechanism removes the need for a broker entirely:

- **The gateway process itself runs an embedded Temporal worker** (same binary/process as the HTTP server and every platform goroutine — not a separate Deployment), registered for `DeliverActivity` on a task queue specific to what it owns — but only while it actually holds the relevant connection lease (connection-based platforms) or unconditionally (webhook-based/polling platforms — see below).
- The turn workflow, at delivery time, computes the target task queue **deterministically** — `deliver:{platform}:{connection_id}` (no `{tenant}` component: each tenant already runs in its own Temporal namespace, which already scopes every task queue name to that tenant — including it again in the queue string would be pure redundancy). See "Resolved: Connection Leasing" below for what `{connection_id}` is and why it can't just be `{platform}` alone.
- `ExecuteActivity(DeliverActivity, response, { taskQueue: computed_queue })` — Temporal's own task dispatch delivers the activity task to whichever gateway replica is polling that queue. Retry, durability, and correct targeting all come from Temporal's existing activity mechanics — the same retry policy already defined in `components/activities-outbound-delivery.md`, no new system needed.
- The `delivered_responses` idempotency ledger (`components/activities-outbound-delivery.md`) is unchanged: the receiving replica still checks-then-inserts before making the real platform send call, regardless of how the activity task reached it.

**Platform-dependent worker registration — still a real, inherent split, now expressed as leasing rather than sharding:**
- **Webhook-based/polling platforms:** the embedded worker for these registers unconditionally on every replica — no coupling to any specific one, any replica polling the shared per-tenant-platform queue can serve it. For a polling platform specifically (`gateway/web.md`), delivery doesn't need this at all — see that doc's "delivery collapses" finding.
- **Connection-based platforms:** the send call must go out over the *exact* live socket, a physical constraint (a TCP connection is memory-resident to one process), not a design preference. So only the replica currently holding that connection's lease registers as the embedded worker for its `DeliverActivity` queue — dynamically starting/stopping worker registration as the lease is acquired/lost, not a static, always-on registration.

**A tenant can run more than one connection of the same platform kind** (e.g. two separate Discord bots, invited to different servers) — `{platform}` alone can't address delivery once that's true, since which specific bot connection has to send the reply is now ambiguous. `{connection_id}` closes that gap: a **stable identity for one specific connection, sourced from the platform itself, never invented in config**. For Discord this is the bot's own Discord user ID — the exact same id `discordMentionsUser` already reads via `session.State.User.ID` for mention detection, so nothing new is being introduced, just reused for addressing too. Resolving it doesn't require the live gateway/websocket connection to already be open: Discord's REST API answers `GET /users/@me` (in `discordgo`, `session.User("@me")`) using just the bot token, so each configured bot's `connection_id` is resolved once at startup — *before* that bot's connection lease is ever acquired, which matters because the lease itself needs to be keyed on `connection_id` (see below), not discovered only after a successful connect. A human-assigned name in Helm values was considered and rejected: it adds a field an operator has to invent and keep from colliding/drifting, for no benefit the platform's own real identity doesn't already give for free.

### Superseded: Shard Assignment — Static Config + StatefulSet Identity
**2026-08-23.** This section assumed a shared, cross-tenant gateway potentially serving thousands of guilds, where Discord's own forced-sharding threshold (~2500 guilds) is a real concern. Under the corrected per-tenant deployment (above), each tenant's own Gateway process only ever serves *that tenant's own* guild(s) — essentially always far below any real sharding threshold. So the entire StatefulSet/shard-formula mechanism this section designed is very unlikely to ever be needed at all; replaced by a much smaller mechanism below. Kept here as history, not deleted.

### Resolved: Connection Leasing — A Postgres Lease Replaces Shard Assignment
For connection-based platforms only (webhook-based/polling platforms have no connection to arbitrate and need none of this). Reuses the exact renewal-based compare-and-swap lease pattern already built and proven for `session_filesystem_leases`/`leases.py` — a new lease *kind* on infrastructure that already exists, not a new mechanism:

```sql
CREATE TABLE gateway_connection_leases (
  platform      text NOT NULL,
  connection_id text NOT NULL,  -- Resolved: Outbound Flow — a platform-provided stable id
                                 -- (Discord: the bot's own user id via GET /users/@me),
                                 -- never invented in config. One row per connection this
                                 -- tenant runs, not one row per platform — a tenant running
                                 -- two Discord bots gets two rows here, both platform='discord'.
  holder_id     text NOT NULL,
  acquired_at   timestamptz NOT NULL DEFAULT now(),
  expires_at    timestamptz NOT NULL,  -- renewed periodically by whoever holds it, not a fixed TTL
  PRIMARY KEY (platform, connection_id)  -- tenant is implicit — this table lives in that tenant's own Postgres
);
```
- Each replica's connection-kind goroutine (one per configured connection — e.g. one per configured Discord bot token, not one per platform) tries to `acquire_or_renew` its own `(platform, connection_id)` row on its own heartbeat cadence, same `ON CONFLICT ... WHERE holder_id = $self OR expires_at < now()` semantics `leases.py` already uses. If it can't acquire (someone else holds it, not yet expired), it simply doesn't open a live connection this cycle and retries later — no error, no coordination protocol beyond the lease itself.
- If it acquires, it opens/maintains the real connection, renews the lease on the same cadence as its own reconnect/heartbeat logic, and registers as the embedded `DeliverActivity` worker for `deliver:{platform}:{connection_id}` for as long as it holds the lease. Registering under `connection_id` (not something tied to this specific lease acquisition or to `holder_id`) is what keeps the queue address stable across a reconnect or a handoff to a different replica — see "Resolved: Failure Analysis" below for why that stability is what makes a pending delivery survive either.
- Crash recovery: the lease simply expires (no renewal from a dead process) and the *next* replica to attempt acquisition gets it — no StatefulSet ordinal, no pinned identity, works identically whichever replica happens to pick it up, and the queue name it re-registers under is unchanged (it's a function of `connection_id`, not of who's holding the lease).

**Real consequence, worth being explicit about — this unlocks something the superseded shard design didn't have**: since ownership is now a lease, not a pinned ordinal, the Gateway can safely run as an ordinary, multi-replica `Deployment` even for connection-based platforms — every replica participates in lease acquisition, only one ever holds it at a time, and losing the holder just means another replica picks it up on the next attempt. No StatefulSet needed for any platform kind anymore.

**Why this and not "just don't worry about two connections"**: raised and checked directly — dedup (`ingested_messages`' own `PRIMARY KEY (platform, platform_message_id)`) already makes duplicate inbound *message processing* a non-issue for free, regardless of how many connections exist, race or not. The lease exists for a separate, real reason dedup doesn't touch: most connection-based platforms' own session semantics don't cleanly tolerate two simultaneous identifies with the same credential (Discord, for instance, can silently invalidate/flap sessions under this), and outbound delivery needs one unambiguous target to route to — a live socket Discord has already silently dropped isn't a valid delivery target even if a local replica still thinks it's connected.

### Resolved: Failure Analysis — What Happens When a Connection-Based Replica Dies Mid-Processing
Split into two genuinely different cases. Language updated 2026-08-23 from "shard"/"StatefulSet ordinal" to "lease" — the underlying two-case analysis is unchanged, only the mechanism restoring service after a crash is different (a lease reacquired by any replica, not a pinned ordinal resuming the same shard identity).

**1. Replica crashes before `SignalWithStart` succeeds (raw event received, not yet durably submitted).** This message is genuinely lost from our system's perspective — there is no mechanism that recovers it, because Temporal's durability guarantee only starts once something is inside Temporal, and nothing was written anywhere durable before the crash. This is an inherent boundary condition of bridging an external at-most-once event source into a durable internal system, not specific to this design. **What bounds the damage:** the platform's own protocol. Discord assigns each connection a sequence number and supports resuming a dropped session (replaying events since the last acknowledged sequence) rather than reconnecting cold. **Requirement this creates: gateway reconnection logic must prefer session-resume over fresh-reconnect wherever the platform supports it** — this is what actually closes most of the loss window, not anything in our own system.

**2. Replica crashes after `SignalWithStart` succeeds.** Fully covered by existing mechanisms, nothing new needed: the signal is durably in Temporal's workflow history regardless of the gateway replica's fate. The only consequence is a window where that connection has no active listener/delivery worker — inbound events during the gap follow case 1's story; outbound deliveries simply sit as pending Temporal activity tasks on `deliver:{platform}:{connection_id}` until some replica reacquires that `(platform, connection_id)` row in `gateway_connection_leases` and resumes polling — nothing is lost on that side, Temporal just holds the task, and it's still the same queue name waiting for it since that name is a function of `connection_id`, not of which replica or lease acquisition served it before the crash. The gap here is bounded by the lease's own expiry, a tunable, not by anything pod-identity-related.

**What does NOT help here, addressed directly:** writing the inbound message to Postgres at the gateway before signaling does not close the loss window — that write is just as vulnerable to a pre-submission crash as the signal itself, since both are downstream of the same gateway process being alive. The only thing genuinely upstream of a gateway crash is the platform's own durable record of what it already sent (the sequence-number/resume mechanism above) — which is also the reason the persist-to-Postgres step was moved off the gateway's inbound path entirely (see Inbound Flow, step 5) rather than kept as a redundant local safety net that doesn't actually add safety.

**Requirement this creates for `gateway_shard_state`** (name kept as-is for now — really "per-connection resume state" under the corrected topology, not literally shard-scoped anymore, and keyed the same way the lease table now is: `(platform, connection_id)` rather than `(platform, shard_id)`, since resume state is inherently per-connection once a tenant can run more than one — a rename is cosmetic, not resolved here): to make session-resume actually work across a crash/restart, the last-acknowledged sequence number needs to survive the crash. This is a few bytes, not real session state — stored in Postgres (`components/state-layer.md`), not on local pod disk, for the same reason session-filesystem rejected worker-pinned state. Whichever replica next acquires the connection lease reads this row to resume correctly — the lease and the resume-state row are two different concerns (who's allowed to connect right now vs. what sequence number to resume from), deliberately not merged into one row.

### Key Design Decisions (recap)
- **One Gateway process per tenant** (Go, `agent-harness-tenant` chart), not shared across tenants — required by `multi-tenancy.md`'s credential-isolation principle, which the original "shared per platform" framing never satisfied. Every platform kind that tenant uses runs inside this one process, as separate goroutines — not one process per (tenant × platform).
- Always async — no platform requiring a same-request synchronous response is supported.
- Delivery is a Temporal worker (embedded in the gateway process), addressed via deterministic task-queue routing (`deliver:{platform}:{connection_id}`, no `{tenant}` — already implied by the tenant's own Temporal namespace) — not a message broker.
- A tenant can run more than one connection of the same platform kind (e.g. two Discord bots) — addressing is per-*connection*, not per-platform. `connection_id` is always sourced from the platform itself (Discord: the bot's own user id, resolved via `GET /users/@me` before the connection lease is even acquired), never an operator-invented name.
- Connection-based platforms: a Postgres-backed connection lease (reusing `session_filesystem_leases`/`leases.py`'s pattern), keyed `(platform, connection_id)`, determines which replica holds a given live connection and registers as that connection's embedded delivery worker — an ordinary multi-replica `Deployment`, no StatefulSet/shard formula needed at per-tenant scale.
- Webhook-based/polling platforms: every replica's embedded worker registers unconditionally; no lease, no connection-identity concept. Delivery for a polling platform specifically may not need this mechanism at all — see `gateway/web.md`.
- Inbound message loss (pre-signal crash) is real and platform-resume-bounded, not solvable by adding a redundant Postgres write at the gateway.
