### Role (one line)
The platform-integration boundary: normalizes whatever a messaging platform sends into a generic `MessageEvent`, submits it durably into Temporal, and delivers the eventual response back to the client. Deliberately platform-generic engineering at this level — nothing in *this* doc is agent-specific or platform-specific; it's the same shared contract any chat-connected system's gateway layer would need, regardless of which platforms sit on top of it.

### Superseded: One Gateway Type Per Platform, Shared Across Tenants
**2026-08-23.** Originally framed as "one gateway per source" meaning one process per channel/chat, then revised to "the deployment unit is one gateway type per platform (`DiscordGateway`, `WhatsAppGateway`, ...), each independently horizontally scaled — internally handling many users/channels/*tenants* at once." That framing is wrong, caught directly rather than carried forward: it means one shared process holding real per-tenant secrets (Postgres passwords, platform API tokens, Clerk keys) for *every* tenant it serves — a direct conflict with `multi-tenancy.md`'s own core principle, *"no process, database, or worker ever holds more than one tenant's credentials or raw content,"* never reconciled against this doc because this doc predates that principle being fully worked out. See "Resolved: Per-Tenant Deployment" below for the corrected shape.

The distinction this section *did* get right, and which still matters under the corrected shape: the right replication/addressing strategy differs fundamentally by platform category —
- **Connection-based platforms** (Discord, Slack Socket Mode, Signal) hold a live, stateful socket. Something has to arbitrate which process holds it — originally "the platform's own shard partitioning," now "a Postgres-backed connection lease," see below.
- **Webhook-based platforms** (WhatsApp Business API, Telegram, Slack Events API, and first-party polling clients like `gateway/web.md`) have no persistent connection — inbound arrives as a stateless HTTP POST, outbound is a stateless HTTP call (or, for a polling client, no outbound call at all — see `gateway/web.md`'s "delivery collapses" finding). No partitioning concept exists; replicas are fully interchangeable.

### Resolved: Per-Tenant Deployment — One Gateway Process Per Tenant, Every Platform Kind via Goroutines
Not shared across tenants (see Superseded section above), and not one process per (tenant × platform) either — **one Gateway process per tenant**, written in Go, deployed as part of the `agent-harness-tenant` chart (alongside `tenant-worker` and that tenant's own Postgres — *not* part of `agent-harness-shared`), holding only that one tenant's own credentials. Internally, it runs one goroutine (or HTTP handler) per platform kind that tenant has actually configured — a tenant using both Web and Discord runs both inside the *same* process, not two separate deployments.

This isn't a new pattern — it directly mirrors something already built and running in this codebase: `loop-worker` already runs one `Client`+`Worker` pair per tenant namespace it serves, concurrently, in the same process, via static config at deploy time (`multi-tenancy.md`'s "Mechanics — resolved 2026-08-14, static config"). Same shape here, just "per configured platform kind" instead of "per tenant namespace," and per-tenant instead of shared.

**Why Go, and why this resolves cleanly**: the language choice (Go, matching `loop-worker`, at the user's direction) initially seemed to conflict with per-tenant credential isolation — Go's *shared* process (`loop-worker`) is deliberately kept credential-free under the reference-passing contract. But that conflict only existed because "Go" and "shared across tenants" were being conflated. A Gateway written in Go that's *also* deployed per-tenant (its own binary, its own deployment, this tenant's own credentials only) has exactly the same isolation shape `tenant-worker` (Python, per-tenant) already has — the language was never the actual constraint.

### Resolved: Always Async — No Sync-Required Platforms Supported
Even platforms that *offer* a synchronous response path (e.g. Slack slash commands, technically answerable within the same request) are deliberately treated as async here: ack fast, deliver the real answer later via whatever async mechanism the platform provides (a callback URL, a separate outbound API, the platform's own live connection). Holding an HTTP request or blocking a thread open for the duration of a full agentic turn (possibly involving deep tool-call sequences or subagent recursion) doesn't scale and doesn't fit this design's turn-duration profile.

**Explicit scope boundary:** a platform with *no* async mechanism at all — the full final answer must be returned on the same inbound request, no callback URL, no separate send API — is simply **not supported** by this gateway design. This was considered (a request-scoped Postgres `LISTEN`/`NOTIFY` wait with a bounded timeout was designed as a possible mechanism) and explicitly rejected in favor of keeping the gateway uniformly async. Stated plainly so it isn't rediscovered as a surprise later.

### Resolved: Inbound Flow
1. Raw event arrives at a gateway replica — via its own websocket (connection-based, only reaches the replica currently holding that platform's connection lease) or via HTTP POST (webhook-based, any replica, load-balanced).
2. Normalize into a `MessageEvent` — the generic/agentic boundary. Nothing past this step is platform-specific.
3. Resolve `session_key`, run the auth check.
4. **Dedup check-then-insert against `ingested_messages(platform, platform_message_id)`** — a ledger symmetric to `delivered_responses` on the outbound side. Needed because webhook platforms redeliver at-least-once; without this, a redelivered webhook would double-signal. If already present, skip to step 6 (ack only) — the message was already durably submitted.
5. `SignalWithStart` the session coordinator (workflow ID = `session_key`), passing the message content as the signal payload. This is the durable submission — Temporal records the payload in workflow history, so **the gateway does not separately write the message body to Postgres.** The full-content persist into `messages` happens later, as an activity inside the coordinator/turn flow, sourced from the signal payload — not duplicated at the gateway. (This removes a real redundancy an earlier version of this design had: writing the same payload durably twice, once to Postgres directly and once via the signal.)
6. Ack the platform (webhook: return 200 now; connection-based: no separate ack, just don't block).
7. Gateway's job for this message ends here — no correlation state kept, no waiting on the turn to finish. This is what "always async" buys structurally: nothing pending, nothing to garbage-collect if the gateway restarts.

*(Slash commands like `/approve`/`/stop` still route differently — unresolved, unchanged by this design.)*

### Resolved: Outbound Flow — Delivery as a Colocated/Separate Temporal Worker, Not a Broker
**Superseded design choice:** the original plan used a message broker (Redis Streams/NATS) as an "outbound queue" between the deliver activity and the gateway. Reconsidered and dropped — it solved a problem created by assuming delivery runs on a generic worker pool physically separate from the gateway. A simpler mechanism removes the need for a broker entirely:

- **The gateway process itself runs an embedded Temporal worker**, registered for `DeliverActivity` on a task queue specific to what it owns — but only while it actually holds the relevant connection lease (connection-based platforms) or unconditionally (webhook-based/polling platforms — see below).
- The turn workflow, at delivery time, computes the target task queue **deterministically** — `deliver:{tenant}:{platform}` (no shard component needed anymore — see "Resolved: Connection Leasing" below, which replaces shard-based addressing entirely now that the Gateway is per-tenant).
- `ExecuteActivity(DeliverActivity, response, { taskQueue: computed_queue })` — Temporal's own task dispatch delivers the activity task to whichever gateway replica is polling that queue. Retry, durability, and correct targeting all come from Temporal's existing activity mechanics — the same retry policy already defined in `components/activities-outbound-delivery.md`, no new system needed.
- The `delivered_responses` idempotency ledger (`components/activities-outbound-delivery.md`) is unchanged: the receiving replica still checks-then-inserts before making the real platform send call, regardless of how the activity task reached it.

**Platform-dependent worker registration — still a real, inherent split, now expressed as leasing rather than sharding:**
- **Webhook-based/polling platforms:** the embedded worker for these registers unconditionally on every replica — no coupling to any specific one, any replica polling the shared per-tenant-platform queue can serve it. For a polling platform specifically (`gateway/web.md`), delivery doesn't need this at all — see that doc's "delivery collapses" finding.
- **Connection-based platforms:** the send call must go out over the *exact* live socket, a physical constraint (a TCP connection is memory-resident to one process), not a design preference. So only the replica currently holding that platform's connection lease registers as the embedded worker for its `DeliverActivity` queue — dynamically starting/stopping worker registration as the lease is acquired/lost, not a static, always-on registration.

### Superseded: Shard Assignment — Static Config + StatefulSet Identity
**2026-08-23.** This section assumed a shared, cross-tenant gateway potentially serving thousands of guilds, where Discord's own forced-sharding threshold (~2500 guilds) is a real concern. Under the corrected per-tenant deployment (above), each tenant's own Gateway process only ever serves *that tenant's own* guild(s) — essentially always far below any real sharding threshold. So the entire StatefulSet/shard-formula mechanism this section designed is very unlikely to ever be needed at all; replaced by a much smaller mechanism below. Kept here as history, not deleted.

### Resolved: Connection Leasing — A Postgres Lease Replaces Shard Assignment
For connection-based platforms only (webhook-based/polling platforms have no connection to arbitrate and need none of this). Reuses the exact renewal-based compare-and-swap lease pattern already built and proven for `session_filesystem_leases`/`leases.py` — a new lease *kind* on infrastructure that already exists, not a new mechanism:

```sql
CREATE TABLE gateway_connection_leases (
  platform    text PRIMARY KEY,  -- tenant is implicit — this table lives in that tenant's own Postgres
  holder_id   text NOT NULL,
  acquired_at timestamptz NOT NULL DEFAULT now(),
  expires_at  timestamptz NOT NULL  -- renewed periodically by whoever holds it, not a fixed TTL
);
```
- Each replica's platform-kind goroutine tries to `acquire_or_renew` this lease on its own heartbeat cadence, same `ON CONFLICT ... WHERE holder_id = $self OR expires_at < now()` semantics `leases.py` already uses. If it can't acquire (someone else holds it, not yet expired), it simply doesn't open a live connection this cycle and retries later — no error, no coordination protocol beyond the lease itself.
- If it acquires, it opens/maintains the real connection, renews the lease on the same cadence as its own reconnect/heartbeat logic, and registers as the embedded `DeliverActivity` worker for `deliver:{tenant}:{platform}` for as long as it holds the lease.
- Crash recovery: the lease simply expires (no renewal from a dead process) and the *next* replica to attempt acquisition gets it — no StatefulSet ordinal, no pinned identity, works identically whichever replica happens to pick it up.

**Real consequence, worth being explicit about — this unlocks something the superseded shard design didn't have**: since ownership is now a lease, not a pinned ordinal, the Gateway can safely run as an ordinary, multi-replica `Deployment` even for connection-based platforms — every replica participates in lease acquisition, only one ever holds it at a time, and losing the holder just means another replica picks it up on the next attempt. No StatefulSet needed for any platform kind anymore.

**Why this and not "just don't worry about two connections"**: raised and checked directly — dedup (`ingested_messages`' own `PRIMARY KEY (platform, platform_message_id)`) already makes duplicate inbound *message processing* a non-issue for free, regardless of how many connections exist, race or not. The lease exists for a separate, real reason dedup doesn't touch: most connection-based platforms' own session semantics don't cleanly tolerate two simultaneous identifies with the same credential (Discord, for instance, can silently invalidate/flap sessions under this), and outbound delivery needs one unambiguous target to route to — a live socket Discord has already silently dropped isn't a valid delivery target even if a local replica still thinks it's connected.

### Resolved: Failure Analysis — What Happens When a Connection-Based Replica Dies Mid-Processing
Split into two genuinely different cases. Language updated 2026-08-23 from "shard"/"StatefulSet ordinal" to "lease" — the underlying two-case analysis is unchanged, only the mechanism restoring service after a crash is different (a lease reacquired by any replica, not a pinned ordinal resuming the same shard identity).

**1. Replica crashes before `SignalWithStart` succeeds (raw event received, not yet durably submitted).** This message is genuinely lost from our system's perspective — there is no mechanism that recovers it, because Temporal's durability guarantee only starts once something is inside Temporal, and nothing was written anywhere durable before the crash. This is an inherent boundary condition of bridging an external at-most-once event source into a durable internal system, not specific to this design. **What bounds the damage:** the platform's own protocol. Discord assigns each connection a sequence number and supports resuming a dropped session (replaying events since the last acknowledged sequence) rather than reconnecting cold. **Requirement this creates: gateway reconnection logic must prefer session-resume over fresh-reconnect wherever the platform supports it** — this is what actually closes most of the loss window, not anything in our own system.

**2. Replica crashes after `SignalWithStart` succeeds.** Fully covered by existing mechanisms, nothing new needed: the signal is durably in Temporal's workflow history regardless of the gateway replica's fate. The only consequence is a window where that platform's connection has no active listener/delivery worker for this tenant — inbound events during the gap follow case 1's story; outbound deliveries simply sit as pending Temporal activity tasks on `deliver:{tenant}:{platform}` until some replica reacquires `gateway_connection_leases` for that platform and resumes polling — nothing is lost on that side, Temporal just holds the task. The gap here is bounded by the lease's own expiry, a tunable, not by anything pod-identity-related.

**What does NOT help here, addressed directly:** writing the inbound message to Postgres at the gateway before signaling does not close the loss window — that write is just as vulnerable to a pre-submission crash as the signal itself, since both are downstream of the same gateway process being alive. The only thing genuinely upstream of a gateway crash is the platform's own durable record of what it already sent (the sequence-number/resume mechanism above) — which is also the reason the persist-to-Postgres step was moved off the gateway's inbound path entirely (see Inbound Flow, step 5) rather than kept as a redundant local safety net that doesn't actually add safety.

**Requirement this creates for `gateway_shard_state`** (name kept as-is for now — really "per-tenant-platform resume state" under the corrected topology, not literally shard-scoped anymore; a rename is cosmetic, not resolved here): to make session-resume actually work across a crash/restart, the last-acknowledged sequence number needs to survive the crash. This is a few bytes, not real session state — stored in Postgres (`components/state-layer.md`), not on local pod disk, for the same reason session-filesystem rejected worker-pinned state. Whichever replica next acquires the connection lease reads this row to resume correctly — the lease and the resume-state row are two different concerns (who's allowed to connect right now vs. what sequence number to resume from), deliberately not merged into one row.

### Key Design Decisions (recap)
- **One Gateway process per tenant** (Go, `agent-harness-tenant` chart), not shared across tenants — required by `multi-tenancy.md`'s credential-isolation principle, which the original "shared per platform" framing never satisfied. Every platform kind that tenant uses runs inside this one process, as separate goroutines — not one process per (tenant × platform).
- Always async — no platform requiring a same-request synchronous response is supported.
- Delivery is a Temporal worker (embedded in the gateway process), addressed via deterministic task-queue routing (`deliver:{tenant}:{platform}`) — not a message broker.
- Connection-based platforms: a Postgres-backed connection lease (reusing `session_filesystem_leases`/`leases.py`'s pattern) determines which replica holds the live connection and registers as that platform's embedded delivery worker — an ordinary multi-replica `Deployment`, no StatefulSet/shard formula needed at per-tenant scale.
- Webhook-based/polling platforms: every replica's embedded worker registers unconditionally; no lease, no shard concept. Delivery for a polling platform specifically may not need this mechanism at all — see `gateway/web.md`.
- Inbound message loss (pre-signal crash) is real and platform-resume-bounded, not solvable by adding a redundant Postgres write at the gateway.

### Open Questions / To Design
**Shared/index-level (genuinely cross-platform, belongs here):**
- Generic `MessageEvent` shape — which fields every platform populates (e.g. `platform`, `platform_message_id`, `session_key`, `content`) vs. which are platform-specific extensions. `gateway/web.md` now has one real concrete instance to check this against, but the shared shape itself isn't written down explicitly yet.
- Exact connection-lease heartbeat/renewal cadence — same numeric-tuning discipline as every other undecided threshold in this project (heartbeat intervals, compression thresholds), deliberately not sized here pending real usage data.
- Whether `gateway_shard_state` gets renamed to something that doesn't say "shard" now that shard assignment is superseded — cosmetic, not resolved.

**Platform-specific (moved out — belongs in each `gateway/<kind>.md`, not here):**
- Auth model — inherently per-platform (Clerk for Web, resolved in `gateway/web.md`; a real third-party platform would need its own bot-token/OAuth story, not a shared mechanism).
- Slash command routing (`/approve`, `/deny`, `/stop`) — a Discord/Slack-specific UI concept, not relevant until a platform with slash commands is actually being built.
- Connection/reconnection handling beyond the general resume-preference requirement below — genuinely per-platform (Web has none, since it polls; a connection-based platform would need real backoff/resume-API specifics).
