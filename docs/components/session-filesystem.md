### Role (one line)
Gives file-touching tool calls (shell exec, file edit, build tools, and anything git-like) a durable, worker-agnostic working directory per session — a real POSIX filesystem on a shared mount, with Postgres as the coordination layer that keeps concurrent writers from colliding. Exists so that workers stay stateless and interchangeable even for tools that need real files on disk, without pinning a session or subagent to a specific worker.

### Why this exists (recap)
Filesystem-touching tools break the "any worker can pick up any activity" statelessness the rest of this design relies on — a checkout or working directory has to survive across multiple tool calls within a session/subagent, and possibly across turns. Two options were considered and rejected before landing here:
- **Git worktrees pinned to one worker** — rejected. Requires per-subagent sticky task-queue routing (Temporal doesn't provide worker-pinning for activities out of the box), and a worker crash silently loses any uncommitted edits with no way for Temporal to recover them elsewhere — a durability regression against the whole point of this redesign.
- **Pure document store (no real filesystem)** — rejected. Most tools in a coding-agent harness (shell exec, build tools, language servers, git) expect a real POSIX filesystem; making that work against a document-store API would require building a filesystem-translation layer, which isn't worth the lift just to get atomic per-document writes.

**Resolved instead:** a real shared mount holds the bytes and the actual directory hierarchy (workers stay interchangeable — any worker can reach any session's files), and Postgres — already the durable store of record everywhere else in this design — holds per-resource lease/metadata rows. Same durable-store-plus-disposable-execution pattern used for conversation state, just applied to files.

### Responsibilities (from architecture)
- Provide a session-scoped working directory, mounted identically and simultaneously by every worker: `/session/{session_key}/`.
- Provide **per-subagent subdirectories**, isolated by default: `/session/{session_key}/sub/{n}/`, nested further for deeper recursion (mirrors the workflow-ID tree scheme already used for turns/subagents — see `components/temporal-workflow.md`).
- Arbitrate concurrent writers via **Postgres-backed leases** (not filesystem-level locking — NFS-style mounts don't give reliable atomic locking across clients).
- Support explicit **merge-back** of a completed subagent's file changes into its parent's working directory, driven by the subagent's result/observation rather than happening automatically or invisibly.

### Key Design Decisions (recap)
- **Hybrid storage, not a pure document store.** Real shared mount for bytes + hierarchy; Postgres for metadata and leases. One row per resource: session/path, content hash, last-writer, lease state.
- **Leases, not fixed-expiry locks.** A lock with a flat TTL would get stolen out from under a legitimately slow write (same failure mode we already rejected for activity cancellation via `ABANDON`). Instead: the holder renews the lease periodically while genuinely still working; it only expires if renewal actually stops (crash), giving deadlock-safety without punishing slow-but-alive writers.
- **Lease granularity starts at session/subagent-directory level**, with per-file leases as a plausible refinement once real contention patterns are observed — not committed to per-file today.
- **Per-subagent subdirectories, isolated by default.** A subagent's changes are not automatically visible to its parent or siblings; they're pulled in explicitly on completion via merge-back.
- **No worker pinning required.** Because the mount is shared and coordination lives in Postgres, any worker can service any tool-call activity for any session/subagent at any point — this preserves the stateless-worker-pool property everything else in this design depends on.

### Resolved: Subagent Merge-Back Mechanics
No new table, no new snapshot mechanism. Two independent pieces working together — one surfaces what changed, the other performs the merge.

- **Changed-file manifest** is produced by a new `SubagentManifest` activity that fires once per completed subagent (dispatched from `turn.go` after every subagent's futures settle, on both the ok-path and the interrupt path — a cancelled subagent may have written files before its interrupt landed, and those still deserve to be surfaced). It walks the subagent's subtree on the shared PV and writes the file list (relative paths, sizes, mtimes) into the subagent's own `tool_calls.result` — the same column `lcm.assemble` already reads verbatim when reconstructing tool results into the parent's context, so nothing else has to change for the parent's next `ModelCall` to see it.
- **Merge stays explicit and model-driven**, consistent with "not automatically visible" above. The subagent's completion result now carries the manifest; the model, in its next reasoning step, decides whether to invoke `merge_subagent_output` — merging all listed files or a chosen subset via the tool's optional `files` argument.
- **Conflict detection uses filesystem mtimes vs. the subagent's `turns.started_at`** — the destination's own mtime is the "last write time" the original design called for. For each source file being merged: acquire a lease on the parent's directory (reuses `_acquire_lease_blocking` from `shell_exec`), then compare `os.stat(dest).st_mtime` to `subagent.started_at`.
  - Destination doesn't exist, or exists with `mtime <= subagent_started_at` → safe to copy over. If the parent itself wrote there before the subagent started and the subagent then modified the same file, this copy overwrites the parent's earlier version — this is what merge-back is *for*, but the merged-file's rel path is also returned in `overwrote_parent_earlier` so the model isn't surprised its prior write is gone.
  - Destination written *after* the subagent's start time → something else (the parent itself, or a sibling subagent) wrote there concurrently. This is a real conflict — the file is **skipped, not silently overwritten**, and returned in the merge tool's `skipped_conflicts` result. Same pattern already used for cancellation's `side_effect: "unknown"`: don't silently resolve an ambiguous case, surface it honestly.

**Original-design caveat honestly recorded, not glossed over.** The doc previously said the manifest would be "a query over `session_filesystem_leases` for every row whose path falls under the subagent's own subtree." That doesn't work as-implemented: leases today are directory-level (one row per session/subagent working dir, keyed by `session_fs_path(turn_id)`) and are `DELETE`d on `release()` (`leases.py`), so "what got leased under my subdirectory" gives exactly one row and is gone the moment the subagent's tool call finishes. Going per-file leases + never-delete post-release would have been a bigger change that also reopened the "per-file lease granularity" open question this doc explicitly parked. Using the PV itself as the source of truth matches the doc's own "no new base-hash or snapshot mechanism required" spirit — the PV *is* the durable file store, and the leases table's job is coordinating live writers, not historical accounting.

### Open Questions / To Design
- Lease granularity — session-directory-level vs. per-file — once real tool contention patterns exist to inform the choice. (Merge-back's conflict check above works at whatever granularity leases end up at; not blocked on this being resolved first.)
- Concrete shared-mount technology (NFS/EFS-equivalent vs. clustered filesystem vs. cloud-specific) — deliberately left open for implementation time, same as the outbound-queue broker choice in `components/activities-outbound-delivery.md`. Now also needs to support hosting a Postgres data directory adequately (fsync/durability behavior matters more for Postgres than for the session tree) — a consideration this choice didn't originally have to account for.
- Lease table schema and exact columns (session/path, holder identity, lease expiry, renewal interval) — belongs in `components/state-layer.md`'s schema design.
- Interaction with session consolidation/archival (`future-work.md` — session management/consolidation): if a session's raw files are ever archived, the turn workflow's context-hydration step needs to notice and transparently rehydrate before a tool call proceeds.
- Exact large-vs-small payload threshold for the Postgres-vs-PV claim-check split (what counts as "large enough to route to the PV instead of Postgres") — not yet numerically specified.
- PV sizing/IO capacity planning given it now serves two workloads (Postgres + session files) — flagged as a cost in `components/multi-tenancy.md`, not sized here.

### Resolved: Multi-Tenant Access Scoping
Originally flagged as an open caveat: a shared mount means every worker's tool-execution process can technically reach every session's directory unless scoped by OS/container-level permissions. Resolved via `components/multi-tenancy.md` — **one dedicated PersistentVolume per tenant namespace**, mounted only by that tenant's own dedicated worker fleet. The mount itself is still shared *within* one tenant (across that tenant's own sessions/subagents, coordinated by the leases above) — nothing here changes. What changes is the boundary: "every worker" now means "every worker in this tenant's fleet," not every worker globally, because tenants no longer share a worker pool at all. No filesystem-specific mechanism was needed beyond that — the tenant boundary is the PV boundary.

(This applies to the **tenant-worker** fleet specifically — the tenant boundary described here is unaffected by the shared-loop-worker-pool decision in `components/multi-tenancy.md`, since the loop worker never touches this mount at all under the reference-passing contract in `components/temporal-workflow.md`.)

### Superseded: The Tenant PV No Longer Also Hosts That Tenant's Postgres
**Introduced 2026-08-14, superseded 2026-08-23 — recorded here so the reasoning trail stays intact, not describing current architecture.** The original decision put a tenant's self-hosted Postgres data directory on this same PV (disjoint subpath from the session tree), reasoning that one Postgres process per tenant owning its data directory exclusively didn't reopen the shared-mutable-file hazard this component already rejected once (git-worktree-per-worker). That held logically, but Postgres moved to the vendored Bitnami `postgresql` subchart as a real dependency rather than a hand-rolled StatefulSet, and that subchart provisions its **own dedicated PVC** (`postgresql.primary.persistence` in `deploy/helm/agent-harness-tenant/values.yaml`) — confirmed directly in `templates/pvc.yaml`'s own comment: "Postgres no longer shares this PV... this volume is session-filesystem only now." The switch happened as a side effect of adopting the subchart, not a deliberate re-litigation of this section — never recorded here at the time, corrected now. Two PVCs per tenant instead of one; see `components/multi-tenancy.md`'s corresponding correction for the isolation-property implications (none — one Postgres process, exclusive data directory, is unaffected by which PVC it sits on).

### Resolved: This PV Serves as the Claim-Check Store for Large Content
Per `components/temporal-workflow.md`'s reference-passing contract: Postgres holds structured/modest-sized content (messages, tool-call metadata); large payloads — big tool outputs, file diffs — are written here instead and referenced by path, keyed by tool call. A large tool result becomes just another file under the session tree.

**Implementation shape (2026-08-27, `activities/activities/claim_check.py` wired into `shell_exec`):**
- **Threshold** = `claim_check.SMALL_OUTPUT_BYTES` (currently 4096, placeholder — same numeric-tuning discipline as every other undecided threshold in this project; the open-questions list below still owns this number). "Above the threshold" now means "write to PV," not "flat-truncate and drop the rest," which is what the pre-claim-check code did.
- **Path** = `{session_dir}/.claim-check/{sanitized_tool_call_id}.{stream}.log`, where `session_dir` is the tool's own calling turn/subagent working directory (`ids.session_fs_path(turn_id)`), NOT a shared session root. Isolation exactly matches this doc's own subagent-subtree model: a subagent's stdout blob lives in the subagent's own subtree and is invisible to the parent, same as anything else the subagent writes. Leading dot keeps it out of `ls`, and both `subagent_manifest.py`'s walk and `merge_subagent_output`'s walk prune it (so tool-output artifacts never appear as subagent-authored "changed files").
- **Reference shape** returned to the model: `{claim_check_path, size_bytes, head, tail, note}` — the model reads whichever part it needs via ordinary `shell_exec` (`cat`, `head`, `tail`, `grep`) against the returned path. No new tool required. `head` + `tail` (split evenly from the same inline budget the truncation used) preserves both the opening context (banner/usage) AND the trailing diagnostic (error/summary) — the previous head-only truncation silently dropped exactly the diagnostic tail, a real information loss beyond "we couldn't fit it."
- **Per-stream, independent decision:** big stdout with tiny stderr (or vice versa) doesn't drag the small stream through the PV — each is inlined or routed on its own byte count.
- **No new lease coordination needed.** The write happens under the tool's already-held session-directory lease; each claim-check file is owned by exactly one `tool_call_id` and written exactly once, so a per-file lease would just be redundant.
- **Type-aware Exploration Summary sits on top, in a separate module** (`activities/activities/exploration_summary.py`, `components/context-slot.md` duty #2 — landed 2026-08-28). `store_if_large` calls it against the same in-memory bytes it just wrote and folds the result into the returned reference as an `exploration_summary` field, so the model sees a schema/shape description (JSON, CSV) or a natural-language summary (unstructured text) alongside the head/tail preview. The two-module split is deliberate: `claim_check.py` owns storage + reference shape (this doc's concern); `exploration_summary.py` owns *how* to describe the content (context-slot's concern). The code-structural (tree-sitter) branch LCM §2.2 originally named remains deferred there, same numeric/dependency discipline as everything else in this project.
