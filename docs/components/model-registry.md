# Component: Model Registry

> STATUS: IN PROGRESS — registry structure, selection mechanism, escalate-on-retry, storage location, pricing table, fallback-past-top-tier, and multi-provider abstraction all resolved **and implemented**: `activities/activities/model_registry.py`, wired into `model_call.py`/`llm.py`/`turn.go`, `context-slot.md`'s compression threshold, `compress_context.py`/`tool_call.py`/`exploration_summary.py`'s downstream call sites, and now (2026-08-28, third revision) a Provider ABC (`activities/activities/providers/base.py`) with per-provider implementations for OpenAI-compatible (real OpenAI, DeepSeek, Qwen, Groq, OpenRouter, Crusoe, etc. — all one class) and Anthropic (native Messages API — its own class). Every configured tier owns its own `LANGUAGE_<TIER>_{PROVIDER,MODEL,API_KEY,BASE_URL,MAX_TOKENS}` config. Provider clients are constructed on demand via `llm_client.get_provider(config)` and cached per unique `(provider, base_url, api_key)` triple — deployments with tiers on the same provider still share one HTTP connection pool for free. Verified live against a real OpenAI-compatible cluster earlier; the Anthropic path is implemented and syntactically verified but not yet live-verified against a real Anthropic account — see Notes Log. **No remaining open items in this component's own scope.**

### Role (one line)
Lets the harness select an appropriate model per task at runtime — which model to call, based on what the turn/subagent/step actually needs — replacing today's single model hardcoded into worker startup with no selection mechanism at all.

### Why this exists (recap — describes the pre-registry state)
Before this component landed, `activities/activities/tenant_worker.py` constructed exactly **one** `AsyncOpenAI` client at process startup, from `PIONEER_API_KEY`/`PIONEER_BASE_URL`/`PIONEER_MODEL`/`PIONEER_MAX_TOKENS` env vars, and injected it once into `ModelCallActivity.__init__`. Every `ModelCall`, for every turn and every subagent at every recursion depth, used that same one model. There was no mechanism for, e.g., a subagent doing a narrow, cheap task to use a smaller/faster model while the top-level turn uses a stronger one, or for a tenant to configure more than a single model choice. The registry replaces this — model NAME and provider IDENTITY are both per-call now, driven by tier config; the process no longer holds any process-wide model or provider default, and `PIONEER_*` names are entirely gone.

### Responsibilities (from architecture)
- Define what models are available: name, provider/base URL, context window size, cost (`$`/input token, `$`/output token), and capability tier.
- Decide selection: how `ModelCall` picks which model to use for a given turn/subagent/step — static per-tenant default vs. dynamic per-task choice.
- Expose per-model context-window size so the context slot (`components/context-slot.md`) can make its compression threshold model-aware, instead of the single hardcoded `budgetTokens` constant in `turn.go` today.
- Stay inside the reference-passing / tenant-isolation contract already established (`components/temporal-workflow.md`, `components/multi-tenancy.md`): model credentials remain tenant-worker-side only, never cross into the shared loop-worker.

### Resolved: Registry Structure — Modality × Tier
```
registry[modality][tier] -> model config
```
- `modality: language` — real, three tiers: `fast | medium | expert`.
- `modality: vision | audio | video` — **placeholders only for now**, no real dispatch logic. Nothing in the current toolset (`shell_exec` plus fixture stubs) calls any of these; the registry's shape accommodates them cheaply, but selection logic for them is explicitly deferred until a real consumer exists.

### Resolved: Selection Mechanism — Model Self-Declares the Next Step's Hint
`ModelCallOutput` gains a `next_step_hint: {modality, tier}` field — the model, as part of producing its current response, also declares what the *next* step needs. This rides along on output the model already has to produce, so it costs no extra call, unlike a separate classification hop. The hint threads into the following `ModelCallInput`; the **activity** (Python, tenant-worker) resolves it against the registry and picks the concrete model — the Go workflow passes the hint through as opaque data and never needs to interpret it, consistent with the tenant-isolation contract.

- **Bootstrapping**: the first `ModelCall` of a turn has no prior hint. Defaults to `{language, medium}`.
- **Applied every step, not damped.** The model re-declares a hint at every reasoning step, since step complexity genuinely varies step to step — a deliberate choice, not an oversight of the cache-prefix-stability concern named in `components/context-slot.md`. The actual cache cost is proportional to how often the declared tier *changes* between consecutive steps, not to how often it's declared — a run of several same-tier steps in a row stays cache-stable even though each one re-declares.

### Resolved: Escalate-on-Retry
When a `ModelCall` attempt fails (e.g. unparseable tool-call output from a fast-tier model), Temporal's own retry mechanism fires. The activity reads its own attempt number via `activity.GetInfo(ctx).Attempt` and escalates the tier by one step per attempt (`fast → medium → expert`), capped at `expert` — never escalates past the top tier. `RetryPolicy.MaximumAttempts` should be sized to match the number of language tiers (3) so the retry ladder and the escalation ladder line up, rather than being an arbitrary retry count picked independently.

### Resolved: Storage — Env Vars, Not Postgres
Deployment-time configuration — not dynamic runtime data, so a Postgres table would be solving a problem this doesn't have. **Every configured tier owns its own full provider triple + tuning knobs** (2026-08-28, second revision — the earlier two-layer "shared provider defaults + per-tier model names" split was collapsed into one after real usage made it obvious that keeping any shared provider state locked the whole deployment to one provider for no meaningful benefit). Per tier:
- `LANGUAGE_<TIER>_MODEL` — the model name.
- `LANGUAGE_<TIER>_API_KEY` — the provider credential.
- `LANGUAGE_<TIER>_BASE_URL` — the provider endpoint.
- `LANGUAGE_<TIER>_MAX_TOKENS` — optional request-tuning knob, defaults to 4096.
- `LANGUAGE_<TIER>_CONTEXT_WINDOW` — optional, defaults to a conservative 128000.
- `LANGUAGE_<TIER>_{INPUT,OUTPUT,CACHED_INPUT}_COST_PER_MILLION_TOKENS` — optional, defaults to 0 (unknown, not free).

Wired through `deploy/helm/agent-harness-tenant`'s `llm.tiers.{fast,medium,expert}.*`; the chart's `templates/tenant-worker-deployment.yaml` and `templates/llm-secret.yaml` render one env-var block and one Secret key per *configured* tier only. AsyncOpenAI client construction is on-demand via `activities/activities/llm_client.py`, cached per unique `(base_url, api_key)` pair — a deployment with all three tiers on the same provider gets exactly one client, same connection-pool behavior as the pre-revision shared-client shape, without needing any shared state.

**No cross-tier fallback, no shared provider defaults.** Every tier the deployment actually uses must set MODEL, API_KEY, and BASE_URL. Any missing field surfaces at call time as a real error naming that specific tier (`llm.py`'s "no model resolved" check + `llm_client.py`'s "no base_url"/"no api_key" checks), not a silent degradation to a different tier or a shared default. Chart-side, the Helm template requires at least one of `llm.tiers.{fast,medium,expert}.model` to be set when `llm.enabled=true`, and for any tier whose model IS set, also requires that tier's `apiKey` and `baseURL` — a partial tier is almost always a mistake worth catching at render time rather than call time. Which specific tier a call actually needs still varies (bootstrap default is `medium`, the hint mechanism above can steer it elsewhere), so we don't require all three tiers up front. This matches the same numeric-tuning-deferral discipline elsewhere in this project — require what's structurally load-bearing, not what a hypothetical scenario might one day want.

**Superseded, kept for the reasoning trail:** an earlier version (2026-08-28, first revision) kept a two-layer split — `LLM_PROVIDER_{API_KEY,BASE_URL,MAX_TOKENS}` shared across every tier plus per-tier `LANGUAGE_<TIER>_MODEL` — reasoning that most deployments use one provider and duplicating credentials across tiers would be unnecessary boilerplate. That held theoretically but locked the whole design out of the actual use case that motivated per-tier separation in the first place (a subagent using a cheap fast-tier model on a different provider from the expensive expert-tier model), and the per-`(base_url, api_key)` client cache landed the same day made the "connection-pool sharing" argument for a shared default moot. Removed. Even earlier (2026-08-23), the registry accepted a `PIONEER_MODEL` fallback that let unset tiers silently reuse one shared model — also removed on the same 2026-08-28 pass, for the same reason: no silent fallbacks, real errors at the tier that isn't configured.

### Resolved: Pricing Table
`ModelConfig` gains three rates, not one: `input_cost_per_token`, `output_cost_per_token`, `cached_input_cost_per_token`. Providers price these separately (input/output routinely 3-5x apart; a prompt-cache hit is priced separately again, further discounted from regular input) — a single `cost_per_token` field would already be wrong for any real provider's pricing sheet. Configured per-tier via `LANGUAGE_<TIER>_{INPUT,OUTPUT,CACHED_INPUT}_COST_PER_MILLION_TOKENS` (per-million, matching how providers publish pricing — a raw per-token float would mean typing `0.0000027` into a Helm value). Unset defaults to `0.0`, meaning "no cost data," not "free" — same honest-scope choice `budget-guardrails.md` already made for token-count metrics shipping ahead of cost metrics. This closes model-registry's side of that component's stated dependency; budget-guardrails.md still needs to actually consume this table into real cost metrics, not built here.

### Resolved: Fallback Beyond Escalate-on-Retry
When `ModelCall` still fails after exhausting `RetryPolicy.MaximumAttempts: 3` (i.e. even the `expert` tier failed), `turn.go` now routes every early-return failure in `TurnWorkflow` — this one included — through a shared `failTurn` helper: marks the turn `failed` in Postgres (`Persist`, a value the `turns.status` CHECK constraint already allowed but nothing wrote), inserts a synthetic assistant-role error message so `Deliver` has something real to send, and delivers it (top-level turns only). Before this fix there was no defer/recover anywhere in `TurnWorkflow`, so a failure here — or from either of `TurnWorkflow`'s other two early-return sites, which shared the identical defect — skipped Persist/Deliver entirely: the turn's Postgres row stayed stuck at `running` forever and the user never received any response or error at all. Not a designed fallback that happened to be minimal; an actual silent drop, confirmed by reading the code path, not assumed.

### Resolved: Multi-Provider Abstraction — Provider ABC (2026-08-28, third revision)
Adopted a real per-provider ABC (`activities/activities/providers/base.py`), not a shared shim. Each concrete Provider owns one API-shape's worth of knowledge — request translation, response translation, streaming event handling, tool-schema shape — and every caller uses `Provider` methods (`call_model`, `call_model_streaming`, `summarize_text`) rather than the underlying SDK directly.

**Two supported providers today:**
- **`openai`** — `providers/openai_provider.py`, using the `openai` SDK. Covers every OpenAI-API-compatible endpoint (real OpenAI, DeepSeek, Qwen/DashScope, Groq, OpenRouter, Crusoe, self-hosted vLLM/llama.cpp servers, etc.) — they all speak the same protocol and differ only in `base_url` + model catalog. Per-tier `LANGUAGE_<TIER>_BASE_URL` is required (no canonical single endpoint).
- **`anthropic`** — `providers/anthropic_provider.py`, using the `anthropic` SDK. Native Messages API. The translation between our internal OpenAI-shaped conversation format and Anthropic's shape is real code: system prompt is pulled into a separate field (Anthropic takes `system` alongside `messages`), assistant tool calls become `tool_use` content blocks (vs. OpenAI's `tool_calls` array), tool results become `tool_result` content blocks in user messages (vs. OpenAI's `role: "tool"` messages), tool schemas are shape-flattened (`{name, description, input_schema}` vs. OpenAI's `{type:"function", function:{...}}`), streaming events are a discriminated union (`content_block_delta` with typed sub-events vs. OpenAI's flat delta shape). Same on_chunk sentence-boundary contract for callers. `LANGUAGE_<TIER>_BASE_URL` is optional (SDK has its own default at `api.anthropic.com`).

**Extending to a new-shape provider** (e.g. Google Gemini's native API, or a hypothetical binary/gRPC-shaped provider): add a class under `providers/` implementing the ABC, plus one dispatch case in `llm_client.get_provider`. That's the whole surface — no other file needs to know the new provider exists. Add the new provider name to `model_registry._KNOWN_PROVIDERS` too so `resolve()` accepts it.

**Universal internal conversation format stays OpenAI-shaped** — `messages`, `tool_calls`, `context_summaries` all use OpenAI's shape as the storage format (matches what `TOOLS_SCHEMA`/`build_conversation`/`lcm.assemble` all speak). Providers translate at their edges. Same reasoning as tool_call_ids: own the shape internally, adapt at the boundary.

**Escalate-on-retry works unchanged across providers.** Each attempt re-resolves the tier through `model_registry.resolve` and gets its own Provider instance from `llm_client.get_provider`. A fast-tier attempt escalating to expert could switch providers entirely (fast=DeepSeek, expert=Claude); the Provider dispatch machinery makes that transparent.
