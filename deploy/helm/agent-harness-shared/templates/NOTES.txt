It does NOT deploy Temporal server itself, and does NOT deploy any
tenant-specific components (tenant workers, each tenant's own Postgres/
Gateway/agent-brain/mcp-hub, tenant PV — those come from the
agent-harness-tenant chart, one release per tenant). This release has no
database of any kind (2026-09-25) — tenant identity is pure convention and
onboarding progress lives in Temporal itself, queryable live.

This release is currently configured to serve:

  Temporal address:    {{ .Values.temporal.address }}
  Temporal namespace:  {{ .Values.temporal.namespace }}
  Task queue:          {{ .Values.temporal.taskQueue }}

Check the pool is actually connecting:

  kubectl logs -l app.kubernetes.io/instance={{ .Release.Name }}

You should see:
  "loop worker starting: temporal=... namespace=... task_queue=..."

If the namespace above is unreachable or doesn't exist yet in Temporal (see
`temporal operator namespace create <name>`), this logs a retry line with
growing backoff instead of crashing the pod.

Onboarding a new tenant no longer touches this release at all (2026-09-26) —
every tenant shares the one namespace above already; only its own
agent-harness-tenant release needs installing.

Note: the ModelCall/ToolCall/Persist/Deliver/CompressContext activities that
this pool's workflows dispatch to are implemented by each tenant's own
agent-harness-tenant release (tenant-worker), on that tenant's OWN task
queue (Gateway/tenant-worker's TEMPORAL_TASK_QUEUE, "<release-name>-loop")
— never this chart's own {{ .Values.temporal.taskQueue }}, which is only
ever used to start a new CoordinatorWorkflow/TurnWorkflow execution, not to
dispatch its activities.
