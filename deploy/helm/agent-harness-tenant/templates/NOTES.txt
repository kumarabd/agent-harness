This is a PER-TENANT release (docs/components/multi-tenancy.md) — one
`helm install` per tenant, each with its own release name (its slug). It
deploys the whole tenant stack:
  - postgresql
    (Postgres — Bitnami subchart, one dedicated instance for this tenant;
    hosts both agent-harness's own database and agent-brain's, see
    values.yaml's postgresql.* comment)
  - {{ include "agent-harness.componentFullname" (dict "context" . "component" "worker") }}
    (Python — ModelCall/ToolCall/InsertMessage/Persist/Deliver/CompressContext
    activities; this tenant's dedicated fleet, holds this tenant's credentials)
  - memory-server / memory-worker-temporal
    (agent-brain, installed under fullnameOverride "memory" — components/
    memory-slot.md's memory backend, vendored subchart under
    charts/agent-brain/, one dedicated instance for this tenant)
  - tools (mcp-hub, installed under fullnameOverride "tools";
    see values.yaml's mcp-hub.* comment)
    (docs/components/tool-registry.md's mcp-hub-mediated tool tier, one
    dedicated instance for this tenant. Reachable at MCP_HUB_BASE_URL; also
    owns this tenant's own connection management end to end now (2026-09-26)
    — its own Postgres-backed `connections` table and POST/DELETE
    /api/connections, GET /api/catalog — reached through the shared router's
    /connections/ proxy. There is no separate connections service anymore.)

It does NOT deploy Temporal server itself, and does NOT deploy the
loop-worker pool (Session Coordinator + Turn Workflow) — that's the
tenant-agnostic shared pool, deployed ONCE for the whole cluster by the
sibling ../agent-harness-shared chart. 2026-09-26: this tenant shares that
pool's own Temporal namespace directly (no per-tenant namespace, nothing to
register with the shared release) — isolation is by task queue instead, this
tenant's own {{ .Release.Name }}-loop, computed automatically from the
release name.

This release's tenant worker is configured to poll:

  Temporal address:    {{ .Values.temporal.address }}
  Temporal namespace:  {{ .Values.temporal.namespace }}
  Task queue:          {{ .Release.Name }}-loop

Check it's actually connecting:

  kubectl logs -l app.kubernetes.io/component=worker

You should see a line like:
  "tenant worker starting: temporal=... namespace=... task_queue=..."

If it's crash-looping, the most common cause at this stage is
`temporal.address` being unreachable from inside the cluster (check network
policy / DNS) or pointing at a namespace it doesn't have access to.

Check Postgres came up (Bitnami subchart, standard naming):

  kubectl logs -l app.kubernetes.io/name=postgresql,app.kubernetes.io/instance={{ .Release.Name }}
  kubectl get pvc -l app.kubernetes.io/instance={{ .Release.Name }}

Then check the init-roles Job (creates agent-brain's and mcp-hub's databases
on that same instance) succeeded:

  kubectl logs -l job-name=postgres-init-roles

If tenantWorker.replicaCount > 1, the session-filesystem PVC's
storageClassName MUST support ReadWriteMany (mounted by every replica
simultaneously) — most cloud block-storage classes (EBS, PD-SSD, Azure
Managed Disks) do NOT support this; you need a file-storage-backed class
(EFS, Filestore, Azure Files, or equivalent). Postgres's own PVC (the
subchart's default) doesn't need this — it's ReadWriteOnce, mounted by a
single Postgres pod only.
