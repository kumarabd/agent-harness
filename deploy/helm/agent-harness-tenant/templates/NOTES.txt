It does NOT deploy Temporal server itself, and does NOT deploy the
loop-worker pool (Session Coordinator + Turn Workflow) — that's the
tenant-agnostic shared pool, deployed ONCE for the whole cluster by the
sibling ../agent-harness-shared chart. For turns in this tenant's namespace
to actually get scheduled, this tenant's `temporal.namespace` (below) must
be listed in that shared release's `temporal.namespaces`.

This release's tenant worker is configured to poll:

Check it's actually connecting:

  kubectl logs -l app.kubernetes.io/component=worker

You should see a line like:
  "tenant worker starting: temporal=... namespace=... task_queue=..."

If it's crash-looping, the most common cause at this stage is
`temporal.address` being unreachable from inside the cluster (check network
policy / DNS) or pointing at a namespace it doesn't have access to.

Check Postgres came up (Bitnami subchart, standard naming):

  kubectl logs -l app.kubernetes.io/name=postgresql,app.kubernetes.io/instance={{ .Release.Name }}
  kubectl get pvc -l app.kubernetes.io/instance={{ .Release.Name }}

Then check the init-roles Job (creates agent-brain's and mcp-hub's databases
on that same instance) succeeded:

  kubectl logs -l job-name={{ include "agent-harness.fullname" . }}-postgres-init-roles

If tenantWorker.replicaCount > 1, the session-filesystem PVC's
storageClassName MUST support ReadWriteMany (mounted by every replica
simultaneously) — most cloud block-storage classes (EBS, PD-SSD, Azure
Managed Disks) do NOT support this; you need a file-storage-backed class
(EFS, Filestore, Azure Files, or equivalent). Postgres's own PVC (the
subchart's default) doesn't need this — it's ReadWriteOnce, mounted by a
single Postgres pod only.
