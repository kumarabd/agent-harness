It does NOT deploy Temporal server itself. All workers are configured to poll:

  Temporal address:   {{ .Values.temporal.address }}
  Temporal namespace: {{ .Values.temporal.namespace }}
  Task queue:         {{ .Values.temporal.taskQueue }}

Check the workers are actually connecting:

  kubectl logs -l app.kubernetes.io/component=workflow-worker
  kubectl logs -l app.kubernetes.io/component=activity-worker

You should see each worker log a line like:
  "workflow worker starting: temporal=... namespace=... task_queue=..."
  "activity worker starting: temporal=... namespace=... task_queue=..."

If either worker is crash-looping, the most common cause at this stage is
`temporal.address` being unreachable from inside the cluster (check network
policy / DNS) or pointing at a namespace neither worker has access to.

{{- if .Values.postgres.enabled }}

Check Postgres came up:

  kubectl logs -l app.kubernetes.io/component=postgres -c postgres
  kubectl get pvc {{ include "agent-harness.fullname" . }}-data

A StatefulSet stuck Pending usually means the PVC never bound — check
`kubectl describe pvc` for a storage-class/capacity error. If
activityWorker.replicaCount > 1, the PVC's storageClassName MUST support
ReadWriteMany (the session filesystem tree is mounted by every replica
simultaneously) — most cloud block-storage classes (EBS, PD-SSD, Azure
Managed Disks) do NOT support this; you need a file-storage-backed class
(EFS, Filestore, Azure Files, or equivalent).
{{- end }}

Note: the ModelCall/ToolCall/Persist/Deliver/CompressContext activities in
this release are stubs — no real LLM or gateway are wired up yet, and the
activities don't yet actually read/write Postgres by reference (that content
contract is resolved in docs/components/temporal-workflow.md but not yet
implemented in code — Postgres/PV are deployed and reachable here, ahead of
the application code that will use them). See the repo root README.md for
what's real vs. stubbed.

CAVEAT: the Postgres StatefulSet/PVC/Secret templates in this chart have been
validated with `helm lint` and `helm template` only — not yet installed
against a real Kubernetes cluster. Watch closely on first real install,
especially subPath auto-creation permissions and the postgres image's
uid/gid (999) against your cluster's storage provisioner.
